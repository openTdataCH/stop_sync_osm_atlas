# E3 Routes

At a high level, the route pipeline has three stages:

1. Adapters return source-specific route records, optionally reading acquisition caches in `data/processed/`.
2. `transport_matcher.routes` normalizes explicit input records into shared `line_families`, `itineraries`, and `stop_calls` after stop matching.
3. The engine builds `line_family_matches` and `itinerary_matches` and exports them in the result bundle. The app validates and persists those rows.

This chapter explains the route model itself. Source extraction details remain in the preprocessing chapter, and stop-to-stop route-assisted matching remains in the matching chapter.

## Route Layers

The implemented route pipeline has three conceptual layers:

| Layer | Purpose | Main Outputs |
|---|---|---|
| Adapter products | Preserve GTFS-derived source route structure and OSM PTv2 route structure | ATLAS route cache CSVs plus current-run OSM route frames; optional `osm_route_*.csv` diagnostics |
| Normalized comparison | Convert both sides into a shared route model | `line_families`, `itineraries`, `stop_calls` |
| Matching | Link equivalent families and itineraries | `line_family_matches`, `itinerary_matches` |

## Main Inputs

- GTFS route-family and itinerary artifacts built jointly by `src/transport_matcher/adapters/get_atlas_gtfs.py` and the orchestration/export code in `src/transport_matcher/adapters/get_atlas_data.py`
- OSM route-master and route-relation artifacts built without network access by `src/transport_matcher/adapters/osm_routes.py`
- base stop-matching output used by `src/transport_matcher/routes.py` to resolve physical stop identity across both sides

## Main Responsibilities

The route subsystem inside `src/transport_matcher/` is responsible for:

- reconstructing ATLAS-side line families and itineraries from GTFS
- extracting OSM route-master, route-relation, tag, member, and stop frames from the current XML; CSV export is optional diagnostics
- resolving route stops onto shared stop identities where possible, preferring matched ATLAS `sloid` values and falling back to UIC or raw canonical keys when necessary
- matching ATLAS and OSM line families
- scoring and pairing ATLAS and OSM itineraries only within already matched families

## Persistence Boundary

The comparator has no file-I/O responsibility: `routes.py` receives explicit DataFrames from adapters and returns a complete route payload. In the Swiss runner, ATLAS route products may come from verified cache CSVs, while OSM route frames are always rebuilt from the current XML. Passing an output directory to the OSM adapter can write `osm_route_*.csv` diagnostics, but those files are not runtime inputs.

- The active import schema keeps `atlas_line_families` and `osm_route_relations` as route-source anchor tables, rather than every intermediate adapter frame.
- The web app reads normalized route data from `line_families`, `itineraries`, `stop_calls`, `line_family_matches`, and `itinerary_matches`.

It also supports two different consumers:

- **stop matching runtime**: `SourceState`, `OsmState`, `RouteState`, and `RouteMatchPredicate`
- **route comparison**: `transport_matcher.routes`; the independent app reads exported results for `/routes` queries

## Schema and portability

Schema v1 retains established route field names such as `atlas_line_id` and `source_sloid` for wire compatibility. Generic adapters use source-neutral names internally; the result projection maps them to the deprecated schema-1 fields. Their values can be generic namespaced source IDs. Swiss adapters supply the Swiss route-year normalizer; the comparison module does not apply it automatically. Generic GTFS preserves ordered calls and feed-scoped identities, including repeated loop visits.

The importer does not read route CSVs, compare sequences or choose links. Route results are complete before the app is invoked. Route-level diagnostic `Problem` rows beyond the existing stop problems remain documented separately as planned work.
