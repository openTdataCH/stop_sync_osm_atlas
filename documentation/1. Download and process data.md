# Download and process data

This chapter explains how we prepare the datasets that power the matching pipeline. Before any OSM ↔ ATLAS matching happens, we download authoritative inputs, apply clear filters, and produce compact, reproducible CSVs used by downstream steps.

### Who is this for
- Public view: a gentle, high-level story of what we download and why the filters matter.
- Developer view: exact URLs, filters, file formats, and references to the code that implements each step.

### What we download and produce
| Input | Source | Key filters | Primary outputs |
| --- | --- | --- | --- |
| ATLAS traffic points (stops) | `https://data.opentransportdata.swiss/en/dataset/traffic-points-actual-date/permalink` | Switzerland only, inside precise CH polygon; validTo in the future; `trafficPointElementType == BOARDING_PLATFORM` | `data/raw/stops_ATLAS.csv` |
| GTFS (timetable) | Example 2025: `https://data.opentransportdata.swiss/de/dataset/timetable-2025-gtfs2020/permalink` | Swiss stops only (`stop_id` prefix 85 + inside CH polygon). Streaming two-pass over `stop_times.txt` to build unique `(stop_id, route_id, direction_id)` | Integrated in-memory; unified with HRDF to `data/processed/atlas_routes_unified.csv` |
| HRDF (HAFAS raw data) | See Cookbook: `https://opentransportdata.swiss/en/cookbook/timetable-cookbook/hafas-rohdaten-format-hrdf/` | Parse only `GLEISE_LV95`, `FPLAN`, `BAHNHOF`; two-pass on `GLEISE_LV95` to target only needed sloids | Direction tuples per sloid; unified to `data/processed/atlas_routes_unified.csv` |
| OSM (nodes + routes) | Overpass API `http://overpass-api.de/api/interpreter` | Switzerland area; PT nodes (`public_transport`, `highway=bus_stop`, etc.), plus route relations referencing them | `data/raw/osm_data.xml`, `data/processed/osm_nodes_with_routes.csv`, `data/processed/osm_routes_with_nodes.csv` |
