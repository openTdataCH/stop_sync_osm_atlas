# A3.1 Dependencies and Builds

The engine and review app install independently. The engine's `pyproject.toml` owns NumPy/SciPy plus optional adapter dependencies. Flask, SQLAlchemy, PostGIS connections, reports and scheduling dependencies belong to the review deployment.

| Build | Contents |
|---|---|
| Sibling engine `Dockerfile` | Engine package, selected adapters and CLI. No backend code. Build from the engine repository root. |
| `docs-diagram-stage` | Build-only Node environment with local Chromium. Uses the pinned Mermaid package plus `puppeteer-core` to pre-render content-addressed SVGs; only those SVGs cross into the app image. |
| `app-stage` | Review app, templates, static assets, docs and example bundle. No engine source or package. |
| `test-stage` | App image plus test tools and APScheduler for job tests. No engine. |
| `scheduler-stage` | Deployment composition: app importer/jobs plus a separately installed engine executable. Communicates through files, with no cross-project Python imports. |

```bash
python -m pip install -e "../engine[test]"
python -m pip install -r requirements-base.txt -r requirements-web.txt -r requirements-test.txt -r requirements-scheduler.txt
```

## Application release identity and Git tag

The review application has its own release identity, independent of the engine:

| Identifier | Example | Meaning |
|---|---|---|
| Application version | `0.6.0` | Canonical version declared in `backend/version.py`, shown in the navbar and on the App documentation badge. |
| Application Git tag | `v0.6.0` | Annotated tag attached to the exact application release commit. It exists in the application repository and must never be moved or reused. |
| Application commit SHA | `0123abcd...` | Immutable identity of the application source. Deployments should record the SHA or an image digest derived from it. |

The application and engine are separate repositories, so each may have a tag such as `v0.6.0` without conflict. A tag belongs only to the repository in which it was created. An application release tag says which importer, database migrations, API and UI were deployed; it does not select an engine release.

Application release checklist:

1. Update `APP_VERSION` in `backend/version.py` and add the release to `documentation/Changelog.md`.
2. Run the application, JavaScript and producer-to-consumer contract tests.
3. Commit the complete release, including migrations and documentation.
4. Create an annotated `v<application-version>` tag on that commit and push it. Never tag an earlier commit while release changes are uncommitted, and never force-move a published tag.
5. Deploy that exact commit or an image built from it, and record the commit SHA or immutable image digest.

```bash
git tag -a v0.6.0 -m "Review application 0.6.0"
git push origin v0.6.0
git rev-list -n 1 v0.6.0
```

## Engine release identity and deployment pin

Do not use the words “version” and “tag” interchangeably. The integration uses four separate identifiers:

| Identifier | Example | Meaning |
|---|---|---|
| Engine package version | `0.1.1` | Release version declared by the engine and written to bundle manifests as `engine_version`. |
| Git tag | `v0.1.1` | Human-readable Git/GitHub name attached to the release commit. Published release tags must never be moved or reused. |
| Commit SHA | `0123abcd...` | Immutable identity of the exact engine source used for a build. This is what `ENGINE_REF` pins. |
| Result schema version | `1` | Version of the file contract consumed by the app. It changes independently of the engine package version. |

The ignored local `.env` contains the private location and immutable pin:

```dotenv
ENGINE_REPO=https://github.com/your-account/matching-engine.git
ENGINE_DIR=../engine
ENGINE_REF=<full-commit-sha>
```

Before every build, run:

```bash
./scripts/verify_engine_checkout.sh
```

The verifier rejects a different origin, a tag/SHA that does not resolve to `HEAD`, or an engine checkout with uncommitted files. Docker receives the already-verified directory as a named build context; Git credentials and the private URL do not enter an image.

### Upgrade procedure

1. Fetch the engine repository and inspect the intended annotated release tag.
2. Resolve it with `git -C ../engine rev-list -n 1 v0.1.1`.
3. Check out that commit and run the engine suite plus the producer-to-consumer contract test.
4. Put the full resolved SHA—not a branch name—in `ENGINE_REF`.
5. Run `./scripts/verify_engine_checkout.sh`.
6. Rebuild the app/documentation and scheduler images, then verify that the documentation badge and installed `transport-matcher` package report the expected package version.

For CI, configure `ENGINE_REPOSITORY`, `ENGINE_REF` and `ENGINE_REPOSITORY_TOKEN` in repository settings. Do not commit a private repository URL or access token.

The package version may change without a schema change when algorithms or documentation change. A breaking result-format change requires a schema-version change and coordinated consumer support.

The requirement list and diagram above can be regenerated with `python documentation/scripts/generate_dependency_overlap.py`. Engine extras are defined separately in the sibling engine repository’s `pyproject.toml`; that file is the authoritative package dependency list.

CI verifies engine tests, app tests without an engine installation, JS tests, and an actual producer-to-consumer fixture run. CI does not modify or commit generated documentation.

Frontend and documentation-build JavaScript dependencies are pinned in `package.json` and `package-lock.json`. The Mermaid package is shared by the browser documentation view and the local PDF pre-renderer so both paths interpret the same diagram syntax. Chromium exists only in the discarded `docs-diagram-stage`; production PDF generation consumes the resulting SVG cache and has no Node, browser, Kroki, or outbound-network requirement.

The Swiss/acquisition engine extras include `duckdb>=1.4,<2` for native GTFS processing. The generic GTFS extra only adds pandas. DuckDB is absent from the independent web image; PostgreSQL COPY uses the app's psycopg dependency. After changing engine or scheduler dependencies, rebuild and recreate the scheduler service so its installed `transport-matcher` executable matches the checkout. See [Pipeline Performance](../engine/documentation/5.2%20Pipeline%20Performance.md) for memory/thread settings and benchmark commands.
