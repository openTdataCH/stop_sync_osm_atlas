# A3.1 Dependencies and Builds

The engine and review app install independently. The engine's `pyproject.toml` owns NumPy/SciPy plus optional adapter dependencies. Flask, SQLAlchemy, PostGIS connections, reports and scheduling dependencies belong to the review deployment.

| Build | Contents |
|---|---|
| `engine/Dockerfile` | Engine package, selected adapters and CLI. No backend code. Build with `docker build -t transport-matcher engine`. |
| `docs-diagram-stage` | Build-only Node environment with local Chromium. Uses the pinned Mermaid package plus `puppeteer-core` to pre-render content-addressed SVGs; only those SVGs cross into the app image. |
| `app-stage` | Review app, templates, static assets, docs and example bundle. No engine source or package. |
| `test-stage` | App image plus test tools and APScheduler for job tests. No engine. |
| `scheduler-stage` | Deployment composition: app importer/jobs plus a separately installed engine executable. Communicates through files, with no cross-project Python imports. |

```bash
python -m pip install -e './engine[test]'
python -m pip install -r requirements-base.txt -r requirements-web.txt -r requirements-test.txt -r requirements-scheduler.txt
```

The requirement list and diagram above can be regenerated with `python documentation/scripts/generate_dependency_overlap.py`. Engine extras are defined separately in `engine/pyproject.toml`; that file is the authoritative package dependency list.

CI verifies engine tests, app tests without an engine installation, JS tests, and an actual producer-to-consumer fixture run. CI does not modify or commit generated documentation.

Frontend and documentation-build JavaScript dependencies are pinned in `package.json` and `package-lock.json`. The Mermaid package is shared by the browser documentation view and the local PDF pre-renderer so both paths interpret the same diagram syntax. Chromium exists only in the discarded `docs-diagram-stage`; production PDF generation consumes the resulting SVG cache and has no Node, browser, Kroki, or outbound-network requirement.

The Swiss/acquisition engine extras include `duckdb>=1.4,<2` for native GTFS processing. The generic GTFS extra only adds pandas. DuckDB is absent from the independent web image; PostgreSQL COPY uses the app's psycopg dependency. After changing engine or scheduler dependencies, rebuild and recreate the scheduler service so its installed `transport-matcher` executable matches the checkout. See [Pipeline Performance](../engine/documentation/5.2%20Pipeline%20Performance.md) for memory/thread settings and benchmark commands.
