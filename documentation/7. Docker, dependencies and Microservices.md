# 7. Microservices, Dependencies and Docker Architecture

This section describes the implemented container architecture, dependency split, migration flow, and runtime ownership boundaries.

## Dependency Split

Dependencies are split by runtime responsibility:

- `requirements-base.txt`: shared runtime foundations (`SQLAlchemy`, `psycopg`, `GeoAlchemy2`, `requests`)
- `requirements-web.txt`: web-only stack (`Flask`, `Flask-Limiter`, `Flask-Talisman`, `Flask-Migrate`, `weasyprint`, `mistune`, `bleach`)
- `requirements-scheduler.txt`: pipeline/scheduler stack (`pandas`, `numpy`, `scipy`, `geopandas`, `shapely`, `APScheduler`, `redis`, `Flask-SQLAlchemy`)
- `requirements-test.txt`: test-only packages (`pytest`, `pytest-flask`, `pytest-mock`)

Key cleanup points:

- Test dependencies are no longer in runtime requirement files.
- Scheduler no longer installs `Flask-Limiter`, `Flask-Talisman`, or `Flask-Migrate`.
- Scheduler no longer imports/executes migration bootstrap from the importer.

## Dockerfile Stages

The Dockerfile now has four logical build targets:

1. `base`
   - Common Python/system setup.
   - Installs `requirements-base.txt`.

2. `app-stage`
   - Web runtime image.
   - Installs PDF system libs (Cairo/Pango) and `requirements-web.txt`.

3. `scheduler-stage`
   - Pipeline runtime image.
   - Installs geospatial system libs (GDAL/GEOS/PROJ) and `requirements-scheduler.txt`.

4. `test-stage`
   - Test execution image.
   - Starts from `app-stage`, adds scheduler geospatial libs and installs both `requirements-scheduler.txt` and `requirements-test.txt`.

This keeps production/runtime images cleaner while still supporting full-suite tests in Docker.

## Compose Services

`docker-compose.yml` defines these primary services:

- `db`: PostgreSQL + PostGIS
- `redis`: shared cache/status/lock backend
- `migrator`: one-shot migration service (`flask db upgrade`)
- `app`: Flask web API/UI (depends on successful `migrator` completion)
- `scheduler`: APScheduler worker (depends on successful `migrator` completion)

Also defined for local test workflows:

- `test`: uses `test-stage` image for pytest execution

## Migration Ownership (Implemented)

Migrations are now owned by a dedicated one-shot container:

- Service: `migrator`
- Command: `python matching_and_import_db/database/init.py && flask db upgrade`

`app` and `scheduler` start only after migration completion via `depends_on: condition: service_completed_successfully`.

`entrypoint.sh` behavior was adjusted accordingly:

- `AUTO_MIGRATE=false` (default): app container skips migration logic
- `AUTO_MIGRATE=true`: app can still run migration flow explicitly (development override)

## Scheduler and Status Behavior

Scheduler implementation:

- Service module: `matching_and_import_db/scheduler/service.py`
- Runner: `matching_and_import_db/scheduler/job_runner.py`
- Shared status/lock backend: `backend/services/pipeline_status.py`

Default schedule:

- Timezone: `Europe/Zurich`
- Time: `02:00`

Config via:

- `PIPELINE_TIMEZONE`
- `PIPELINE_SCHEDULE_HOUR`
- `PIPELINE_SCHEDULE_MINUTE`
- `PIPELINE_IMPORT_ETA_SECONDS`

Status API:

- `GET /api/system/pipeline_status`

Fields include `status`, `phase`, `message`, `blocking_maintenance`, `eta_seconds`, `run_id`, `trigger`, `last_success_at`, `last_error`, `next_run_at`.

## PDF Ownership Boundaries

### Stats summary PDF

Ownership moved to app runtime:

- Scheduler now exports stats JSON only (`data/stats.json`).
- App endpoint `/api/download_stats_summary_pdf` generates/regenerates `documentation/generated/stats_summary.pdf` on demand.
- Optional forced regeneration is supported with `?refresh=true`.

### Documentation PDF

Docs PDF is no longer generated at app startup.

- Built on demand by docs route logic or explicitly with the `Docs: Build PDF` task.

## Entry Point Modes

Shared `entrypoint.sh` supports:

- `app` mode (default): waits for DB, optionally migrates (only when `AUTO_MIGRATE=true`), starts Flask
- `scheduler` mode: waits for DB, starts APScheduler service

Optional startup pipeline run remains available:

- `RUN_STARTUP_PIPELINE=true`

## Validation and Tasks

VS Code task updates:

- `Docker: Run All Tests` and `Docker: Run Small Pipeline Test` now use the `test` service.

Pipeline tasks still execute through scheduler runner:

- `Docker: Run Matching & Import (Existing Data)`
- `Docker: Run Full Data Pipeline (Download & Match & Import)`
- `Docker: Trigger Scheduled Pipeline Now`

## Concurrency and Safety

- Scheduler uses a distributed Redis lock to prevent overlapping runs.
- Import remains a full refresh of import tables.
- UI blocking maintenance mode is only enabled during blocking import phases.

## Operational Notes

- `app`, `scheduler`, and `test` mount the same project root into `/app` for local development.
- `user_input_db` remains separate and is not truncated by import jobs.
- If Redis is unavailable, status falls back to in-process memory (best effort), but distributed locking guarantees are reduced.
- `backend/extensions.py` now tolerates missing web-only extension packages in non-web environments, which keeps scheduler imports safe while preserving strict behavior when app initializes web extensions.
