# Review application changelog

This page records notable changes to the review application, its database import, browser interface and deployment. Matching releases are recorded separately in the [matching engine changelog](../engine/documentation/Changelog.md).

Changes to the [result bundle contract](../engine/documentation/Result%20bundle%20format.md) are recorded in both changelogs: here from the consumer side and in the engine changelog from the producer side.

---

## Unreleased

### Result bundle

- **SLOIDs in OSM** — The engine now links an OSM element that names its ATLAS platform with `ref:sloid` or `railway:ref:sloid` before any other rule, as `sloid_identifier`, and also reads platform ways that carry one ([E2.1](../engine/documentation/2.1%20Reference%20matching.md#identifier-matching-identifier)). The application shows that rule first in the map's Matched filter (**SLOID in OSM**) and in **Matches by rule**. The new problem type `identifier` ("OSM SLOID" on the Problems page, in problem statistics and exports) lists elements whose SLOID names a platform more than 150 m away (P1), names no platform (P2), or is not a SLOID (P3); its detail panel shows the element's SLOID tags beside the matched platform's SLOID. `/data/analytics` adds a **SLOID in OSM** block to the OSM stops section, and `railway:ref:sloid` to the tag table. The block counts elements with a SLOID, the elements and platforms linked by it, and matched elements that could still be tagged. The bundle reader accepts the optional `identifier_only` flag on OSM rows. No migration is needed; import a new bundle. See [A2.4](2.4%20Problems%20Page.md#osm-sloids).
- **Source-neutral route records** — The importer reads the engine 0.1.0 bundle: `source_routes`, a `side` and stable `key` on families and itineraries, `source_stop_key`, `osm_node_id` and `station_ref` on stop calls, `source_line_family_id` and `source_itinerary_id` on matches, and the `unknown_source_stop_references` counter. `projection.py` maps them onto the existing tables, so no migration is needed. The `quality_metrics` many-to-one block (`source_to_multiple_osm`, `osm_to_multiple_source`) and the GTFS coverage counter `atlas.resolved_by_gtfs` use the engine's new names. Import a new bundle after upgrading.
- **Match types name their evidence** — Each match type names the rule and branch that decided it, such as `uic_reference_local_ref`, `gtfs_shared_route` or `local_ref_distance`, and OSM stop units name their PTv2 layout (`ptv2_two_sided_stop` with `middle` and `side` members). The Matched filter groups rules as identifier, GTFS route and distance matching and sends rule keys; `backend/services/matching_rules.py` expands them to match types. Analytics shows **Matches by rule** in run order, with one row per branch. Migration `20261106_000010` rewrites stored rows and constraints. See [A2.2](2.2%20Filters%20and%20Search%20logic.md#matched-branch) and [E2](../engine/documentation/2.%20Matching%20process.md#the-matching-rules).
- **Disused OSM elements** — The bundle reader accepts the optional `disused` flag on OSM `unmatched` rows and checks it against `lifecycle`, the unmatched-problem coverage and `disused` problems. The importer stores disused elements as `osm_disused` map entries outside the stop units and counts, and keeps every tag of each OSM element in `osm_nodes.osm_tags`. The map has an "OSM disused" filter and draws them as grey hollow rings with a `U`; the Problems page, problem statistics and exports gain the `disused` type; OSM popups list all tags. Migration `20261030_000008` adds `osm_lifecycle` and `osm_tags`; run migrations, then import a bundle to fill them. See [A1.1 Bundle import and publication](1.1%20Import%20Process.md#disused-osm-elements).

### Operators

- **Simpler operator cards** — Each card now stacks the ATLAS operator above a breakdown of its matched OSM stops by `operator` value: a stacked bar plus one row per value, including a "Not tagged" row, so the counts add up to the total. `operator:wikidata` uses the same rows. A status pill (Consistent, Partly tagged, N different values, Not tagged) summarises each operator. The connector arrows, nested boxes and repeated labels are gone, and "See on map" buttons are now compact "Map" links.
- **Distinct stop counts** — "Matched" in the card header now counts distinct ATLAS stops, and the tag breakdown counts distinct OSM stops. Before, both counted match pairs, so an ATLAS stop matched to several OSM stops could make "matched" exceed the operator's stop total. See [A2.7 Colours and styles](2.7%20Colours%20and%20styles.md).

### Routes

- **Variants compared by station** — A stop at another platform of the same station now counts as shared, in the engine's variant pairing ([E3.2](../engine/documentation/3.2%20Route-Route%20Matching.md#step-4-pair-the-itineraries)) and in the comparison and *Highest overlap* figures. The S10 relation *Uetliberg → Selnau* now pairs with the ATLAS variant ending at Selnau, 8 of 8, instead of the one running on to Zürich HB, 8 of 9. When several ATLAS variants share enough stops, the one with the same first and last stop as the OSM relation wins, then the higher overlap: bus 791 *Schwägalp → Urnäsch* pairs with the variant ending at Urnäsch, not the one running on to St. Gallen. The stop list still marks such a row *Same station, other platform*, and the summary says how many stops are *at another platform*. On the data of 6 November 2026, 3,727 variants are paired instead of 2,477. No migration is needed: `engine.ref` pins engine `e733be5`, which contains the change, and the next import shows it.
- **Short lines and station-only calls** — The engine links a line by number and stops when it shares four stops, or every stop of a shorter line but at least two, so two-station cableways and funiculars can now be linked. It also keeps the station of a Swiss GTFS call that names only a station SLOID; before, 24,862 such calls, mostly ferries and aerialways, had no stop identity ([E3.2](../engine/documentation/3.2%20Route-Route%20Matching.md#by-line-number-and-stops)). On the data of 7 November 2026, 2,300 lines are linked instead of 2,250, none lost, and 4,405 variants are paired instead of 3,727. Stop matches and problems are unchanged. No migration is needed: `engine.ref` pins engine `8f89259`, which contains the change, and the next import shows it.
- **Lines linked by number and stops** — The engine now links two lines through a `gtfs:route_id` of another timetable year only when they also have the same line number and share a stop, and links an OSM line without a usable ID to the GTFS line with the same mode, line number and stops, as `line_number_and_stops` ([E3.2](../engine/documentation/3.2%20Route-Route%20Matching.md#step-2-match-the-families)). On the data of 6 November 2026 this removes 29 links between lines that share no stop, mostly lines with the same number in different towns, such as bus 11 around Fribourg linked to Basel's bus 11, and adds 116 links. `/data/analytics` names the new link method and two new reasons why a line stays unlinked: an OSM line whose `gtfs:route_id` of another year names a different line, and a GTFS line whose route ID an OSM line carries from another year for a different line. No migration is needed: `engine.ref` pins engine `18d7837`, which contains the change, and the next import shows it.
- **Stored highest overlap for unmatched variants** — The import now computes, for every ATLAS and OSM itinerary, the itinerary of the other source sharing the most stops in order, and publishes it with the snapshot in the new `itinerary_best_overlaps` table. Route cards render the "Highest overlap" figure directly instead of scanning every itinerary after each page load (previously about 9 seconds for 20 unmatched OSM variants on the Swiss dataset). Variants without any shared stop now say so instead of showing an arbitrary 0% route. The batch endpoint `/api/routes/comparison/best` and the `best` field of `/api/routes/comparison/options` are removed. Run migrations, then import a bundle to fill the table. See [A2.6 Routes pages](2.6%20Routes%20Pages.md).
- **Paired route details** — On a matched route, opening the ATLAS or the OSM details card opens the other one too, so both attribute lists sit side by side for comparison. The two cards keep the same height. Cards of unmatched routes still open on their own.
- **Variant maps show stop matching** — Marker colours on a variant map are those of stop matching, as on the main map, in every view; the comparison no longer turns a matched stop red. The comparison adds its own marks instead: a solid line for the same stop, a dashed amber line for the same station at another platform, a dashed amber ring for a stop the other variant lacks, and a thin line from each stop to its own stop matches, drawn faded when neither variant calls at them. A **Legend** explains them. In the stop list, the two platforms of one station share an amber row, *Same station, other platform*. See [A2.6](2.6%20Routes%20Pages.md#expanded-variant-layout).
- **Main map link opens the variants** — A variant map's **Main map** button opens the main map on the variants it shows (`?atlas_variant=…&osm_variant=…`), at its view, instead of only at its view.
- **Wider variant maps** — From 1600px the routes page widens to 1760px and the map takes 45% of the card; between 1200px and 1600px it takes 42%.
- **Route filter narrowed to variants** — On the main map, the route chip's dropdown lists the line's variants under their direction, each named once with an **ATLAS** and/or **OSM** tag. Choosing one keeps exactly its stops and their matches. `/api/data` and the other filtered endpoints take `route_variants`, and the new `/api/routes/variants` lists a line's variants or resolves a variant link. `atlas_variant` and `osm_variant` in a main map link open the filter ([A2.9](2.9%20Permalinks.md#map)); an ATLAS variant is found with the timetable year ignored. See [A2.2](2.2%20Filters%20and%20Search%20logic.md#route-filters-and-their-variants).
- **Direction of the first route filter** — Choosing a direction in the chip of the first route filter did nothing: its dropdown had no index, so the choice went nowhere. `route_directions` also lost its position when a filter before it had no direction. Both are fixed.

### Public API

- **Stop lookup for scripts and AI agents** — `/api/lookup` returns every match of a stop as JSON, with distances, match types, problems, OSM tags and the snapshot's attribution. It takes the permalink identifiers (`osm=node/<id>`, `osm=way/<id>`, `sloid=`) plus `uic_ref=` for a whole station, never database row numbers, and it is the only `/api/` endpoint whose fields are kept stable. See [A2.10 Public API](2.10%20Public%20API.md).
- **Stop links readable without JavaScript** — Map and Problems links with `sloid` or `osm` name the stop in their title, description and `og:` tags, link to its lookup and carry a visually hidden summary, so link previews and fetch tools see the stop.
- **`/llms.txt` and `robots.txt`** — A new `/llms.txt` explains the site and the lookup to AI agents. `robots.txt` allows `/api/lookup` and puts its most specific rule first, so parsers that apply the first matching rule no longer read `Allow: /` as permission for every `/api/` path.

### Reliability and interface

- **No invented match type for two-sided stop middles** — The importer stored `uic_two_sided_stop` for the effectively matched middle of a two-sided stop, although the bundle has no match for it and the engine names that match type after the profile. The middle now has no match type; its popup reads **Middle of a matched two-sided stop**, with the same link to the rule. `backend/services/matching_rules.py` is now the only file that spells match types: the Matched filter and the **SLOID in OSM** statistics look them up there by rule key. `tests/test_match_type_names.py` keeps it that way, and the engine import contract fails when the engine writes a match type that file does not list. Import a new bundle to update stored rows. See [A1.1](1.1%20Import%20Process.md#match-types).
- **Faster map** — Circle markers and lines are drawn on one canvas per map instead of as thousands of SVG elements. Eight pans of central Zürich at zoom 15, on a processor slowed four times, blocked the page for 0.6 s instead of 2.2 s. On touch screens, a tap up to 5 px outside a marker still hits it. JSON answers are gzipped: that view's `/api/data` answer is 80 kB instead of 590 kB. See [A2.1](2.1%20Map%20Data%20Loading%20and%20Rendering.md#markers).
- **Round lettered markers** — From zoom 18, the markers with a letter had their border cut flat on four sides and were 2 px narrower than the circles they replace. They are now round and the same size.
- **Links to the docs** — An info icon beside the map's Matched, OSM groups and Problems filters, and the Problems page's type filter, opens the documentation section that explains them. The match type in a popup opens the section of its rule, such as the group distance rules for `uic_ref_group_long_distance`, instead of the top of the page. On the Problems page, a chip names the problem's type and opens its section of the stop problems page. The docs portal now scrolls to the linked section after drawing the page's diagrams; before, the diagrams drawn above it pushed it out of view. A test checks that every such link names an existing section. See [A2.8](2.8%20Documentation%20Page%20Delivery.md).
- **Clearing a drawn area** — In the Problems page's **Area** dialog, **Clear selection** wipes the rectangle so it can be drawn again. **Show problems here** now reads **Filter problems in this area**; after clearing an applied area it reads **Show all problems**, which replaces **Remove area**. See [A2.4](2.4%20Problems%20Page.md#area).
- **The Problems map stays on the problem** — While a problem is shown, the map cannot be panned past the problem's box or zoomed out beyond it, so no area without loaded stops comes into view. The box spans every ATLAS and OSM position of the problem and its members, plus 0.02° on every side, and **See other markers** loads the stops of that box; before, it loaded a box around the first position only. See [A2.4](2.4%20Problems%20Page.md#context-markers).
- **Disabled buttons keep their colour** — A disabled button, such as **Filter problems in this area** before a rectangle is drawn, turned Bootstrap blue. It now keeps its own colour, faded. See [A2.7](2.7%20Colours%20and%20styles.md).
- **Shorter map banners** — The banner says what the map shows, then what to do, without emoji: zoomed out it reads "Showing only unmatched ATLAS stops. Zoom in to see all." (it read "📍 Zoomed out: only ATLAS stops without an OSM match (red). Zoom in to see every stop."), and with filters "Showing 1,800 filtered stops. Zoom in to see all." or "245 stops match the filters." It no longer repeats the number of active filters, which the filter chips show. Only the error message keeps its ⚠️. On the GTFS/SLOID routes page, the banner reads "Zoom in to see all markers here."
- **Problems by area** — The map has a **Problems** dropdown: *All problems*, one checkbox per problem type and the priorities P1 to P3. It keeps the stops with such a problem, so the map shows the problems of the area in view; the summary, **Random** and Top N follow it, and links keep it as `problem_type` and `priority`. On the Problems page, **Area** opens a map where two clicks draw a rectangle; the list, the type counts and the link (`bbox=west,south,east,north`) then keep the problems inside it, and the Problems map outlines the area. `/api/problems` and `/api/problems/stats` take `bbox`. See [A2.2](2.2%20Filters%20and%20Search%20logic.md#problem-predicate) and [A2.4](2.4%20Problems%20Page.md#area).
- **Messages without browser dialogs** — The twelve `alert()` boxes of the map are gone. Messages such as "This filter is already applied." or "No stop found for the current filters." now appear as the app's toast, through `SharedUtils.notify()`, which takes plain text, and the ESLint rule `no-alert` keeps new ones out. The four ways of adding a search filter share one duplicate check.
- **Labels** — The OSM entity filter reads *OSM ways* in the menu and in its chip (it read *Osm ways* and *OSM: Ways*). The *OSM disused* checkbox loses its explanation, the only one in the filter menus. On wide screens **Random** is its icon, with its hint on hover, to leave room for the summary panel.
- **Counts with thousands separators** — The map summary, the zoom banner and the Problems page show counts grouped by thousands: *49,452 OSM stops*, *38,166 problems*, and the entry chip reads *Entry 1 of 38,166* instead of *Entry 1/38166* (`SharedUtils.formatCount`).
- **Map legend and a clearer first view** — A **Legend** above the layer switcher explains the marker colours, the hollow disused ring, match lines and OSM stop lines with the zoom they appear at, and the letters shown from zoom 18. It opens on a first visit to a wide screen and then stays as the viewer left it. The zoomed-out banner now says what the red markers are: "Zoomed out: only ATLAS stops without an OSM match (red). Zoom in to see every stop." See [A2.1](2.1%20Map%20Data%20Loading%20and%20Rendering.md#legend).
- **Shareable filter links** — The map's address bar now keeps every filter: scope, matching rules and unmatched reasons, transport and entity types, OSM groups, duplicates, operators, Top N and the search filters (`search=uic:8503000`, `search=route:<id>+dir:0`). Opening the link restores them, and **Copy link** in the summary panel copies the link with the current view. Before, only the operator filters and route variants were read from a link, and nothing was written back. See [A2.9](2.9%20Permalinks.md#map).
- **Problems page layout** — The entry's popup no longer opens under the filter toolbar or above the top of the map: the map frames the entry between the toolbar and the problem panel, and the popup pans into that space once it has its full height. The problem panel is shorter (at most 240 px of details instead of 300 px), its cards and notes are more compact, and it sits 8 px above the bottom of the map instead of 16 px. See [A2.4](2.4%20Problems%20Page.md#navigation).
- **Search filters keep whole identifiers** — A stop ID, OSM ID or UIC search filter kept every row whose identifier contained the text: `ch:1:sloid:10035:0:1` also kept `ch:1:sloid:10035:0:1955`, and 177 SLOIDs of the Swiss data begin another one. Identifiers now match whole, and a UIC number also matches an OSM `uic_ref` that lists it among `;`-separated values. See [A2.2](2.2%20Filters%20and%20Search%20logic.md#search-predicate).
- **Search by name, with suggestions** — The map's search box now takes stop names. From the second character, a list suggests stations of the official dataset and unmatched OSM elements by name or number, each with its UIC number, stop ID or OSM ID, its number of platforms or OSM state, and the OSM name it was found under. Names match without case, accents or punctuation, and a station is also found under the OSM names of its matched elements. Arrow keys and Enter, or a click, pick a suggestion; Enter on a name picks the first one, while identifiers such as `8503000` are searched as typed. A picked suggestion adds the same filter as its number, and search chips now name the stop, as in *Zürich HB · UIC: 8503000*. The new `/api/search/suggest` reads an index of the published snapshot that each web worker builds on its first request after an import. See [A2.2](2.2%20Filters%20and%20Search%20logic.md#names-and-suggestions).
- **Stop popups keep one width** — ATLAS, OSM and GTFS popups open 260 px wide instead of a width taken from their widest button row, which made OSM popups wider than ATLAS ones and grew 28 px each time the layout ran. Coordinates show at most 7 decimals. Manual resizing stops at 420 px. **See Matches** shows each matched pair as an ATLAS | OSM table of the fields both sources describe, at the same width, and highlights a UIC Ref, platform code or operator that differs. Fields only OSM has stay in the Tags panel. *Close Matches* moves to a bar at the top. Below the table, tabs open the ATLAS routes, the OSM routes or the tags, one at a time and coloured by source. A stop with several matches has a tab per match, named by OSM element type or ATLAS platform code, each with its own distance and match type. The popup no longer jumps sideways or flickers on the toggle, and a dragged popup stays where it was put. An OSM node matched to several ATLAS stops now shows its tags. Searches, links and **Random** that open a popup place the stop two thirds down the map, so the popup clears the top. See [A2.1](2.1%20Map%20Data%20Loading%20and%20Rendering.md#stop-popups).
- **One marker for a stop opened by search or a link** — A stop opened from the search box, a `?sloid=` or `?osm=` link or **Random** got a second marker, at its own coordinates, that looked like the map's marker but had no match line and stayed until another stop was opened. When the map spreads stops that nearly share a position, as it does for the two platforms of Zürich Selnau, 1 m apart, the two markers came apart at high zoom. The popup now opens on the map's own marker for the stop. A stop the filters leave out of the map still gets a marker of its own, until the map draws it. See [A2.1](2.1%20Map%20Data%20Loading%20and%20Rendering.md#stop-popups).
- **Popups keep their Move bar** — After a popup had been closed and opened again, clicking its marker removed the **Move** bar, so the popup could no longer be dragged.
- **A second click closes a popup** — Clicking the marker of an open popup now closes it, for every marker. Lettered markers already did; a circle kept the popup open and rebuilt it, which threw away an open **See Matches** view, tab or chosen match.
- **Popups survive zoom 18** — Markers change between circles and lettered markers at zoom 18, and an open popup on such a marker was rebuilt there: it went back above the marker, at the default width, on the stop's card. The popup now moves to the new marker as it is. See [A2.1](2.1%20Map%20Data%20Loading%20and%20Rendering.md#markers).
- **One source for the popup of an OSM element with several matches** — The map had its own way of building the popup of an OSM element matched to several ATLAS stops, from the stops it had loaded, meant for zoom 13 and above; switching between it and the server's popup closed an open popup. `/api/data` never sent the matches it needed, so it never ran. It is removed: `/api/stop_popup`, which lists every ATLAS match of the element, is the only source, so the popup cannot depend on the zoom or on which stops are loaded.
- **Match lines ignore the pointer** — Lines between matched stops showed a hand cursor although clicking them did nothing. A click on a line now reaches what is under it.

- **First start on a new database volume** — The `db` healthcheck has a 90-second `start_period`. Creating a new PostGIS volume runs initdb, installs PostGIS and restarts the server, which took longer than the two allowed checks, so `docker compose up` on a fresh clone stopped with `container stop_sync_osm_atlas_db is unhealthy`.
- **Unused API routes removed** — Five JSON routes with no caller in the application are gone. `/api/search` was a free-text search that the map never used: the search box looks stops up through `/api/stop_by_id`. `/api/route_stops` listed a route's stops, which the map filter and search compute on the server. `/api/docs/stats` returned statistics that the documentation pages render on the server instead. `/api/generate_report` was the deprecated synchronous export, replaced by `/api/generate_report_async`. `/api/download_stats_summary_pdf` lost its last link when the summary PDF moved to the async download. Their helpers, rate limits, tests and the "Search guardrails" section of [A3.2](3.2%20Security%20and%20Rate%20Limits.md) went with them. The public `/api/lookup` is unchanged.
- **Engine 0.1.0** — `engine.ref` pins the engine's first release, `v0.1.0`. It downloads public transport route relations only, which the OSM route figures on `/data/analytics` describe ([E1.3](../engine/documentation/1.3%20OSM%20data.md#which-route-relations-are-services)).
- **Page views apart from the JSON API** — The HTML pages moved to `backend/pages/`: the map, Problems, Data and error pages (`main.py`), the route tabs (`routes.py`) and the Operators page (`operators.py`). Their queries moved to `backend/services/route_listing.py` and `backend/services/operator_coverage.py`, and `backend/blueprints/` keeps the JSON endpoints. The page endpoints are now `pages.index`, `pages.problems`, `pages.data_analytics` and `pages.data_reports`, and the route JSON endpoints `routes_api.*`; URLs are unchanged. See [A2.6](2.6%20Routes%20Pages.md#shared-shell-and-routing).
- **Clearer analytics sections** — The sections after the pipeline on `/data/analytics` lose their nested cards and coloured tile borders: each topic is one block with uncoloured key figures, compact tables and label/value lists. Bars use ATLAS navy and OSM green, and only priorities use red, orange and grey. Percentages and distances have one decimal, and repeated headings are gone. The section menu now follows jumps such as the End key, the scrollbar or a reload part-way down the page. The statistics PDF uses the same layout, and its problem table now shows the counts per priority instead of zeros. Route contradictions get their own row, so the rows of each priority add up to its total. See [A2.7](2.7%20Colours%20and%20styles.md#analytics).
- **Analytics by source** — `/data/analytics` has the sections Stop matching, Unmatched, Route matching, Problems, ATLAS stops, Swiss GTFS, OSM stops and OSM routes, and every figure names its unit: OSM elements, stop units, lines or itineraries. OSM stops covers geometry (element types, nodes and ways, stop units), groups by type with their match state, and tag coverage for identifiers, operator and network, and amenities, per platform and stop position. Route matching shows the link count once, since lines and itineraries are linked one to one, then the coverage of each side by mode, why GTFS and OSM lines stay unlinked, and itinerary links within linked lines. Swiss GTFS splits stop ID resolution into platforms, stops and parent stations, and reports the stop IDs that trips use. ATLAS stops shows the filter steps from the download to the platforms and counts duplicates in SLOIDs. Unmatched OSM elements leave out two-sided stop middles, which count as matched. `backend/services/dataset_stats.py` computes the per-source sections from the published tables, so `scripts/regenerate_stats.py` refreshes them too. See [A1.2](1.2%20Stats%20and%20timestamps.md#the-sections-of-statsjson).
- **SQL NULL for absent JSON values** — `duplicate_group_sloids`, `duplicate_group_node_ids`, `osm_tags` and `details_json` store an absent value as SQL `NULL`, on both the COPY and the insert path, so `IS NOT NULL` selects exactly the rows with a value. See [A1](1.%20Database.md#stops-and-identities).
- **Simpler export form** — `/data/export` is one form that fits a desktop screen without scrolling. The three export types are cards on the left, and the chosen one shows its own options (sources, problem types, priorities), so switching type does not move the rest of the form. ATLAS operators and the output settings sit on the right, and the operator list opens over the form. The summary and the download button sit in a bar that stays in view, and the daily limit is a note beside the button instead of a banner. The page heading and the "Stats computed" time are gone: the Export tab already names the page, and the time belongs to `/data/analytics`.
- **Race-safe pipeline status** — Scheduler startup no longer resets an active manual run, and shared status fields are patched atomically for both file and Redis backends.
- **Heartbeat recovery** — A live pipeline lease can recover the web view from an unfinished legacy status record incorrectly marked idle.
- **Orphaned-run recovery** — Pipeline leases now record process/container ownership and heartbeat time. A scheduler watchdog marks killed runners failed and releases their stale locks at startup or within the configured heartbeat grace period, so restarting services cannot leave the UI claiming a nonexistent background run.
- **Detailed live pipeline timeline** — The Data page always shows the eight workflow phases, including before the first analytics snapshot exists. Engine events distinguish source preparation, stop and route matching, bundle creation, database staging and the actual atomic publication; reused or skipped work is explicit, elapsed bars resize every second, and truncated labels expose their full text on hover or keyboard focus.
- **Self-describing pipeline substages** — A versioned stage plan now combines engine-owned matching work with app-owned database/publication work. The analytics UI generically renders persistent colour-coded substage lists, preserves selection during polling, and accepts future engine stages without a frontend mapping change.
- **Complete stage timing records** — Reused and skipped stages now write timestamped, zero-duration history events, and compact UI timestamps explain whether they represent a stage start, reuse decision or skip decision. Legacy gaps remain unknown instead of being filled with fabricated times.
- **Engine pinned in the repository** — The committed `engine.ref` holds the engine commit the app is built and tested with. CI, `scripts/verify_engine_checkout.sh` and the documentation's engine source links read it, so upgrading the engine is a one-line commit. `ENGINE_REPO`, `ENGINE_REF` and `DOCS_ENGINE_BLOB_BASE` in `.env`, and the CI variable and token, are no longer used; remove them.

### Code quality

- **One module at a time on the functions map** — Clicking a module in the list beside the functions map now draws only that module's functions, laid out on their own and fitted to the map, instead of fading the other 2,000 dots. A module opens in about 0.1 to 0.4 seconds, against about 1.4 seconds for every function. **All functions** in the breadcrumb, **Reset** or <kbd>Esc</kbd> brings every function back, and a search match in another module switches to that module. Zooming is also smoother: names are placed again once a zoom rests instead of on every frame, which took zooming from about 16 to 60 frames a second. The legend under the map is one short line instead of three. See [A4.3](4.3%20Code%20Quality.md#read-the-dashboard).
- **Circles for modules and files, with room to zoom** — On the functions map each module is now a light circle with its name on top, and a module drawn alone has a circle for each file, so its structure reads at a glance. Dots no longer touch: each keeps clear of its neighbours by more than half its width, so zooming in opens space where the lines and more names show; before, zooming in only made touching dots larger. Double-clicking a module's circle draws it alone, and double-clicking a file's circle opens its functions.
- **Details button for the dashboard panel** — The icon-only info button that hid the side panel is now labelled **Details**. While the panel is open, the button is tinted blue. The panel drops in below the button when it opens, and the guide ("How to read the map") has a × that hides it, after which the button rings once. See [A4.3](4.3%20Code%20Quality.md#read-the-dashboard).
- **Dashboard easier to find** — The documentation sidebar ends with a **Code quality dashboard** link above the PDF download, and the header of [A4.3](4.3%20Code%20Quality.md) has **Open the dashboard** beside **Download PDF**. Before, the only way in was a link in the text of A4.3.
- **Code quality dashboard** — `/quality` draws the module map of both repositories: how the modules' code depends on each other, which dependencies the module catalog does not declare, which modules depend on each other both ways and which private names cross a module border. Opening a module shows its files, with the modules that use it on one side and the modules it uses on the other. The evidence table and required checks follow. `make deploy-report` now also publishes the code map the dashboard draws. See [A4.3](4.3%20Code%20Quality.md#read-the-dashboard).
- **HTTP and template links on the code map** — The map now links browser requests and `url_for` references to the Flask routes they reach, and views and templates to the templates they render, extend or include. Browser scripts are parsed with espree instead of regular expressions, so a name in a comment or string is no longer a reference and members of shared namespaces such as `MapComponents` link to the script defining them. A new **What the map cannot see** section lists references that reach nothing, routes nothing reaches, URLs built at runtime and browser names declared by several scripts. See [A4.3](4.3%20Code%20Quality.md#read-the-dashboard).
- **Function view and calmer map** — Double-clicking a file on the code quality map opens its functions, with what uses them on the left and what they use on the right; selecting one lists its callers and callees. Hovering now only marks a box and its own arrows, with a tooltip beside it after a short rest; a click focuses and fades the rest until <kbd>Esc</kbd>. A full screen button joins the zoom controls. See [A4.3](4.3%20Code%20Quality.md#read-the-dashboard).
- **Calls between files in the code map** — The map resolves Python calls through imports and re-exports, and counts a browser script's top-level names used by other scripts. Importing a submodule no longer counts as importing its package's `__init__.py`.
- **Browser script calls on the functions map** — A browser script's calls and references to its own functions and classes are now links, and a name a script reads from another is read by the function around it rather than by the file. The review interface, mostly JavaScript, had lines on 72 of its 845 functions and now has them on 750. Module and file arrows are unchanged.
- **Every module dependency declared** — The code map has no undeclared dependency and no two modules depending on each other. Leaf code moved to the bottom layer: `version.py`, `state_backend_config.py` and the new `site_url.py` belong to Queries, APIs and exports, as do the PDF report templates with their `printable.html` layout (now in `templates/reports/`). `seo.py` and `scripts/regenerate_stats.py` belong to Schema, deployment and quality gates, `system.py` to Pipeline orchestration, and `jquery-lite.js` and `page-tabs.js` (now in `static/js/shared/`) to the design system. The code changed where a module reached into one above it: the routes API's maintenance guard is registered by the application factory, `seo.py` and `docs.py` no longer import each other, the importer lost its unused `run_type` parameter and the pipeline stamps the progress schema version on the importer's stage events, `pipeline-status.js` uses `fetch` instead of jQuery, and the engine reads its version from a leaf module (`engine.ref` pins that commit). The catalog now declares that the design system's base layout loads the pipeline status, and that the documentation pages use the base layout and the report export overlay.
- **Functions map** — The code quality map has three levels: **Modules**, **Files** and **Functions**. **Functions** draws every function and class of both repositories in one map, coloured by module so each module forms its own region, sized by how many functions and files use it. A column beside it searches functions, classes and files, switches lines and names on and off, and lists the modules: clicking one picks out its functions. Selecting a dot shows its callers and callees; double-clicking opens its file. See [A4.3](4.3%20Code%20Quality.md#read-the-dashboard).
- **Expanded map below the navbar** — **Expand**, now at the right end of the map's toolbar, fills the window below the navbar instead of switching the browser to full screen, so the navbar and the browser stay usable. Expanded, it becomes a blue **Exit** in the window's top-right corner; it or <kbd>Esc</kbd> returns. An info button beside it hides the side panel to give the map the whole width, and a selection opens it again. The map zooms in up to 10×, so every name on the functions map can be read.
