# A2.8 Documentation Page Delivery

This page describes how the documentation section is served inside the web application, from markdown discovery to rendered HTML and PDF export.

## Route Entry Point

The documentation experience is owned by docs.py. It registers the `/docs` routes and assembles two canonical source trees into one portal:

| Source tree | Owns |
|---|---|
| Engine build context projected at `engine/documentation/` | Curated input integrations, acquisition, matching, route comparison, problem detection and engine performance |
| `documentation/` | Bundle import, database, API/UI, deployment and cross-project guidance |

The engine produces versioned result bundles. The review application consumes those bundles and owns their persistence and presentation. The source trees make that boundary reviewable now and can move into separate repositories without reorganizing the documentation again.

Reader-facing section numbers are scoped by owner: `E1`–`E6` identify matching-engine documentation and `A1`–`A4` identify review-application documentation. Each source tree is numbered independently in logical reading order so the two repositories can evolve without renumbering each other. Changelogs, related projects and contribution guidance remain unnumbered. Public page slugs omit the number, so reorganizing the source filenames does not change their URLs.

The route flow is:

1. Discover top-level Markdown pages in both source trees.
2. Build one deterministic `document ID -> slug` map. Unique filenames retain their concise slug; duplicate filenames receive an owner-qualified slug, such as `/docs/changelog` and `/docs/engine_changelog`.
3. Arrange pages into Project overview, Engine input integrations, Matching engine core, and Review application & deployment collections. The two engine collections share Engine ownership but keep dataset integrations visibly outside the source-neutral core.
4. Resolve the active page from its canonical slug. Unknown or legacy filename-style paths return 404.
5. Convert the Markdown to sanitized HTML using the active page's source directory for links and assets.
6. Render docs.html for full page loads or return JSON when the docs UI fetches partial content.

## Template and Client Navigation

docs.html is the shell for the documentation UI. It provides:

- The left sidebar with section grouping and active-page state.
- Collection labels that distinguish engine input integrations from the matching core, plus ownership badges that distinguish shared, engine and application pages.
- A compact `Shared`, `Engine` or `App` ownership pill beside each article title. The detailed boundary is explained once in the introduction instead of repeated on every page.
- The main article container where rendered HTML is injected.
- Previous and next navigation controls.
- The PDF export modal.
- Client-side progressive navigation that fetches only the updated article content when users move between pages.

The inline script in docs.html keeps sidebar expansion state in `localStorage`, intercepts internal `/docs/...` links, requests partial payloads with `X-Docs-Partial: 1`, swaps the article HTML, and then re-runs Mermaid and MathJax rendering.

## Markdown Enrichment Pipeline

The markdown conversion logic also lives in docs.py. Before Mistune renders the markdown, the content is enriched in several passes:

1. Plain-text code file mentions such as docs.py, repo_scanner.py, or scripts under `engine/src/transport_matcher/core/` are resolved to repository-relative paths and turned into GitHub blob links.
2. Mermaid code fences are processed separately so node labels stay valid Mermaid syntax while matching nodes receive `click` commands that open the corresponding GitHub file.
3. Relative links to a served Markdown page in either source tree are rewritten to canonical `/docs/<slug>` routes. Links to non-served repository notes remain GitHub links.
4. GitHub-style alerts are converted to styled HTML blocks.
5. Special placeholders are expanded. For example, the color palette in Section 6.7 is injected from the backend into the web documentation renderer.
6. Relative assets are served from the page owner's documentation directory.
7. The final HTML is sanitized with Bleach before it is sent to the browser.

The Mermaid-specific isolation is important because Mermaid has its own DSL. The general text-linking pass must not inject standard markdown links inside node labels.

## Repository File Resolution

repo_scanner.py performs a lazy, one-time scan when documentation auto-linking first needs it and builds a filename-to-path index for code files. The scanner ignores documentation trees, `data/`, vendored assets, virtual environments, build output and generated caches. It scans application code under `backend/`, `static/` and `templates/`, plus engine code under `engine/src/`.

This index supports two documentation features:

- Linking plain text mentions like `backend/app.py` or `get_atlas_data.py` directly to GitHub.
- Resolving Mermaid node labels such as `SG[get_atlas_gtfs.py]` into `click SG "..."` commands without forcing documentation authors to hardcode repository paths.

When a filename is ambiguous, the service only links it if the path can be resolved uniquely.

## Dynamic Stats Placeholders

docs_stats.py provides the stats placeholder helpers used by the documentation renderer and the PDF builder.

It supports placeholders of the form `{{stat:summary.match_rate_percent}}`, loads `data/stats.json`, formats values for human-readable output, and can inject either HTML-wrapped spans or plain text depending on the rendering target.

That split matters because:

- The web UI wants `<span>` wrappers for styling and future dynamic behavior.
- Mermaid fences need raw text values so the diagram syntax stays valid.
- Static PDF generation needs explicit HTML escaping.

The same helper module also converts GitHub alert syntax into reusable HTML fragments and exposes the canonical palette block used in the visual design documentation.

## Partial Rendering Contract

The documentation page supports both full-page and partial-page responses from the same route.

- A normal request returns the full layout through docs.html.
- A request with `X-Docs-Partial: 1` returns a JSON payload containing the rendered article HTML, ownership context, active slug, active section, and previous or next navigation metadata.

This keeps the docs section feeling responsive without introducing a separate frontend framework.

## PDF Export Integration

The documentation routes also expose async PDF generation endpoints. The modal in docs.html posts export parameters to `/api/docs/generate_pdf_async`, polls task progress, and downloads the generated file when the background export finishes.

The exported PDF reads both canonical source trees in the same overview → engine inputs → engine core → application order used by the site. Section identifiers include their owner (for example, `engine:2`, `app:2`, `engine:extra-changelog` or `app:extra-changelog`), preventing equal section numbers and duplicate filenames from colliding. PDF anchors resolve relative to the current source page, so cross-links between the two changelogs remain unambiguous. The exporter uses the same enrichment helpers as the web page, which keeps the on-site documentation and downloadable document aligned.
