# A2.8 Documentation portal

The `/docs` section of the web app presents the Markdown of both projects as one manual and exports it as one PDF. This page explains where the pages come from, how they are numbered and named, how Markdown becomes safe HTML, how links to pages and source files are resolved, and how the PDF stays in step with the portal.

## Where the pages come from

Each project keeps its Markdown next to the code it describes. `docs.py` reads both trees:

| Tree | Location | Covers |
|---|---|---|
| Application | `documentation/` in this repository | Bundle import, database, API and UI, deployment, cross-project guidance |
| Engine | `documentation/` in the engine checkout, presented as `engine/documentation/` | Input integrations, acquisition, matching, route comparison, problem detection, engine performance |

The engine checkout is the first of `ENGINE_DIR`, `engine/` inside the application, or a sibling `../engine` that contains a `pyproject.toml`. The web image contains no engine code: its build copies only the engine's `documentation/` and `pyproject.toml` (for the version shown in the sidebar) to `engine/`.

## Numbers, titles and addresses

Section numbers belong to the project that owns the page, so each repository can renumber its pages without touching the other:

| Prefix | Pages |
|---|---|
| `0.` | Project overview: introduction and glossary |
| `E1`–`E6` | Matching engine |
| `A1`–`A4` | Review application |
| none | Changelogs and contributing guides |

The sidebar arranges the pages in four collections: **Project overview** (application section 0), **Engine input integrations** (engine section 1), **Matching engine core** (the other engine sections) and **Review application & deployment** (the other application sections). Unnumbered pages close the collection of their owner.

| Item | Taken from |
|---|---|
| Section titles (`E2`, `A3`, …) | A curated label in `docs.py`, so the sidebar stays short |
| Other page titles | The page's `#` heading; the number is shown separately |
| Address | The file name without its number: `2.1 Exact matching.md` is `/docs/exact_matching`. When both trees have a page of the same name, the application page keeps the short address and the engine page gets a prefix: `/docs/changelog` and `/docs/engine_changelog` |
| Section anchors | The heading text, lower-cased and hyphenated as on GitHub: `## Top N distances` is `#top-n-distances`; a repeated heading gets `-1`, `-2`, … |

Unknown addresses and old file-name addresses return 404, so renaming a file changes its address: update the links that point to it.

## From Markdown to HTML

`docs.py` prepares each page in this order before Mistune renders it:

1. **Code mentions become links.** Inline code that is exactly a file path, such as `backend/app.py` or `backend/app.py::create_app`, and bare file names in prose link to the file. A Mermaid node named after a file gets a `click` command instead, so the diagram source stays valid.
2. **Code blocks are set aside**, so the passes below never change an example.
3. **Links to pages** in either tree become `/docs/<address>` routes and keep their `#anchor`.
4. **Other relative links** point to source files: application files become GitHub links; engine files are handled as described under [Links to source code](#links-to-source-code).
5. **Alerts** written as `> [!NOTE]`, `> [!IMPORTANT]` and so on become styled blocks.
6. **Placeholders** are filled in prose, never inside code: dataset statistics (`{{stat:summary.match_rate_percent}}`), the code-quality report (`{{CODE_QUALITY_REPORT}}`) and the colour palette (`[[canonical_palette]]`, used in [A2.7](2.7%20Colours%20and%20styles.md)).
7. **Images** with a relative path such as `images/route-model.svg` are served from the owner's tree at `/docs/assets/<owner>/images/…`.

After rendering, Bleach removes every tag and attribute outside an allowlist and turns URLs written with `http://` or `https://` into links, except inside code; then kit diagrams are inlined (see [Diagrams](#diagrams)) and headings receive their anchors. Only written-out URLs become links: a file name is never mistaken for a web address, although `.py` and `.name` are top-level domains.

## Links to source code

`repo_scanner.py` indexes the code files of the application checkout the first time a page needs it: Python, SQL, shell, configuration, JavaScript, TypeScript, CSS and HTML files. It skips hidden directories and every directory named `node_modules`, `venv`, `__pycache__`, `data`, `vendor`, `build`, `dist`, `coverage`, `htmlcov` or `generated`. An engine checkout inside the application at `engine/` is indexed too. A file name links only when it identifies one file; when two files share a name, write enough of the path to tell them apart, such as `backend/blueprints/docs.py`.

Application files link below `DOCS_GITHUB_BLOB_BASE`, by default `https://github.com/openTdataCH/stop_sync_osm_atlas/blob/main/`. Engine files link to the public engine repository at the commit pinned in `engine.ref`, so the links show the code that produced the published data.

## Statistics and quality placeholders

`docs_stats.py` fills the statistics placeholders from `data/stats.json` ([A1.2](1.2%20Stats%20and%20timestamps.md)). Numbers get thousands separators, and keys ending in `_percent` get their `%` sign, so do not type one after the placeholder. The portal wraps each value in a `<span>` for styling, a Mermaid block receives the raw value so its syntax stays valid, and the PDF receives escaped text.

The [Code quality page](4.3%20Code%20Quality.md) uses the code-quality placeholder. `backend/services/quality_report.py` fills it from the committed report in `quality/published/latest.json`, separately from `data/stats.json`: dataset results and code verification answer different questions.

The report shows both repository revisions, generation time, tool versions, required check results and separate module lanes for tests, branch coverage, mutation, structural debt, documentation and architecture. It links to the CI run holding the raw evidence instead of reducing those signals to one score. Catalog metadata is maintained by hand; measurements, maps and rendered reports are generated by the quality commands described in [A4.4](4.4%20Running%20Quality%20Checks.md).

`make deploy-report` writes the published report before a deployment ([A4.3](4.3%20Code%20Quality.md#how-the-report-reaches-the-site)). Alongside it, `publication.json` records a hash of the shipped code at the measured commit. The renderer hashes the same files on disk without Git, because the image has no `.git`, and compares the report's engine revision with `engine.ref`. If either differs, the report opens with a warning alert and every result is marked stale. The renderer inserts the report before alert conversion so that warning renders as an alert. Missing or malformed evidence displays an explicit unavailable message.

The same published evidence feeds the code quality dashboard at `/quality` (`backend/blueprints/quality.py`, `templates/pages/quality.html`, `static/js/quality/dashboard.js`). `load_published` in `quality_report.py` reads `latest.json`, `publication.json` and `code-map.json` and applies the same stale check, so the page and the dashboard always agree. `/api/quality` returns that evidence as JSON, or `{"available": false}` when it is missing or malformed. The dashboard draws the code map with the vendored Cytoscape.js ([A3.4](3.4%20Frontend%20Asset%20Management.md)); [A4.3](4.3%20Code%20Quality.md#read-the-dashboard) explains how to read it.

The renderer never runs tests or regenerates measurements while serving a page.

## Diagrams

| Kind | In the portal | In the PDF |
|---|---|---|
| Mermaid block | Rendered in the browser by the vendored Mermaid | Pre-rendered to SVG with `npm run docs:render-mermaid`; the build fails if one is missing |
| Kit diagram (`images/*.svg`) | Inlined into the page, so links in it work | The same file, embedded as a static image |
| Other SVG or bitmap image | A static image | The same file, embedded |

Kit diagrams are generated from `documentation/diagrams/catalog.py`; `npm run docs:diagrams` regenerates them.

A browser draws an SVG loaded through `<img>` as a static picture and ignores its links. The portal therefore replaces the `<img>` of a kit diagram with the file's markup, after Bleach, because Bleach would strip the SVG. A diagram is inlined only when it lies below an owner's `images/` directory and carries the kit's "Generated by documentation/diagrams/build.py" comment. The kit writes no styles or scripts and prefixes its element IDs with the diagram name, so several diagrams can share a page. Other SVGs, such as hand-drawn illustrations with their own stylesheet, stay images, so their CSS cannot affect the page. GitHub and the PDF always show kit diagrams as images, where their links cannot be clicked.

## Full pages and partial updates

`docs.html` is the shell of the portal: the sidebar, the page header, the article, "On this page", previous and next links, and the PDF export dialog.

| Part | Shows |
|---|---|
| Sidebar | A filter box (`/` focuses it, Escape clears it), then the collections. Each collection heading is in small capitals with its project's version; each page shows its number in grey before its title, and long titles wrap. Only the page being read is highlighted; the section that holds it is in bold. At the bottom, a link opens the PDF export for the whole documentation. |
| Page header | The collection and the page number (`Matching engine core · E.2.1`), the page's `#` heading without its number, and a link that opens the PDF export for this page. `docs.py` takes the heading out of the rendered article for it. |
| On this page | The article's `##` and `###` headings, when there are at least two. On screens 1400 pixels wide or more it is a column beside the article that marks the section being read; on narrower screens it is a collapsed list above the article. |

Colour says which project owns a page, faintly: a dot before each collection heading and the page header's collection, and the tint of the highlighted page. The engine is green, the review application navy and the shared overview purple, as in the system diagrams. The text always names the collection as well, so colour is never the only signal.

Moving between pages does not reload the shell. `static/js/docs/portal.js` intercepts internal `/docs/...` links and requests the page with the header `X-Docs-Partial: 1`. The route then returns JSON with the rendered article, the page header, the address and section, and the previous and next pages; the script swaps the article and the header, rebuilds "On this page" and runs Mermaid and MathJax again. A normal request to the same route returns the full page. The sidebar remembers which sections are expanded in `localStorage`; filtering does not change what it remembers.

## PDF export

The export dialog offers this page, the whole documentation or chosen sections; the link that opens it picks the first choice, and chosen sections start from the section being read. It starts a background task at `/api/docs/generate_pdf_async` and downloads the file when it is ready ([A2.5](2.5%20Generate%20Reports%20and%20PDFs.md#documentation-pdf)). `build_docs_pdf.py` reads both trees in the order of the sidebar and applies the same link, placeholder and alert helpers as the portal, adapted to one document:

| Portal | PDF |
|---|---|
| `/docs/<address>` | An anchor built from the owner and the file name, such as `#doc-engine-2-1-exact-matching` |
| `/docs/<address>#<section>` | The page anchor followed by `--<section>`, such as `#doc-engine-2-1-exact-matching--platform-codes` |
Sections are selected by owner-qualified identifiers such as `engine:2`, `app:2` and `engine:extra-changelog`, so equal numbers and file names in the two trees never collide. A single page is selected by its address and downloads under it, such as `exact_matching.pdf`. The complete PDF is cached and rebuilt when any page, image, statistic, quality artifact, print style or renderer changes. An exported PDF records the evidence of its generation time; use the live page or export again for a current check.
