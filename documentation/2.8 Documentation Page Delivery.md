# A2.8 Documentation portal

The `/docs` section of the web app presents the Markdown of both projects as one manual and exports it as one PDF. This page explains where the pages come from, how they are numbered and named, how Markdown becomes safe HTML, how links to pages and source files are resolved, and how the PDF stays in step with the portal. To write or illustrate a page, see the [documentation style guide](Documentation%20style%20guide.md).

## Where the pages come from

Each project keeps its Markdown next to the code it describes. `docs.py` reads both trees:

| Tree | Location | Covers |
|---|---|---|
| Application | `documentation/` in this repository | Bundle import, database, API and UI, deployment, cross-project guidance |
| Engine | `documentation/` in the engine checkout, presented as `engine/documentation/` | Input integrations, acquisition, matching, route comparison, problem detection, engine performance |

The engine checkout is the first of `ENGINE_DIR`, `engine/` inside the application, or a sibling `../engine` that contains a `pyproject.toml`. The web image contains no engine code: its build copies only the engine's `documentation/` and `pyproject.toml` (for the version shown in the sidebar) to `engine/`.

## Numbers, titles and addresses

Section numbers belong to the project that owns the page, so each repository can renumber its pages without touching the other:

| Prefix | Pages |
|---|---|
| `0.` | Project overview: introduction and glossary |
| `E1`–`E6` | Matching engine |
| `A1`–`A4` | Review application |
| none | Changelogs, contributing guides, related projects, this style guide |

The sidebar arranges the pages in four collections: **Project overview** (application section 0), **Engine input integrations** (engine section 1), **Matching engine core** (the other engine sections) and **Review application & deployment** (the other application sections). Unnumbered pages close the collection of their owner.

| Item | Taken from |
|---|---|
| Section titles (`E2`, `A3`, …) | A curated label in `docs.py`, so the sidebar stays short |
| Other page titles | The page's `#` heading; the number is shown separately |
| Address | The file name without its number: `2.1 Exact matching.md` is `/docs/exact_matching`. When both trees have a page of the same name, the application page keeps the short address and the engine page gets a prefix: `/docs/changelog` and `/docs/engine_changelog` |
| Section anchors | The heading text, lower-cased and hyphenated as on GitHub: `## Top N distances` is `#top-n-distances`; a repeated heading gets `-1`, `-2`, … |

Unknown addresses and old file-name addresses return 404, so renaming a file changes its address: update the links that point to it.

## From Markdown to HTML

`docs.py` prepares each page in this order before Mistune renders it:

1. **Code mentions become links.** Inline code that is exactly a file path, such as `backend/app.py` or `backend/app.py::create_app`, and bare file names in prose link to the file. A Mermaid node named after a file gets a `click` command instead, so the diagram source stays valid.
2. **Code blocks are set aside**, so the passes below never change an example.
3. **Links to pages** in either tree become `/docs/<address>` routes and keep their `#anchor`.
4. **Other relative links** point to source files: application files become GitHub links; engine files are handled as described under [Links to source code](#links-to-source-code).
5. **Alerts** written as `> [!NOTE]`, `> [!IMPORTANT]` and so on become styled blocks.
6. **Placeholders** are filled in prose, never inside code: dataset statistics (`{{stat:summary.match_rate_percent}}`), the code-quality report (`{{CODE_QUALITY_REPORT}}`) and the colour palette (`[[canonical_palette]]`, used in [A2.7](2.7%20Colours%20and%20styles.md)).
7. **Images** with a relative path such as `images/route-model.svg` are served from the owner's tree at `/docs/assets/<owner>/images/…`.

After rendering, Bleach removes every tag and attribute outside an allowlist and turns URLs written with `http://` or `https://` into links, except inside code; then headings receive their anchors. Only written-out URLs become links: a file name is never mistaken for a web address, although `.py` and `.name` are top-level domains.

## Links to source code

`repo_scanner.py` indexes the code files of the application checkout the first time a page needs it: Python, SQL, shell, configuration, JavaScript, TypeScript, CSS and HTML files. It skips hidden directories and every directory named `node_modules`, `venv`, `__pycache__`, `data`, `vendor`, `build`, `dist`, `coverage`, `htmlcov` or `generated`. An engine checkout inside the application at `engine/` is indexed too. A file name links only when it identifies one file; when two files share a name, write enough of the path to tell them apart, such as `backend/blueprints/docs.py`.

The engine is a separate, possibly private, repository, so its files are linked only through a configured base URL:

| Setting | Default | Effect |
|---|---|---|
| `DOCS_GITHUB_BLOB_BASE` | `https://github.com/openTdataCH/stop_sync_osm_atlas/blob/main/` | Base URL of application source links |
| `DOCS_ENGINE_BLOB_BASE` | unset | Base URL of engine source links. Unset, links to engine files show their label as plain text instead of a URL that would return 404 |

Pin `DOCS_ENGINE_BLOB_BASE` to the reviewed engine commit, for example `https://github.com/<owner>/<engine>/blob/<commit>/`, so the links show the code that produced the published data. Compose passes it to the web service.

## Statistics and quality placeholders

`docs_stats.py` fills the statistics placeholders from `data/stats.json` ([A1.2](1.2%20Stats%20and%20timestamps.md)). Numbers get thousands separators, and keys ending in `_percent` get their `%` sign, so do not type one after the placeholder. The portal wraps each value in a `<span>` for styling, a Mermaid block receives the raw value so its syntax stays valid, and the PDF receives escaped text.

The [Code quality page](4.3%20Code%20Quality.md) uses the code-quality placeholder. `backend/services/quality_report.py` fills it from `quality/latest.json`, separately from `data/stats.json`: dataset results and code verification answer different questions.

The report shows both repository revisions, generation time, tool versions, required check results and separate module lanes for tests, branch coverage, mutation, structural debt, documentation and architecture. It links to raw evidence instead of reducing those signals to one score. Catalog metadata is maintained by hand; measurements, maps and rendered reports are generated by the quality commands described in the [quality guide](../quality/README.md).

Evidence older than seven days or collected for different checkout inputs is marked stale. Missing or malformed evidence displays an explicit unavailable message. If a deployment omits Git metadata or the engine checkout, the page says that those inputs cannot be verified; the recorded revisions remain visible. A source edit during a test run invalidates that run's fingerprints even when individual assertions passed.

`/docs/quality-artifacts/<path>` serves an allowlist of generated files: `latest.json`, `quality-map.json`, `report.md` and JSON, XML and TXT files under `raw/`. It rejects hidden paths, traversal and manual configuration such as the module catalog. CI uploads generated evidence; a deployment must copy the selected run's `quality/` outputs explicitly to expose them through the portal, so a plain source checkout or image shows "unavailable" until evidence is provided. A PDF has no application origin to resolve portal links, so it lists raw artifact paths relative to the accompanying `quality/` directory as plain text; the web report keeps downloadable links.

The renderer never runs tests or regenerates measurements while serving a page. Refresh evidence with `make quality`, then publish the report and its raw files from the same run together.

## Diagrams

| Kind | In the portal | In the PDF |
|---|---|---|
| Mermaid block | Rendered in the browser by the vendored Mermaid | Pre-rendered to SVG with `npm run docs:render-mermaid`; the build fails if one is missing |
| Kit diagram (`images/*.svg`) | A static image | The same file, embedded |

Kit diagrams are generated from `documentation/diagrams/catalog.py`; the [style guide](Documentation%20style%20guide.md#illustrate-with-the-diagram-kit-or-mermaid) explains when to use which and how to regenerate them.

## Full pages and partial updates

`docs.html` is the shell of the portal: the sidebar with collections, ownership badges and the active page; an `App`, `Engine` or `Shared` pill beside the article title; previous and next links; and the PDF export dialog.

Moving between pages does not reload the shell. The inline script intercepts internal `/docs/...` links and requests the page with the header `X-Docs-Partial: 1`. The route then returns JSON with the rendered article, its ownership, address and section, and the previous and next pages; the script swaps the article and runs Mermaid and MathJax again. A normal request to the same route returns the full page. The sidebar remembers which sections are expanded in `localStorage`.

## PDF export

The export dialog starts a background task at `/api/docs/generate_pdf_async` and downloads the file when it is ready ([A2.5](2.5%20Generate%20Reports%20and%20PDFs.md#documentation-pdf)). `build_docs_pdf.py` reads both trees in the order of the sidebar and applies the same link, placeholder and alert helpers as the portal, adapted to one document:

| Portal | PDF |
|---|---|
| `/docs/<address>` | An anchor built from the owner and the file name, such as `#doc-engine-2-1-exact-matching` |
| `/docs/<address>#<section>` | The page anchor followed by `--<section>`, such as `#doc-engine-2-1-exact-matching--platform-codes` |
| Engine source link | Plain text, unless `DOCS_ENGINE_BLOB_BASE` is set |

Sections are selected by owner-qualified identifiers such as `engine:2`, `app:2` and `engine:extra-changelog`, so equal numbers and file names in the two trees never collide. The complete PDF is cached and rebuilt when any page, image, statistic, quality artifact, print style or renderer changes. An exported PDF records the evidence of its generation time; use the live page or export again for a current check.
