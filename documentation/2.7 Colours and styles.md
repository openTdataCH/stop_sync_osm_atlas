# A2.7 Colours

## Purpose

This chapter defines the color system used by the web app and map rendering logic.
It standardizes previous mixed blue/green/red/gray hardcoded values into semantic tokens.

## Canonical Palette

[[canonical_palette]]

The core ATLAS–OSM palette is centralized in CSS tokens and JavaScript constants. Authored CSS should use semantic tokens wherever possible; new hues must be added to the token source and documented here before use.

## Semantic Mapping

### Map markers

- Matched ATLAS marker: navy `#174092`
- Matched OSM marker: green `#4CAF50`
- Matched GTFS stop_id marker (GTFS stop_id ↔ SLOID view): orange `#F0AD4E`
- Unmatched ATLAS marker: red `#DC3545`
- Unmatched OSM marker: gray `#6C757D`

### Map lines

- ATLAS-OSM connection lines: navy `#174092` (solid)
- OSM group partner lines: green `#4CAF50` (dashed `6,4`)
- OSM trio lines: green `#4CAF50` (dashed `6,4`)

### Information Banners

Used for global stats summaries and problem identification details.

- Background: Primary subtle `#eef3fb`
- Border: Primary muted (alpha variant of `#174092`)
- Text: Primary navy `#174092`

### Priority System

Standardized across Analytics reports and Problem identification chips.

- **P1**: Red `#DC3545` (Danger/Critical)
- **P2**: Orange `#F0AD4E` (Warning/Significant)
- **P3**: Gray `#6C757D` (Secondary/Minor)

## Style Policy

### Semantic colors

- Prefer semantic CSS variables over raw color literals.
- Do not introduce a second gray, blue, green, warning, or danger palette for an individual page.
- A genuinely new visual meaning may receive a narrowly named token. A one-off shade should normally be mapped to an existing background, foreground, border, or status token.
- New token hues must be described in this chapter. The Stylelint configuration does not maintain a separate hidden color allowlist.

### Alpha, shadows, and overlays

Opacity does not create a new palette color. For example, `#174092` and `rgba(23, 64, 146, 0.2)` share the same documented navy base and are both recognized by the lint policy.

Prefer the standard `--shadow-*` tokens for ordinary elevation. Component-specific shadows and overlays may use alpha variants of black, white, or another documented base color; their individual opacity values do not need separate palette entries.

### Borders

Do not use a colored left border or left accent border. Use a neutral full border, a semantic full border, spacing, or background color to communicate grouping and status. Transparent left borders used only for CSS geometry, such as a tooltip arrow, are allowed.

### Gradients

Gradients are not approved merely because their colors belong to the palette. They should be reserved for a clear visual purpose and reviewed separately from color-token compliance. Flat semantic surfaces are the default.

## Enforcement

Stylelint checks authored CSS with:

```bash
npm run lint:css
```

The policy:

- rejects color bases not defined by `static/css/src/01-settings/tokens.css`;
- treats equivalent hex, named, RGB, and alpha variants as the same base color;
- rejects colored or accented left borders while permitting transparent geometry;
- rejects Bootstrap `border-start` utility classes in templates;
- checks empty blocks, duplicate declarations, and unknown CSS properties;
- excludes the import-only `static/css/main.css` entrypoint and vendor assets.

## GTFS Color

Matched GTFS stops use warning orange `#F0AD4E`, exposed as `--color-map-gtfs-matched` in CSS and `AppConstants.COLORS.GTFS_MATCHED` in JavaScript. Unmatched GTFS stops reuse the standard unmatched gray through `AppConstants.COLORS.GTFS_UNMATCHED`.
