# A2.7 Colours and styles

Every colour in the web app, the maps and the documentation diagrams comes from one small palette. Each colour has a fixed meaning: navy is ATLAS, green is OSM, orange is GTFS, red is an unmatched ATLAS stop. This page lists the palette, what each colour means, where the tokens are defined and how the rules are enforced.

## Canonical palette

[[canonical_palette]]

The palette is defined once as CSS tokens and once as JavaScript constants. Authored CSS uses the semantic tokens. A new hue is added to the token source and documented here before it is used.

## What the colours mean

### Map markers

| Marker | Colour |
|---|---|
| Matched ATLAS | Navy `#174092` |
| Matched OSM | Green `#4CAF50` |
| Matched GTFS `stop_id` (GTFS `stop_id` ↔ SLOID map) | Orange `#F0AD4E` |
| Unmatched ATLAS | Red `#DC3545` |
| Unmatched OSM | Grey `#6C757D` |
| Unmatched GTFS `stop_id` | Grey `#6C757D` |

### Map lines

| Line | Colour and style |
|---|---|
| ATLAS–OSM match | Navy `#174092`, solid |
| OSM pair partners | Green `#4CAF50`, dashed `6,4` |
| OSM trio members | Green `#4CAF50`, dashed `6,4` |

### Route family cards

Route family cards reuse the marker palette with a full semantic border and a flat, subtle background: matched ATLAS is navy, matched OSM is green, unmatched ATLAS is red, and unmatched OSM is grey. Their colours reflect saved family matches; exploring a candidate inside an unmatched variant does not change the family card's status.

Stop links in variant comparisons use the navy of the ATLAS–OSM match line.

### Operator tag breakdowns

The Operators page shows how the matched OSM stops of each ATLAS operator are tagged, as a stacked bar with one labelled row per value. The roles reuse existing tokens and differ by lightness, so they stay distinguishable with colour-vision deficiencies:

| Role | Colour |
|---|---|
| Most common value | Success foreground `#1F5E22` (`--color-success-fg`) |
| Values in between | Even steps between the two greens |
| Least common value | OSM green `#4CAF50` (`--color-success`) |
| Not tagged | Emphasis border grey `#CED4DA` (`--color-border-emphasis`) |

One value is dark green; two values are the dark green and the OSM green; each further value adds an intermediate step, so four values get four greens. The steps are mixed from the two tokens with `color-mix()` in OKLab, which keeps the lightness steps even and adds no new palette colour.

The status pill reuses the status tokens: success for a single consistent value; warning for several values, partial tagging or no tag; muted grey when no stop is matched. Each pill also carries an icon and a label, so colour is never the only signal.

### Information banners

Banners carry the global statistics summary and the problem details.

| Part | Colour |

| Border | Primary muted, an alpha variant of `#174092` |

### Priorities

The same three colours mark priorities in reports and on the Problems page:

| Priority | Colour |
|---|---|
| **P1** | Red `#DC3545` (danger, critical) |
| **P2** | Orange `#F0AD4E` (warning, significant) |

### Documentation diagrams

The SVG diagrams in this documentation use the same tokens. Domain diagrams use the map colours (ATLAS navy, OSM green, GTFS orange, unmatched red); system diagrams use green for the engine, navy for the application and the shared-owner purple `#6B21A8` (`--color-docs-shared`) for the result bundle. The [documentation style guide](Documentation%20style%20guide.md#the-visual-vocabulary) explains when to use which.

## Token sources

### CSS tokens

Defined in `static/css/src/01-settings/tokens.css`:

| Tokens | Use |
|---|---|
| `--color-primary`, `--color-primary-hover`, `--color-primary-subtle` | Navy brand colour and its states |
| `--color-success`, `--color-success-hover` | Green and its hover state |
| `--color-map-atlas-matched`, `--color-map-osm-matched`, `--color-map-gtfs-matched` | Matched markers |
| `--color-map-atlas-unmatched`, `--color-map-osm-unmatched` | Unmatched markers |
| `--color-map-line-atlas-osm`, `--color-map-line-osm-group` | Map lines |
| `--color-docs-shared`, `--color-docs-shared-subtle`, `--color-docs-shared-border` | Shared ownership in the documentation portal |

The documentation portal marks engine-owned pages with the success palette and application-owned pages with the primary palette.

### JavaScript constants

Defined in `static/js/shared/constants.js`:

| Constants | Use |
|---|---|
| `AppConstants.COLORS.ATLAS_MATCHED`, `OSM_MATCHED`, `GTFS_MATCHED` | Matched markers |
| `AppConstants.COLORS.ATLAS_UNMATCHED`, `OSM_UNMATCHED`, `GTFS_UNMATCHED` | Unmatched markers; `GTFS_UNMATCHED` reuses the unmatched grey |
| `AppConstants.COLORS.LINE_ATLAS_OSM`, `LINE_OSM_GROUP` | Map lines |
| `AppConstants.COLORS.LINE_OSM_GROUP_DASH`, `LINE_OSM_GROUP_DASH_ALT` | Dash patterns of group lines |

## Style rules

### Semantic colours

- Prefer semantic CSS variables over raw colour literals.
- Do not introduce a second grey, blue, green, warning or danger palette for an individual page.
- A genuinely new visual meaning may receive a narrowly named token. A one-off shade should normally be mapped to an existing background, foreground, border or status token.
- New token hues must be described on this page. The Stylelint configuration does not keep a separate hidden colour allowlist.

### Alpha, shadows and overlays

Opacity does not create a new palette colour. For example, `#174092` and `rgba(23, 64, 146, 0.2)` share the same documented navy base, and the lint policy accepts both.

Prefer the standard `--shadow-*` tokens for ordinary elevation. Component-specific shadows and overlays may use alpha variants of black, white or another documented base colour; their individual opacity values do not need separate palette entries.

### Borders

Do not use a coloured left border or left accent border. Use a neutral full border, a semantic full border, spacing or a background colour to show grouping and status. Transparent left borders used only for CSS geometry, such as a tooltip arrow, are allowed.

### Gradients

A gradient is not acceptable merely because its colours belong to the palette. Use one only for a clear visual purpose, and review it separately from colour-token compliance. Flat semantic surfaces are the default.

## Enforcement

Stylelint checks authored CSS:

```bash
npm run lint:css
```

The policy:

- rejects colour bases that `static/css/src/01-settings/tokens.css` does not define;
- treats equivalent hex, named, RGB and alpha variants as the same base colour;
- rejects coloured or accented left borders while permitting transparent geometry;
- rejects Bootstrap `border-start` utility classes in templates;
- checks empty blocks, duplicate declarations and unknown CSS properties;
- excludes the import-only `static/css/main.css` entry point and vendor assets.
