# A2.7 Colours and styles

Every colour in the web app, the maps and the documentation diagrams comes from one small palette. Each colour has a fixed meaning: navy is ATLAS, green is OSM, orange is GTFS, red is an unmatched ATLAS platform. This page lists the palette, what each colour means, where the tokens are defined and how the rules are enforced.

## Canonical palette

[[canonical_palette]]

The palette is defined once as CSS tokens and once as JavaScript constants. Authored CSS references the tokens and never writes a colour value itself, not even an alpha variant of a palette colour. A new colour is added to the token source and documented here before it is used.

### Route family cards

Route family cards use the status family of each marker colour, with a full semantic border and a flat, subtle background: matched ATLAS is primary navy, matched OSM is success green, unmatched ATLAS is danger red, and unmatched OSM is secondary grey. The same families colour the source headings in map popups. The `--color-map-*` tokens colour what mirrors the map itself, such as legend dots, because they do not change with the theme. Their colours reflect saved family matches; exploring a candidate inside an unmatched variant does not change the family card's status.

Stop links in variant comparisons use the navy of the ATLAS–OSM match line.

### Operator tag status

The Operators page lists the `operator` and `operator:wikidata` values on each ATLAS operator's matched OSM stops as plain rows with counts, without colour: green stays reserved for OSM and matches, and the counts say more than bar lengths would. **Not tagged** rows are muted grey italic.

The status pill reuses the status tokens: success for a single consistent value; warning for several values, partial tagging or no tag; muted grey when no stop is matched. Each pill also carries an icon and a label, so colour is never the only signal.

## Token sources

### CSS tokens

Defined in `static/css/src/01-settings/tokens.css`. Each token names a role, not a colour, so that a second theme can give the same role a different value.

| Group | Tokens | Use |
|---|---|---|
| Surfaces | `--color-bg`, `--color-bg-subtle`, `--color-bg-muted` | Page, card and section backgrounds, from lightest to darkest |
| | `--color-surface-glass` | Translucent panel over the map or a tinted page |
| | `--color-surface-veil` | Lightens what lies beneath it: hover and open states |
| | `--color-surface-dark` | Hints, banners and toggles over a map: dark in both themes |
| | `--color-surface-banner`, `--color-on-banner` | The translucent zoom banner over a map and its white text: the same in both themes |
| | `--color-overlay` | Backdrop behind modals, drawers and loading screens: dark in both themes |
| | `--color-on-dark`, `--color-on-dark-muted` | Text, and borders or key caps, on the dark surface and the backdrop |
| Text | `--color-fg`, `--color-fg-muted`, `--color-fg-subtle` | Body text and headings, secondary text, placeholders and faint icons |
| | `--color-on-accent`, `--color-on-accent-subtle`, `--color-on-accent-muted` | Text and icons on a filled colour; translucent controls on a filled chip |
| | `--color-on-warning` | Text on the warning fill, where `--color-on-accent` is too light in the light theme |
| Lines | `--color-border`, `--color-border-emphasis` | Standard and stronger borders |
| | `--color-focus-ring` | Keyboard focus ring |
| Status | `--color-{family}`, `-hover`, `-subtle`, `-border` | Base, hover, tinted background and tinted border of `primary`, `secondary`, `success`, `warning` and `danger` |
| | `--color-success-fg`, `--color-warning-fg`, `--color-danger-fg` | Text on the family's subtle background or on the page |
| Map | `--color-map-*` | Markers and lines, the same values as the JavaScript constants below, in both themes |
| Code quality | `--color-quality-*` | Lines of the code quality map, and `--color-quality-module-1` to `-10` for its modules ([values](#code-quality-map)) |
| Documentation | `--color-docs-shared`, `--color-docs-shared-subtle` | Shared ownership in the documentation portal |

Primary navy also carries information: there is no separate info family. Secondary grey marks neutral and minor states.

The documentation portal marks engine-owned pages with the success palette and application-owned pages with the primary palette.

The same file defines the shadows: `--shadow-xs` to `--shadow-xl` for elevation, `--shadow-inset` for recessed controls, `--shadow-primary` for navy-tinted emphasis and `--shadow-text` for text on a filled colour.

Tints are literal `rgba()` values in the token file rather than `color-mix()` expressions, because WeasyPrint renders the token file into the PDF reports and does not support `color-mix()`. Outside the token file, a `color-mix()` of tokens is allowed where a page derives a shade.

## Dark theme

The app has a light and a dark theme. The navbar's theme menu offers **System**, **Light** and **Dark**; System, the default, follows the operating system and changes with it. The choice is kept in the browser's local storage under `theme`.

`static/js/shared/theme.js` loads in `<head>` before the stylesheets and sets `data-bs-theme` on `<html>`, so a page is painted in its theme from the start. Bootstrap reads the same attribute. When the theme changes, the script fires a `themechange` event on the document for code that draws its own colours.

The dark theme gives every role in the token file a dark value; outside the token file, only `c-leaflet.css` refers to a theme, to dim the map tiles and invert the layer control's dark icon. Its rules:

- Surfaces get lighter as they rise: the page (`--color-bg-subtle`) is darkest, cards (`--color-bg`) are lighter and `--color-bg-muted` lighter still. Borders separate them, since shadows barely show on dark surfaces.
- Status colours are lighter than in the light theme so that they read on dark surfaces, and text on a filled colour (`--color-on-accent`) turns dark.
- Hints and banners over a map (`--color-surface-dark`, `--color-surface-banner`) and the backdrop stay dark in both themes, with light text (`--color-on-dark`, `--color-on-banner`): over the map tiles, a light banner would stand out less than a dark one.
- Every text and fill pair meets WCAG AA: at least 4.5:1 for text.
- The map markers and lines and the code quality colours keep their values; their meaning does not depend on the theme. Map tiles are dimmed. The code quality map, which draws its own light palette on a canvas, keeps the light theme with `data-bs-theme="light"` on its container: any element can opt out this way.
- Bootstrap's body, border, link and tertiary variables point at the tokens, so its components, forms and tables follow the theme. Use theme-aware Bootstrap utilities such as `bg-body` and `text-body`, not `bg-white`, `text-dark` or `btn-light`.
- Bootstrap colours a disabled button from its own palette, so `buttons.css` points each button variant's `--bs-btn-disabled-*` variables at the tokens: a disabled button keeps its colour, faded.
- The PDF reports never set the attribute and are always light.

## Style rules

### Semantic colours

- Use the tokens. Hex, `rgb()`, `hsl()` and named colours appear only in the token file; `transparent` and `currentColor` are allowed everywhere.
- Do not add a fallback to a colour token (`var(--color-bg, #fff)`): every token is defined, and a fallback is a second, stale copy of its value.
- Do not introduce a second grey, blue, green, warning or danger palette for an individual page.
- A genuinely new visual meaning may receive a narrowly named token. A one-off shade is mapped to an existing background, foreground, border or status token.
- New tokens must be described on this page. The Stylelint configuration does not keep a separate hidden colour allowlist.

### Alpha, shadows and overlays

Opacity creates a new colour value, so it is a token like any other. Each family has one subtle background and one border tint; a translucent surface is either `--color-surface-glass` (a panel) or `--color-surface-veil` (a hover or open state), and a dark one is `--color-overlay`, `--color-surface-dark` or `--color-surface-banner`. A component does not pick its own opacity.

Use the `--shadow-*` tokens for elevation, insets and text shadows.

### Borders

Do not use a coloured left border or left accent border. Use a neutral full border, a semantic full border, spacing or a background colour to show grouping and status. Transparent left borders used only for CSS geometry, such as a tooltip arrow, are allowed.

### Gradients

A gradient is not acceptable merely because its colours belong to the palette. Use one only for a clear visual purpose, and review it separately from colour-token compliance. Flat semantic surfaces are the default.

## Enforcement

Stylelint checks authored CSS:

```bash
npm run lint:css
```

The policy:

- rejects every colour literal outside `static/css/src/01-settings/tokens.css`, including those in `var()` fallbacks and inside `color-mix()`;
- rejects `var(--color-*)` references to tokens the token file does not define;
- rejects coloured or accented left borders while permitting transparent geometry;
- rejects Bootstrap `border-start` utility classes in templates;
- checks empty blocks, duplicate declarations and unknown CSS properties;
- excludes the import-only `static/css/main.css` entry point and vendor assets.
