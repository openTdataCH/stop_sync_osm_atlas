# Problem Detection and Prioritization

After the matching pipeline completes ([Section 2](2.%20Matching%20process.md)), the system performs a comprehensive analysis to identify data quality issues in both datasets.

## Problem Categories

The documentation separates problems into three conceptual categories, but the current implementation only emits stop-level `Problem` rows. Route entity and route membership problem pages describe planned route diagnostics.

| Category  | Question | User Action |
|----------|----------|-------------|
| **[Stop Problems](4.1%20Stop%20Problems.md)**  | "Is this stop at the correct location with correct attributes?" | Move node, update tags, fix matching. |
| **[Route Entity Problems](4.2%20Route%20Entity%20Problems.md)** | "Does this route exist and is it defined correctly?" | Create or delete route relation; fix route tags. |
| **[Route Membership Problems](4.3%20Route%20Membership%20Problems.md)** | "Is the list of stops for this route consistent?" | Add/remove stops from relation; reorder stops; fix roles. |

### 1. Stop Problems (Implemented)
Issues with **individual stops** (Distance, Attributes, Isolation, Duplicates). See [4.1 Stop Problems](4.1%20Stop%20Problems.md).

### 2. Route Entity Problems (Planned)
Issues with the **Route object** itself.
*   **Not yet implemented**: route-level `Problem` rows, metadata mismatch diagnostics, and unmatched route detection.
*   See [4.2 Route Entity Problems](4.2%20Route%20Entity%20Problems.md).

### 3. Route Membership Problems (Planned)
Issues with the **stop-route relationship**.
*   **Goal**: Ensure the sequence of stops and their directional roles match.
*   See [4.3 Route Membership Problems](4.3%20Route%20Membership%20Problems.md).

## Architecture

Problem detection is built on the same domain models as the matching pipeline. The enriched `MatchingOutput` (containing `MatchRecord`, `SourceStop`, and `OsmNode` entities plus duplicate and route-evidence lookups) flows directly into problem detection — no ORM or dictionary conversion is needed.

### Polymorphic Predicates

Each problem predicate is a plain function with a **polymorphic signature**:

```python
def predicate(ctx: ProblemContext, record: MatchRecord | SourceStop | OsmNode) -> list[ProblemResult]
```

Predicates use `isinstance` checks to decide what to evaluate:
- `distance_problem`, `attributes_problem`, and `contradicts_route_matching_problem` only act on `MatchRecord` (return `[]` for bare nodes)
- `unmatched_problem` only acts on bare `SourceStop` or `OsmNode` (returns `[]` for `MatchRecord`)
- `duplicates_problem` acts on all three types

This allows the same `STOP_PROBLEM_PIPELINE` list to be used for both matched and unmatched records.

### Two Invocation Paths

| Record type | Invocation | Where |
|-------------|-----------|-------|
| **Matched** (`MatchRecord`) | `match_record.evaluate_matched_problems(problem_ctx, STOP_PROBLEM_PIPELINE)` | `api.py` — evaluates the domain entity |
| **Unmatched** (`SourceStop` / `OsmNode`) | Direct iteration over `STOP_PROBLEM_PIPELINE`, calling each predicate with the node | `api.py` — evaluates unmatched entities and attaches nearest-counterpart evidence |

Both paths produce `ProblemResult` values. The exported `evaluate_unmatched_problems(...)` helper offers the same list-oriented predicate contract to external callers, but the runtime path in `api.py` iterates directly. The engine exports complete problems with stable IDs, priorities and affected entity keys. The app projects the exported `problem_type` and `priority` into its own rows, without reevaluating predicates.

### `ProblemResult` Value Object

All predicates return `ProblemResult`, a lightweight frozen dataclass decoupled from SQLAlchemy:

```python
@dataclass(frozen=True)
class ProblemResult:
    problem_type: str        # 'distance', 'attributes', 'contradicts_route_matching', 'unmatched', 'duplicates'
    priority: int            # 1 = P1, 2 = P2, 3 = P3
    has_source_duplicate: bool = False
    has_osm_duplicate: bool = False
```

## Priority Levels

All problems use a consistent three-level priority system:

| Level | Meaning |
|-------|---------|
| **P1** | Critical |
| **P2** | Significant |
| **P3** | Minor |

Priority assignment is **rule-based** and considers factors like:
- Distance thresholds (explicit values in `MatchingProfile`)
- source operator abbreviation (`SBB` is exempt from the two highest distance severities in the Swiss profile)
- attribute importance (the configured station reference is more critical than operator names)
- Isolation status (stops with no nearby counterparts are higher priority)
