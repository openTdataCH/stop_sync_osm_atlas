# ATLAS Routes Unified

This section describes how we enrich the ATLAS stop data with route and direction information.

## Statistics

- **Total ATLAS Stops**: {{stat:routes.atlas_total}}
- **ATLAS Stops with Route Data (Any Source)**: {{stat:routes.atlas_with_routes}} ({{stat:routes.atlas_with_routes_percent}}%)

## The Goal
The raw ATLAS data gives us the physical location of stops (platforms), but it doesn't tell us **what** stops there. To perform matching with OpenStreetMap, we can use:
- Which lines serve a platform (e.g., "Tram 11", "S12").
- The direction of travel (e.g., "towards Rehalp").

## Two Data Sources
The unified schema supports two timetable sources. In the current active pipeline, GTFS ingestion is enabled and HRDF ingestion is documented for future reuse:

1.  **GTFS ([1.2.1](1.2.1%20GTFS%20ATLAS%20data.md))**:
	Provides `(stop_id, route_id, direction_id)` memberships plus a representative first→last Swiss-stop direction string per `route_id`.

2.  **HRDF ([1.2.2](1.2.2%20HRDF%20ATLAS%20data.md))**:
	Provides `(sloid, line_name, direction_uic)` memberships plus a human-readable destination name derived from `FPLAN` and `BAHNHOF` when enabled.

## Orchestration
The creation of this unified file is orchestrated by the main script `matching_and_import_db/downloader/get_atlas_data.py`. This script:
1.  Downloads the raw ATLAS data.
2.  Calls the active **GTFS** processing flow to extract route information in memory.
3.  Writes unified rows directly to the output CSV using the `write_unified_routes_csv_direct()` function.

HRDF processing logic exists in a separate module and can be reconnected in the future, but it is not currently invoked by this orchestration path.

## The Unified Output
The processing output is a single unified file: `data/processed/atlas_routes_unified.csv`.

The unified schema supports one route-evidence row per stop-source association: a GTFS `(sloid, route_id, direction_id)` row and, when HRDF ingestion is enabled, an HRDF `(sloid, line_name, direction_uic)` row.

**Why combine GTFS and HRDF into one file?**
Having a single unified file simplifies the downstream matching algorithm (`route_matching_unified.py`) and the database importer. It allows them to ingest all route and direction data agnostically without needing to parse multiple different datasets or manage logic across multiple files. The matching algorithm simply treats each row as a piece of "route evidence" associated with an ATLAS platform.

**Are rows mixed with GTFS and HRDF data?**
The schema is source-exclusive per row: a row contains **either GTFS or HRDF fields**, and the `source` column indicates the origin. In the current active pipeline, rows are GTFS-sourced; if HRDF ingestion is re-enabled, platforms served by both sources will appear as multiple rows.

> **Note on Terminology**: This file establishes **Route-to-Stop associations** (enriching ATLAS stops with route info). This is distinct from the **Stop-to-Stop matching** (ATLAS to OSM).  [2.4 Route Matching](2.4%20Route%20Matching.md) uses the **Route-to-Stop** data to find Stop-to-Stop matches.

### Data Structure

> **A Note on GTFS `route_id`s**:
> The `route_id` is an internally generated ID specific to the system creating the timetable data. It follows a strict naming convention: `<Betriebszweig>-<Liniennummer>-<Projektkurzbezeichnung>-<Linienversionsnummer>` *(Branch of operation) - (Line number) - (Project short designation) - (Line version number)*

The file contains the following columns, note which ones are populated by which data source:

| Column Name | Source | Example | Explanation |
| :--- | :--- | :--- | :--- |
| **`sloid`** | Both | `ch:1:sloid:1234:1` | The ATLAS identifier for the specific platform. |
| **`source`** | Both | `gtfs` | The data source (`gtfs` or `hrdf`). Determines which following columns are populated. |
| **`evidence`** | Both | `gtfs_first_last` | Internal metadata indicating the method used to associate the route/direction with the ATLAS stop. |
| **`route_id`** | GTFS | `11-T-j25-1` | The original GTFS identifier for the route. Empty for HRDF rows. |
| **`route_id_normalized`** | GTFS | `11-T-jXX-1` | A simplified version of `route_id`. In Switzerland's GTFS data, the `route_id` format includes a `<Projektkurzbezeichnung>` (project short designation) that denotes the specific timetable year (e.g., `-j24`, `-j25`, `-j26`). This means a physical route gets a new ID every year. If an OSM mapper entered `gtfs:route_id=11-T-j24-1` in 2024, it wouldn't match the backend's 2026 data (`11-T-j26-1`). This field normalizes year-specific codes to `-jXX` (e.g. `11-T-jXX-1`), allowing historical OSM tags to successfully match against current datasets. Empty for HRDF rows. |
| **`route_name_short`** | GTFS | `11` | The GTFS short route name (usually the line number). Empty for HRDF rows. |
| **`route_name_long`** | GTFS | `Tram` | The GTFS long route name. Empty for HRDF rows. |
| **`direction_id`** | GTFS | `0` or `1` | GTFS direction identifier. Empty for HRDF rows. |
| **`line_name`** | HRDF | `11` | The HRDF line name (often equivalent to `route_name_short`). Empty for GTFS rows. |
| **`direction_name`** | Both | `Rehalp` | For HRDF rows, the destination name from `FPLAN`/`BAHNHOF`. For GTFS rows, a representative first→last Swiss-stop direction string reduced per `route_id`. |
| **`direction_uic`** | HRDF | `8503000` | The UIC station identifier of the destination. Empty for GTFS rows. |

This unified dataset allows the matching algorithm to work agnostically, without worrying about where the route data came from.
