# 8. Tests and Continuous Integration

CI separates the engine, review application, browser code and result contract. Jobs only read the repository: tests never commit or push generated documentation.

| Suite | Command from repository root | Dependencies |
|---|---|---|
| Engine | `python -m pytest engine/tests -q` | Install `./engine[swiss,gtfs,acquisition,test]`. No app or database. |
| Review application | `python -m pytest tests -q` | Base, web, scheduler and test requirements. No engine. |
| Browser | `npm test -- --runInBand` | `npm ci`. |
| Producer/consumer contract | Run the example GTFS CLI, then `backend.importing.bundle.read_bundle` | Engine producer plus the stdlib-only bundle reader. |
| Real publication | `python -m pytest tests/test_snapshot_publication.py -q` | Disposable PostGIS database in `TEST_POSTGRES_URI`. |

The PostGIS tests require a database name ending in `_test` and reset its public schema. They cover staging visibility, transactional rollback and publication lock timeout. Default app tests skip those cases when that explicit test URI is absent.

Engine regressions include the original Swiss predicate and pair/trio cases, per-run state isolation, namespace conflicts, co-located OSM identities, optional route evidence, adapter parsing and atomic result writing. The generic GTFS example uses no Swiss IDs.

Application contract tests read the checked-in `tests/fixtures/result-v1` fixture with engine imports forbidden. The app suite also preserves Routes SQL pagination, maintenance and timeout checks. JavaScript tests cover all four canonical map entity adapters, layouts, relationships, popups, viewport policies and page-specific behavior.
