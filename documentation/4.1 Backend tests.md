# A4.1 Backend Tests

Application tests live in `tests/` and cover Flask blueprints, queries, import/publication, scheduling, documentation and export services. Keep this environment separate from the engine's environment: the app consumes a versioned bundle and does not require the producer package to be installed.

## Setup and execution

`make quality` is the supported complete run. It supplies Python 3.13, native PDF dependencies, an isolated engine interpreter and disposable PostGIS. For native focused development, use Python 3.13 and install the app dependencies in their own virtual environment:

```bash
python3.13 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements-base.txt -r requirements-web.txt -r requirements-scheduler.txt -r requirements-test.txt -r requirements-quality.txt
DATABASE_URI=sqlite:// STATE_BACKEND=memory python -m pytest tests/test_result_bundle.py tests/test_bundle_properties.py -q
```

Native PDF tests also require WeasyPrint's platform libraries. Use the quality container if these are unavailable; an import or missing-library failure is an environment failure, not proof of a product regression. The [quality guide](../quality/README.md) covers complete native setup, supported versions and Docker troubleshooting.

Run an individual test with `python -m pytest tests/test_file.py::test_name -q`, or use `-k expression` to select a behavior. Use `DATABASE_URI=sqlite:// STATE_BACKEND=memory` for app-only runs. `ENGINE_DIR` selects the engine source/documentation checkout when it is not in the default sibling or nested location; it does not install the engine into the app environment.

## Database and producer isolation

Most Flask tests use the lightweight SQLite fixtures in `tests/conftest.py`, with `monkeypatch` replacing expensive background tasks where the test concerns request handling. These tests cannot establish PostgreSQL transaction or locking behavior.

For publication tests, set `TEST_POSTGRES_URI` to a **disposable PostGIS database whose name ends in `_test`**. These tests reset its public schema. The full quality command creates this database automatically; never point the variable at a deployment database. Missing the explicit URI causes those cases to skip in a focused native run.

The three tests in `test_engine_progress_contract.py` require `PROGRESS_CONTRACT_ENGINE` and an engine-capable interpreter. The full runner clears that variable for the app suite, then executes these tests separately using `ENGINE_PYTHON`. This preserves the app's engine-free guarantee while verifying the real producer. Follow the quality guide's isolated setup rather than installing both packages together to remove the expected app-suite skips.

## Coverage and evidence

The full runner collects `--cov=backend --cov-branch`, JSON/XML coverage and JUnit test results under `quality/raw/`. It separately collects engine evidence and records command results, tool versions, repository revisions and input fingerprints. It clears previous raw evidence before starting so a failed run cannot inherit a previous passing report.

For a one-off coverage inspection, use `python -m pytest tests --cov=backend --cov-branch --cov-report=term-missing`; this does not create a complete supported quality report. The report generator requires the full run manifest and matching inputs. Do not hand-edit generated JSON or update its timestamp to hide a stale result.

Coverage measures execution, not correctness. Review the negative examples and invariant tests for critical paths alongside the branch percentage. Changed-line coverage and module targets remain advisory during baseline collection. Documentation obligations measure the presence of the module's explanation/reference/operations/decision documents; reviewers still judge their accuracy and usefulness.

## Adding or changing backend behavior

Assign new production files to exactly one module in `quality/modules.yml`, add meaningful acceptance and failure examples, and update the module's test references and relevant documentation. Prefer exercising public behavior through the existing fixtures. Keep the producer and consumer validators independent: cross-repository compatibility is tested through versioned data, not shared Python imports.

Run focused tests while developing, then `make quality-fast` or its container equivalent. Finish with `make quality` for changes affecting contracts, publication, scheduling, dependencies or the quality infrastructure. Inspect failures and raw evidence even if a report was generated: generating a report is not itself a passing gate.
