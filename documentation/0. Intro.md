# 0. Project overview

This project compares official public transport data with OpenStreetMap (OSM), explains where they disagree and shows the result on a map, so that both datasets can be improved. The Swiss deployment, [atlas.osm.ch](https://atlas.osm.ch), compares **ATLAS**, Switzerland's official stop registry, and the Swiss **GTFS** timetable with OSM. The matching engine can process other GTFS feeds as well.

This page explains how the project works, what it links, and how to find your way through the documentation. Unfamiliar terms are defined in the [glossary](0.1%20Glossary.md).

## How the project works

![How the project works: sources, matching engine with adapters and a source-neutral core, result bundle, review application](images/overview-big-picture.svg)

- The **matching engine** (`public-transport-matcher`) downloads or reads the public sources, matches stops and routes, and detects data problems. It is a separate Python package with its own repository, and needs no web server or database. Format adapters turn each source (ATLAS, any GTFS feed, OSM) into common records, a dataset profile sets the matching rules, and a source-neutral core does the matching ([E1](../engine/documentation/1.%20Download%20and%20process%20data.md)).
- It writes a **result bundle**: a versioned directory of files containing every match, unmatched stop, problem and route comparison. The bundle is the only data that passes from the engine to the application.
- The **review application** (this repository) imports each bundle into a PostGIS database and presents it on a website: a map, a problems page, route comparisons, statistics and reports. Its scheduler runs a pinned engine release on a schedule (daily by default) and publishes each new result as one database snapshot. Other sites and scripts can read the same bundle format.
- Reviewers use the findings to fix OpenStreetMap and to report issues in ATLAS. The next run measures the improvement.

## What the project links

Official data and OSM describe the same stops very differently. The figure follows one stop with two platforms through the three datasets.

![One stop in three datasets, with the four links the project maintains](images/overview-one-stop.svg)

The figure numbers the four links the project maintains from top to bottom. Link 2 is the main result; the other three make it reliable.

1. **OSM node ↔ OSM node.** OSM often maps one platform as two nodes, a platform and a stop position on the road. Before matching, the engine groups such nodes into one [OSM stop unit](0.1%20Glossary.md#osm-stop-unit), so that both are matched together. See [OSM grouping](../engine/documentation/2.%20Matching%20process.md#osm-grouping-before-the-rules).
2. **ATLAS platform ↔ OSM stop.** Each official platform is matched to the OSM element or elements that represent it, by a fixed sequence of [matching rules](0.1%20Glossary.md#matching-rule): shared identifiers, names, routes and distance. See [E2 Matching process](../engine/documentation/2.%20Matching%20process.md).
3. **GTFS `stop_id` ↔ ATLAS SLOID.** Routes come from the GTFS timetable, which identifies stops by `stop_id`. The engine resolves every `stop_id` to an ATLAS [SLOID](0.1%20Glossary.md#sloid), so that a route's stops can be compared with OSM. See [E1.2 GTFS and ATLAS](../engine/documentation/1.2%20GTFS%20ATLAS%20data.md).
4. **GTFS route ↔ OSM route relation.** Whole lines and their directions are compared, using the resolved stop identities. Shared routes are also evidence for link 2: a nearby OSM node served by the same route and direction is very likely the same stop. See [E3 Routes](../engine/documentation/3.%20Routes.md).

Where the datasets disagree, the engine records a [problem](0.1%20Glossary.md#problem): a matched pair that is too far apart, a stop without a counterpart, conflicting names or platform codes, duplicates, or a match that contradicts the route evidence. See [E4 Problems](../engine/documentation/4.%20Problems.md).

## Two projects, one contract

The engine and the review application are separate repositories with separate releases, tests and dependencies. They are developed side by side as sibling checkouts.

| | Matching engine | Review application |
|---|---|---|
| Repository | The `public-transport-matcher` package, checked out beside this one as `../engine` | `stop_sync_osm_atlas` (this repository) |
| Does | Acquisition, input parsing, stop and route matching, problem detection, result bundles | Scheduling, bundle import, PostGIS, web API, map and review pages, reports |
| Depends on | NumPy and SciPy; optional extras add pandas, DuckDB and geospatial libraries | Flask, SQLAlchemy, PostgreSQL/PostGIS |
| Never | imports Flask, SQLAlchemy or application code, or opens the application database | imports engine code or re-implements a matching rule |
| Documentation | [E1–E6](../engine/documentation/1.%20Download%20and%20process%20data.md), in the engine repository | [A1–A4](1.%20Database.md), in this repository |

Three things connect them: the scheduler starts the engine's command-line tool as a separate process, the engine reports progress as JSON lines on its output, and the engine writes a [result bundle](../engine/documentation/Result%20bundle%20format.md) that the application imports. [A3 Architecture](3.%20System%20Architecture.md) shows the complete picture.
