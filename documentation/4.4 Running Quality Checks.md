# A4.4 Running the quality checks

This page explains how to run, maintain and troubleshoot the quality checks of the application and the engine: the commands, the supported setups, CI, the module catalog and its baselines. Start in the application repository. To read the results, see [A4.3 Code quality](4.3%20Code%20Quality.md).

## Choose a command

| Command | Purpose | Requirements |
|---|---|---|
| `make quality-fast-container` | Catalog, architecture, Python/JS/CSS lint, template/config syntax, vendor checks and focused quality/contract tests | Docker Compose v2 and an engine checkout |
| `make quality` | Full app, browser and engine suites; PostGIS publication and producer/consumer checks; coverage sanity; structural debt; report and map generation. CI runs this command too | Docker Compose v2 and an engine checkout |
| `make quality-fast` | Same fast checks using installed local tools | Python 3.13, Node 22.x at least 22.13, `requirements.txt` and `requirements-dev.txt` |
| `make quality-down` | Remove the dedicated quality Compose stack and its disposable data | Docker Compose v2 |
| `make deploy-report` | Commit and push the passing CI report of the pushed `HEAD` for the next deployment ([details](4.3%20Code%20Quality.md#how-the-report-reaches-the-site)) | `git`, an authenticated `gh` CLI |

A fast pass ends by naming `make quality`. It does not execute the complete browser or application suite, so it establishes neither coverage nor publication safety. Dependency audits and CodeQL are separate CI checks; `make quality` does not run those network services.

Even a full pass leaves some things unchecked. There is no type checking, no end-to-end, rendering or visual test in a real browser and no performance budget; mutation testing covers only a sample of the engine's result validation.

## Supported local setup

### Docker: the complete reproducible path

Keep a quality-enabled engine checkout beside the application:

```text
workspace/
  stop_sync_osm_atlas/
  engine/
    quality/modules.yml
```

From `stop_sync_osm_atlas/`:

```bash
make quality-fast-container
make quality
make quality-down
```

For another engine location, set `ENGINE_DIR`, in `.env` or on the command line:

```bash
make quality ENGINE_DIR=/absolute/path/to/engine
```

Every tool finds the engine the same way: `ENGINE_DIR` if set (relative paths start at the application checkout), else `engine/` inside the application, else `../engine`. The Python tools share `engine_dir()` in `backend/version.py`; Docker Compose also reads `ENGINE_DIR` from `.env`.

`Dockerfile.quality` supplies Python 3.13, Node 22, PDF rendering libraries, app tools and an isolated engine virtual environment. `compose.quality.yml` bind-mounts app source and the engine checkout, keeps engine source read-only, and gives the runner its image's Node dependencies. The dedicated `osm-atlas-quality` project provisions PostGIS 16/3.4 with disposable in-memory database storage. It does not share production volumes or use the deployment's database credentials. Full publication tests can replace test data, so this separation is essential.

Both container commands build the image. Rebuild after requirement, lockfile or engine dependency changes; changing a bind-mounted source file does not update installed packages. Preflight rejects an installed Python package that does not satisfy the requirement files.

A full run clears `quality/raw/` before collecting evidence, so a failed run cannot inherit an earlier passing result, then writes outputs back into the app checkout. Save any previous run you need to investigate before starting another full run. Stop editing either repository while the final run is in progress: source changes invalidate its fingerprints, including changes to documentation, configuration and tests.

### Native development

Use Python **3.13** and Node **22.x, version 22.13 or later**. The runner checks those versions; an arbitrary newer Node major is not the supported toolchain. Native PDF tests also need the platform's Pango/Cairo libraries. Prefer the container when those libraries are unavailable.

```bash
python3.13 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt -r requirements-dev.txt
npm ci
make quality-fast PYTHON=python
```

`requirements-dev.txt` holds the test tools and the exact analyser versions the quality runner uses. It includes Hypothesis and JSON Schema because ordinary pytest collection includes property and quality-schema tests. See [A3.1 Dependencies and builds](3.1%20Dependency%20Management%20%26%20Build%20Strategy.md#python-requirements).

Do not install `osm-public-transport-matcher` into the app interpreter. Full verification checks this boundary explicitly. To run the full command natively, create a separate engine environment and supply a database dedicated to tests:

```bash
python3.13 -m venv ../engine/.venv
../engine/.venv/bin/python -m pip install '../engine[swiss,gtfs,quality]'
TEST_POSTGRES_URI=postgresql+psycopg://test:test@localhost:5432/transport_test \
  python scripts/run_quality.py full --engine-python ../engine/.venv/bin/python
```

The example assumes that disposable PostGIS database already exists. It is not a command for connecting to a production database. For engine-only work, use the engine's own quality guide, `engine/quality/README.md`.

## CI and repository setup

The **Required quality** job of the **Quality** workflow (`.github/workflows/tests.yml`) runs on pull requests, pushes to `main` and manual dispatch. It checks out the engine commit pinned in `engine.ref` into `engine/` and runs `make quality`, so CI builds the same image and disposable PostGIS database as a local run. The app suite runs without an engine installation; the engine suite uses the image's separate engine interpreter, which the app's engine import contract also runs as a subprocess.

Repository administrators must configure branch protection or rulesets requiring **Required quality**, **Dependency security audit**, and the applicable **Security analysis** checks for Python and JavaScript/TypeScript. Confirm the exact check names after the first run.

Committing workflow files does not configure repository protection or publish engine changes. Update `engine.ref` as part of a reviewed cross-repository contract change.

The required workflow always uploads `quality-<app SHA>` evidence, including failed-run outputs, with 30-day retention. Inspect job output alongside the artifact: missing outputs may indicate that collection itself failed. The workflows only read the repository: neither they nor the tests commit or push the evidence they generate. A report reaches the site only through `make deploy-report` ([A4.3](4.3%20Code%20Quality.md#how-the-report-reaches-the-site)).

The **Periodic quality** workflow (`.github/workflows/deep-quality.yml`) runs production Python dependency auditing and an npm audit on pull requests, weekly and on manual invocation. The npm audit fails at high severity; the Python audit fails on its reported vulnerabilities. Its `dependency-security-<app SHA>` artifact preserves both audit reports. Dependency changes must update the corresponding requirement or lockfile and any vendored assets, then rerun behavioural tests.

**CodeQL** (`.github/workflows/codeql.yml`) analyses app Python and first-party browser JavaScript on pull requests, pushes to `main` and its weekly schedule. Vendor files are excluded. Findings are available through GitHub code scanning; a successful job is not itself a per-module security score. The report records security as `not measured` for every module, so read the audit and CodeQL results directly.

The standalone engine has its own production dependency audit and Python CodeQL workflow. Configure its required branch checks independently, as its quality guide describes. An app audit does not establish that the engine's separate dependency closure was scanned.

The periodic mutation job runs on the weekly and manual paths, not every pull request. It targets the engine's result-position validator and publishes a `result-validation-mutation-<app SHA>` artifact. Survivors do not fail the job; inspect them in the artifact. A failed execution, a target that matches no mutant, or sources or tests that change during the run do fail it.

## Maintain the module catalog

| File | Who maintains it | Meaning |
|---|---|---|
| `quality/modules.yml` | Maintainers | Module responsibility, criticality, owner, invariants, source/test paths, entry points, documentation and declared dependencies/contracts |
| `quality/modules.schema.json` | Quality maintainers | Validated catalog structure; the catalog uses JSON-compatible YAML |
| `quality/exclusions.json` | Maintainers, with reasons | Shared source exclusions and additional clone exclusions |
| `quality/baseline.json` | Reviewed changes | Accepted structural findings |
| `quality/exceptions.json` | Named owners | Exact, temporary structural finding exceptions with expiry |
| `quality/latest.schema.json` | Quality maintainers | Versioned aggregate evidence structure |
| `quality/decisions.md` | Maintainers | Why ownership, contracts, evidence and ratchets work this way |

Every inventoried production source has exactly one ownership module. Source inventory combines tracked and new nonignored Git files, configured source roots and explicit files. It recognises Python, JS/MJS/CJS, CSS, templates, SQL, shell, YAML, JSON and TOML; explicit catalog entries include extensionless deployment files and requirement lists. New files outside an established directory must still be assigned an owner. Symlinks are not followed as source files.

Tests may support multiple modules and are associated through each module's test patterns. Contract nodes connect producer and consumer owners; a contract does not assign a second owner to their implementation files. Documentation paths are obligations, not an instruction to document every private helper.

The source exclusions cover generated evidence and documentation, the published report, the built CSS bundle, vendored/installed dependencies, runtime data, bytecode, mutation worktrees, and tests/fixtures that are modelled as evidence. Migrations remain owned source, but their immutable steps are excluded from clone detection. Each repository can add explicit exclusions to its catalog; always explain the category being excluded.

Runtime coverage denominators are narrower than source ownership: app `backend/**/*.py`, engine `src/**/*.py`, and every first-party `static/js/**/*.js`. CSS, templates, deployment files and build tooling remain owned and checked, but are not assigned runtime coverage percentages.

When adding or moving code:

1. Choose the existing responsibility owner, or add a module with a coherent responsibility and failure boundary.
2. Update source/test patterns and required explanation/reference/operations documents. Set criticality with the [rubric](4.3%20Code%20Quality.md#criticality).
3. Declare stable entry points, dependencies and cross-repository contracts. The dashboard flags code dependencies that the catalog does not declare.
4. Run `check`, relevant focused tests and `make quality-fast`; finish with full evidence appropriate to the change.

## Command-line reference

Run `python scripts/quality.py --help` for all options. Examples below assume the supported environment; each command finds the engine like every other tool, and `--engine-dir PATH` overrides it.

| Command | Result |
|---|---|
| `python scripts/quality.py check` | Validates catalog schemas, single ownership, documentation/test references, entry points, exceptions and enforced architecture boundaries |
| `python scripts/quality.py coverage` | Validates current raw coverage against source fingerprints and all expected runtime files; does not execute tests |
| `python scripts/quality.py debt` | Runs jscpd and Vulture, writes raw findings and fails on new unexcepted structural debt |
| `python scripts/quality.py report` | Reads existing evidence and writes `latest.json`, `report.md` and both maps; does not recollect tests |
| `python scripts/quality.py map` | Generates the complete machine-readable module/file/symbol map and the dashboard's code map |
| `python scripts/quality.py context app.snapshot-publication` | Prints that module's responsibility, invariants, entry points, dependencies, tests, docs and verification commands |
| `python scripts/quality.py impact backend/importing/publication.py --depth 1` | Prints a bounded JSON neighbourhood for matching module/file IDs |
| `python scripts/quality.py symbol publish_snapshot --depth 2` | Prints matching symbols and their bounded graph neighbourhood |

`--depth` accepts only `1` or `2` for `impact` and `symbol`. Matching is case-insensitive substring matching over node IDs; a broad search term can match several symbols or files. Use a more specific path or name to narrow the result. These commands also refresh the complete map before printing the selected view.

`report --base origin/main` enables advisory changed-line coverage for the app. The comparison revision must exist locally. New untracked code is included in local comparisons; CI supplies the pull request base through `QUALITY_BASE`. It does not compute an engine diff, so engine modules always record changed coverage as `not_measured`, as does every module without a base.

`debt --write-baseline` is an explicit baseline-maintenance operation, described in [Structural debt and exceptions](#structural-debt-and-exceptions). It must not be added to CI or to an automatic fix command.

The lower-level runner is `python scripts/run_quality.py fast|full|syntax`. `fast` and `full` accept `--engine-dir`; `full` also uses `--engine-python` (defaulting to `ENGINE_PYTHON` or `/opt/engine-venv/bin/python`). `syntax` parses Jinja templates and configured YAML/JSON without importing the app. Prefer the Make targets for ordinary use.

## Evidence files and freshness

The full runner records in `raw/checks.json` both repositories' revisions and source fingerprints, the Python, Node and analyser versions, and each check's command, exit status and duration. It continues collecting independent checks after failures and returns nonzero if any required check failed. Report generation is useful even after a test failure; producing a report is not equivalent to passing the run. A local run writes these files; to read the report, open `quality/report.md`. The site shows only the published report ([A4.3](4.3%20Code%20Quality.md#how-the-report-reaches-the-site)).

| Artifact, relative to `quality/` | Contents |
|---|---|
| `latest.json` | Schema-validated aggregate: app/engine revisions, fingerprints, generation time, completeness, tools, checks, module measurements and raw-artifact references |
| `report.md` | Generated Markdown projection of the same aggregate |
| `quality-map.json` | Typed nodes/edges, provenance and graph limitations |
| `code-map.json` | The dashboard's projection of that map: modules with their catalog entries, files, file-to-file links counted by kind, and each module's names used from other modules |
| `raw/checks.json` | Full-run manifest and check results |
| `raw/fast-checks.json` | Fast-run manifest; does not certify earlier full-run evidence |
| `raw/app-tests.xml`, `raw/engine-tests.xml` | Pytest JUnit test outcomes |
| `raw/app-python-coverage.json`, `raw/app-python-coverage.xml` | App line/branch coverage in JSON and XML |
| `raw/engine-python-coverage.json`, `raw/engine-python-coverage.xml` | Engine line/branch coverage in JSON and XML |
| `raw/javascript-tests.json` | Jest suites, individual assertions and outcomes |
| `raw/javascript-coverage.json`, `raw/lcov.info` | Browser production coverage: Istanbul statements, functions and branches keyed by source path, and LCOV for other coverage viewers |
| `raw/jscpd/jscpd-report.json` | Raw clone-detector output |
| `raw/vulture.txt`, `raw/debt.json` | Certain dead-code output and normalised structural findings |
| `raw/python-audit.json`, `raw/npm-audit.json` | Separate dependency-audit workflow outputs, when copied/published with the evidence |
| `raw/engine-python-audit.json` | Standalone engine production dependency audit, when copied/published with the evidence |
| `raw/engine-mutation.json`, `raw/engine-mutation.txt` | Optional scoped mutation evidence, copied from the engine's output directory |

Analyser formats retain their own details; the aggregate is not a replacement for their raw reports. Coverage paths from another checkout are normalised for module association, and pytest class-based test names are attributed to their source test file. A shared test can count as evidence for multiple modules; module counts are not additive suite totals.

Freshness requires a recent full-run manifest, matching app/engine Git revisions, and matching source fingerprints. Fingerprints hash tracked and new nonignored inputs while excluding generated quality/documentation outputs. The accepted age is seven days, with a five-minute tolerance for future clock skew. Running `report` again does not make an old raw run fresh. Editing a document or test after collection also makes the earlier evidence stale. Never hand-edit generated JSON or change its timestamp to hide a stale result.

Missing declared test files or skipped scenarios never become a clean module pass. The docs count measures required catalog slots, not the editorial quality or exhaustive correctness of those documents. Read the source documents when reviewing behaviour and invariants.

## Coverage sanity and the changed-line target

JavaScript tests use an instrumented browser-script loader. Coverage includes shared scripts and never-loaded first-party files, which correctly contribute zero hits. `npm run test:coverage` runs Jest and then `scripts/check-js-coverage.cjs`; that check requires every production JS file and actual executed statements and branches. Use [A4.2 JavaScript tests](4.2%20JavaScript%20tests.md) when adding tests.

The full `coverage` sanity gate additionally requires all three app/engine/JS reports, matching source fingerprints, Python branch coverage, complete runtime file denominators, executed production statements in each report and valid count bounds. A green test process with broken instrumentation or missing files must fail this gate.

These are correctness checks on the evidence, not thresholds: no coverage percentage fails a run. The only target concerns changed lines. With a comparison base (`report --base`, see [Command-line reference](#command-line-reference)), `latest.json` records each application module's coverage of its changed lines with an advisory target of 90 %. Falling below it fails nothing, and neither the report nor the dashboard shows it.

Coverage measures execution, not correctness. A high percentage does not replace publication rollback, invalid-input, concurrency or contract scenarios. For a one-off look at backend coverage, run `python -m pytest tests --cov=backend --cov-branch --cov-report=term-missing`; it does not produce a supported quality report.

For optional engine mutation evidence, run its documented `quality-mutation` command, retain the selected target and provenance, and copy `engine-mutation.json` into app `quality/raw/` after the full run, then regenerate the report. The sample is checked against its source and test hashes and seven-day age limit. Only `engine.result-producer` consumes this scoped report; it must not be presented as mutation coverage of the entire engine. A subsequent full run clears the copied raw file, so archive it before rerunning.

## Structural debt and exceptions

The clone gate uses jscpd at a minimum of 10 lines and 70 tokens. Vulture reports only 100%-confidence Python findings. These tools identify duplication and certain unused or unreachable candidates; unexecuted coverage is not proof of dead code, and browser-global reachability is not measured. The report's **Python dead code** column uses the analysed Python file inventory recorded in `raw/debt.json`. Modules with no analysed Python files are **not applicable**, without a zero-findings claim; without that inventory the column is **not measured**. Each measured lane identifies Vulture and its 100% minimum confidence, so this column makes no JavaScript or CSS reachability claim.

Baseline identities include content and participating files. Distinct physical occurrences are counted: adding another identical copy within an already baselined file pair still creates a new finding. Ordinary line movement does not change the content identity, but editing the code inside an accepted clone does: the edited clone is reported as new and its baseline entry matches nothing. Deleting one clone does not buy permission for a different new clone.

When the gate reports a new finding, read both copies in `raw/debt.json` and decide:

- **Refactor** when both copies do the same job in one repository: move the shared code into one function and let the finding disappear.
- **Accept** when the duplication is intentional, such as the bundle contract validated independently by the app and the engine, or when an accepted clone only changed content: re-record the baseline as below.
- **Except** when a real duplicate must stay for now: add an expiring entry to `exceptions.json`, as below.

To re-record the baseline after removing or accepting findings, run:

```bash
python scripts/quality.py debt
python scripts/quality.py debt --write-baseline
git diff -- quality/baseline.json
```

Review the resulting JSON, confirm it reflects intended removals, and rerun the normal `debt` command. Do not refresh the baseline merely to make an unexpected failure disappear. Producer/consumer validation can intentionally duplicate a wire contract across independent repositories; sharing app/engine implementation imports would violate the boundary. Review the responsibility before extracting an abstraction.

If a specific new finding must temporarily remain, append an entry to `quality/exceptions.json` using its exact ID from `raw/debt.json`:

```json
{
  "module": "app.snapshot-publication",
  "finding": "REPLACE_WITH_EXACT_FINDING_ID",
  "owner": "Maintainer responsible for the follow-up",
  "reason": "Concrete reason and link/reference to the removal work",
  "expires": "YYYY-MM-DD"
}
```

The example is a template, not valid dates or IDs to copy unchanged. The actual file is a JSON array. Supply a real future ISO date and an affected module; validation rejects unknown modules and expired entries, and the debt gate requires the exception's module to participate in that finding. Exceptions are visible in the aggregate. They do not waive tests, coverage collection, syntax or security checks. An excepted structural finding may still need attention in the module table; the exception records why it is temporarily permitted.

## Code maps and context packets

The map joins module ownership, files, tests, documents, Python imports and calls, browser-script globals, template script order and declared contracts. The [dashboard](4.3%20Code%20Quality.md#read-the-dashboard) draws it at module, file and function level. Use `context` before changing a critical module, then `impact` or `symbol` to inspect a small neighbourhood. The JSON is generated on demand.

Edges carry provenance. `static-exact` describes parsed ownership, import and script syntax; it is not a promise about all runtime resolution. `static-heuristic` marks inferred calls and JavaScript symbol uses. `declared` relationships come from catalog dependencies, documentation/test associations and contracts. The builder does not generate runtime-observed call graphs, complete dynamic dispatch, or every cross-language fetch or database relation. Test associations are catalog declarations, not proof that every test executes every owned symbol.

## Troubleshooting and review workflow

| Symptom | What to check |
|---|---|
| Unsupported Python/Node or missing package | Use the supported versions with `requirements.txt` and `requirements-dev.txt`, or rebuild/run the container |
| Engine catalog missing | Set `ENGINE_DIR` to a quality-enabled checkout and update `engine.ref` |
| App interpreter contains `osm_public_transport_matcher` | Recreate an isolated app environment; use `ENGINE_PYTHON` for engine tests |
| PostGIS test missing/skipped | Use `make quality` or provide a dedicated `TEST_POSTGRES_URI`; SQLite does not establish publication safety |
| Coverage all zero or missing JS files | Use `load-browser-script`, keep production roots included in Jest, and run the coverage sanity command |
| Unexpected console/error or leaked timer | Fix the cause or lifecycle cleanup; assert expected errors only within their test, as shown in the JS guide |
| New clone/dead-code finding | Inspect `raw/debt.json` and analyser locations before considering a reviewed baseline/exception change |
| Report remains partial after passing tests | Inspect which measurements are unavailable; security is not measured per module, so `partial` alone is not a failure |
| Report is stale immediately after collection | Check concurrent edits, engine revision and dependency/image changes; rerun once inputs are stable |
| Dashboard or Code quality page shows a stale warning | The running code differs from the measured commit; run `make deploy-report` after CI passes and deploy again |

Before requesting review, follow the checklist in [Contributing](Contributing.md#before-requesting-review).
