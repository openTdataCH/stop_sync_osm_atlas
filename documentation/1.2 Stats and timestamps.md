# A1.2 Statistics and timestamps

The website shows statistics and dates about the published dataset: match rates, problem counts, when the sources were downloaded and when the data was last updated. This page explains where each value comes from. In short, the engine records facts about its run in the bundle, and the review application derives its analytics files from the bundle and its own database after each publication.

## What the bundle provides

Every bundle's manifest carries, in `metadata`, a summary of counts, the complete dataset profile, the capabilities and a fingerprint of every input file. The Swiss integration adds its acquisition record: which sources were downloaded, when, and with which validators. The `quality_metrics` extension holds the engine's matching-quality summaries; the optional `gtfs_atlas_stats` and `atlas_filtering` extensions hold the Swiss GTFS identity and ATLAS filter statistics. The engine writes all timestamps in UTC.

## What the application derives

After the switch, the publication step (`publish.analytics`) writes these files under `data/`:

| File | Written by | Holds |
|---|---|---|
| `data_meta.json` | `record_bundle_metadata()` in `backend/services/data_meta.py`, and the job runner | The active `run_id`, the bundle's capabilities, the source acquisition times, the time the data was last updated, the result schema version |
| `stats.json` | `export_stats_after_import()` in `backend/importing/importer.py` | The analytics of the published snapshot, described [below](#the-sections-of-statsjson) |
| `gtfs_atlas_stats.json` | The importer | The GTFS identity statistics, for the GTFS identity map |

`stats.json` combines values exported by the engine with counts the application queries from its own database; it never recomputes spatial matching. `backend/services/stats_export.py` builds the matching sections and the [statistics PDF](2.5%20Generate%20Reports%20and%20PDFs.md); `backend/services/dataset_stats.py` builds the per-source sections from the published tables only, so `scripts/regenerate_stats.py` can refresh them without the bundle. The documentation pages read `stats.json` through `{{stat:…}}` placeholders, such as the key statistics of the [project overview](0.%20Intro.md#key-statistics).

`dataset_publication.manifest` in the database records the published run within the switch transaction, so it stays correct even if writing these files fails afterwards. In that case the run ends as "published with warnings" and the files can be regenerated.

## The sections of stats.json

`/data/analytics` and the statistics PDF show these sections in this order.

| Section | Keys | Source |
|---|---|---|
| Stop matching | `summary`, `matching_stages`, `quality_metrics` | The bundle's matches and the engine's quality metrics |
| Unmatched | `unmatched_analysis` | The bundle's unmatched records |
| Route matching | `route_links` | `line_families`, `itineraries` and their matches |
| Problems | `problems` | `problems` and `stops_matched` |
| ATLAS stops | `atlas_stops`, `atlas_filtering` | `atlas_stops`; the engine's ATLAS filter counts |
| Swiss GTFS | `gtfs`, `gtfs_atlas` | `gtfs_stop_identity_resolution` and the GTFS side of the route tables; the engine's GTFS identity statistics |
| OSM stops | `osm_stops` | `osm_nodes`, `osm_stops`, `osm_stop_members` |
| OSM routes | `osm_routes` | `osm_route_relations` and the OSM side of the route tables |

Each figure names what it counts:

- An OSM **element** is one active node or way tagged as a stop. Elements with a lifecycle prefix, such as `disused:`, are counted apart.
- An OSM **stop unit** is one single element, or one pair or trio grouped as one physical stop ([E2](../engine/documentation/2.%20Matching%20process.md#osm-grouping-before-the-rules)). It counts as matched when one of its elements is matched. An unmatched trio middle between two matched sides counts as matched.
- A **line** is a GTFS route, or an OSM route master or group of relations ([E3.2](../engine/documentation/3.2%20Route-Route%20Matching.md#step-1-build-the-families)). An **itinerary** is one stop pattern: one per distinct GTFS stop sequence, one per OSM route relation.
- A **matched pair** is one link between an ATLAS platform and an OSM element; one platform can have several.
- An ATLAS platform or OSM element is **isolated** when it is unmatched and nothing from the other source lies within 50 m.

Lines and itineraries are linked one to one, so one link count describes both sides; the coverage on each side is the share of its lines that are linked. OSM route figures count public transport relations only ([E1.3](../engine/documentation/1.3%20OSM%20data.md#which-route-relations-are-services)).

## Time zones

The engine and the pipeline status store use UTC (ISO 8601), and the browser converts status times to the viewer's local time. The Swiss presentation formats data-update and source dates in Europe/Zurich time with `backend/services/time_utils.py`; the presentation time zone never affects matching.
