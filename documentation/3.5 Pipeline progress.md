# A3.5 Pipeline progress

The Data page (`/data/analytics`) shows the progress of a pipeline run live, without the review application knowing how the engine works inside. The engine describes its own stages; the application merges them with its own into one versioned **stage plan**, and records the state of each stage under a stable ID. This page describes that model, the order of the phases, the rules at the engine boundary, the timestamps and how the browser displays them. [A3.3](3.3%20Background%20scheduler.md) describes how runs are started, in which modes, and how a dead run is detected.

## Data model

`backend/services/pipeline_progress.py` defines the eight top-level phases and the application's own stages for loading and publishing the database. The separately installed engine sends a plan of its stages, each with its own label and description. `backend/services/pipeline_status.py` validates and merges both plans into the persisted status:

```json
{
  "progress_schema_version": 2,
  "stage_plan": [
    {
      "id": "database.validate",
      "parent_id": "database",
      "phase": "database",
      "label": "Validate the result bundle",
      "description": "Verify the bundle schema, checksums and entity references.",
      "order": 10,
      "progress_kind": "indeterminate"
    }
  ],
  "stage_states": {
    "database.validate": {
      "status": "complete",
      "started_at": "2026-09-21T10:00:00+00:00",
      "finished_at": "2026-09-21T10:00:02+00:00",
      "duration_seconds": 2.0
    }
  }
}
```

A stage is `waiting`, `running`, `complete`, `reused`, `skipped` or `failed`. A stage of kind `determinate` may also report `processed` and `total`; the UI never invents a percentage for indeterminate work.

## Execution order

The phases follow the processing order. They describe the work a user can see rather than process boundaries. The engine performs the first six; the application's importer performs the last two.

| # | Phase | ID | Work |
|---|---|---|---|
| 1 | Check sources | `source_check` | Probe ATLAS and GTFS freshness and prepare the geographic boundary |
| 2 | Prepare source files | `source_files` | Download and filter or reuse ATLAS, download and extract or reuse GTFS, prepare timetable patterns, identities and routes, then download the current OSM extract |
| 3 | Load matching inputs | `matching_inputs` | Read ATLAS stops and cached timetable products, optionally prepare a supplied GTFS feed, then parse OSM stops, route relations and evidence |
| 4 | Stop matching | `stop_matching` | Group OSM stops, run the stop-matching rules and detect stop problems |
| 5 | Route matching | `route_matching` | Normalize and compare line families, itineraries, directions and stop sequences |
| 6 | Build result bundle | `bundle` | Record fingerprints and quality metrics, write and compress the result, write checksums and validate the bundle |
| 7 | Stage database | `database` | Validate the bundle independently, prepare application rows, load an isolated PostgreSQL schema and build indexes, while readers keep using the published snapshot |
| 8 | Publish dataset | `publish` | Switch the staged tables into public view in one transaction, generate statistics and update the publication metadata. This publishes data; it does not deploy the website |

The engine's stages within phases 1 to 6 are listed in [E5.3](../engine/documentation/5.3%20Pipeline%20progress%20contract.md#public-engine-stages); the application's stages are listed [below](#application-stages).

The stages within a phase run in the order shown. A stage served from cache is marked `reused` in place. `match-import` skips the source check, reuses the source files and then loads the inputs normally. `import` skips acquisition, input loading and matching, and reuses the existing bundle.

This is progress schema version 2. Live events of another version are rejected. When the version changes, update the engine, the scheduler and the web application together, between runs. The result bundle format does not depend on it.

## Application stages

| Parent | Stable ID | Label |
|---|---|---|
| Stage database | `database.validate` | Validate the result bundle |
| Stage database | `database.prepare` | Prepare application records |
| Stage database | `database.load` | Load and index the staged database |
| Publish dataset | `publish.swap` | Publish the new dataset |
| Publish dataset | `publish.analytics` | Generate analytics |

The import functions receive an optional callback for stage events. The events carry no `progress_schema_version`: the runner's callback in `backend/jobs/job_runner.py` stamps the current version before recording them, so the importer does not depend on the progress schema. Reporting is best effort: an exception in the callback is logged, and can neither abort the work nor hide the work's own exception. `publish.swap` finishes only after its transaction has committed, and the cleanup after it depends on the committed result even if reporting fails.

A failure to generate statistics is reported, not hidden. The importer then raises `PublishedDatasetError` with the committed manifest. The runner keeps the publication, records the data-update timestamp and finishes with `dataset_published: true` and non-empty `warnings`. The page shows "Dataset published with warnings" and does not claim that the statistics were generated. Such a run does not advance `last_success_at`.

Input warnings that the engine records in the bundle's `metadata.warnings`, such as a missing ATLAS column, come first in the same `warnings` list and lead to the same message.

## Engine boundary

The runner copies every line the engine prints, standard error included, to the scheduler log, and reads the lines as JSON. A version-2 progress event is validated completely before a pure transition function turns it into one stored update. JSON without a progress version, such as the engine's log lines about cache decisions, is diagnostic output and never changes what the UI shows. An invalid event is logged and ignored: it neither changes the plan nor stops the reading of the engine's output.

The engine can add a stage without any change to the application, because the plan carries its label, description, parent and order. A conflicting definition for an existing ID is rejected during a run, and an unknown schema version is rejected rather than guessed.

Cache and run-mode outcomes stay explicit. When a whole phase is marked `reused` or `skipped` before the engine's plan arrives, its stages inherit that outcome.

Engine events may describe only stages below the engine's own phases, never a top-level phase or the database and publication work. Numbers must be finite and non-negative, counts must be integers, and a supplied `stage_spec.id` must equal `stage_id`. Definitions cannot conflict, and a plan cannot repeat an ID.

## Lifecycle and persistence

`pipeline_progress.apply_progress_event(current, payload, now)` computes stage transitions without any I/O. `project_stage_states` derives the state of each phase from its stages and from the runner's phase. The browser uses these phase states instead of assuming that every earlier phase succeeded. A phase's duration is the sum of its stages' work. Preparing source files finishes before loading matching inputs begins; reuse and skip decisions take no work time.

The runner binds events to its run ID. The store checks that ID and the active-run state again under its write lock. A finished run ignores late updates; a completed or failed stage ignores repeated events and delayed heartbeats. An explicit start may replace an earlier reuse or skip decision, but completed or failed work is never silently restarted.

When a run fails, running stages are marked failed and stages that never started are marked skipped with a reason; finished work keeps its state. `finish_failure()` stores the error of the first failed stage that reported one as `last_error`, prefixed with the stage label, the stage ID as `failed_stage` and the active phase as `failed_phase`. The runner's own error, `The matching engine exited with code N`, is used only when no stage reported a cause; the engine command and its exit code stay in the scheduler log. A successful exit with unresolved stages produces warnings instead of invented completion. A new run resets the plan, the stages, the publication flag and the warnings. A lifecycle event that carries its own definition can still add a stage that the initial plan missed, under the same validation rules.

## Timestamps

The status store records every stage event with a UTC ISO 8601 timestamp; the browser shows it in the viewer's time zone. Reused and skipped stages are recorded as events with zero duration, so every stage has a time without pretending that cached work took time. `phase_history` records each phase the run has left, with the same fields; a cache decision looks like this:

```json
{
  "phase": "source_files",
  "started_at": "2026-09-21T14:18:23.100000+00:00",
  "finished_at": "2026-09-21T14:18:23.100000+00:00",
  "duration_seconds": 0.0,
  "status": "reused"
}
```

The other timestamps of the status record mean different things:

| Field | Meaning |
|---|---|
| `started_at` | Start of the whole run; never changes during the run |
| `phase_started_at` | Start of the active phase; cleared when the run ends |
| `phase_history[].started_at` / `finished_at` | Measured boundaries of completed, failed, reused or skipped phases |
| `updated_at` | Last write of the run state; neither a phase boundary nor proof of liveness |
| `finished_at` | End of the run, successful or failed |
| `last_success_at` | End of the most recent successful run without warnings |
| `last_pipeline_data_import_ended_at` | Publication time used by the statistics snapshot |
| `schedule_updated_at` / `next_run_at` | Scheduler metadata, independent of any run |
| Lease `acquired_at` / `heartbeat_at` / `expires_at` | Lease ownership and health ([A3.3](3.3%20Background%20scheduler.md#detecting-a-dead-runner)); never used as stage times |

## Browser rendering

### Polling and the navbar

Every page polls `/api/system/pipeline_status`: every 10 s when idle, every 1.5 s during a run. A failed or timed-out request keeps the last status until the next poll. The navbar is rendered with the current state on the server, so a run in progress is visible before the first poll.

Every status read also derives `data_warning`, which the navbar shows as an amber dot before `Data updated`, with the text as its tooltip:

| Condition | `data_warning` |
|---|---|
| The latest run failed before publishing | `Latest update failed; showing data from <time>`, or `…; no data is published yet` |
| The publication is older than twice `schedule_interval_hours` | `No update for more than <hours> hours; showing data from <time>` |
| Otherwise, or before the scheduler has recorded its interval | None; the dot is hidden |

The value is derived, never stored, so it appears as the data ages, without a writer.

### The pipeline card

The pipeline card on the Data page does not depend on the published statistics. It stays visible during the first run of a new deployment, when `stats.json` does not exist; the notice about missing statistics appears below the card until statistics exist.

When a stage reported the failure of a run, the card shows the first line of its error, and below it the stage, its phase and when it failed; the full error is the message's hover text. Otherwise the card shows `last_error`.

### The timeline

`static/js/pages/data-analytics.js` takes the phases of the timeline from `stage_plan` and keeps both the timeline and the stage lists in step with it; a new run's plan replaces the displayed one without a page reload. The time below each phase is:

| Phase state | Time shown | Duration |
|---|---|---|
| Running | `phase_started_at` | Browser clock minus the phase start, refreshed every second |
| Completed or failed | The start of its first stage, or the history entry's `started_at` for a phase without stages | The sum of its stages' durations, or `finished_at - started_at` for a phase without stages, calculated by the backend |
| Reused | When the cache decision arrived | `0`; the UI says `Reused` instead of `0s` |
| Skipped | When the mode decision was recorded | `0`; the UI says `Skipped` instead of `0s` |
| Waiting | None | None |

How the timeline behaves:

- Completed phases show a green check, the active phase a spinner, and phases that have not started stay empty at their minimum width on the right.
- The active phase's elapsed time and width update in the browser every second, without waiting for the next poll.
- A completed phase keeps its measured duration as its weight; the active phase gains one unit per elapsed second. As a later phase runs, earlier phases take a shrinking share of the bar and their boundaries move left.
- After a successful run, all phases use their measured durations. Without duration data, the template's fixed proportions are used.
- A failed phase stays visually distinct, and the phases before it keep their measured proportions.
- Labels stay within their segment and end with an ellipsis when they do not fit; the full name appears on hover and keyboard focus. Narrow screens use two columns instead of overlapping labels.
- Each time has a hover text such as `Started at`, `Reuse decided at`, `Skip decided at` or `Stopped at`, with the full local date and time.

The timeline shows elapsed time, not an estimate of the remaining time. `processed`, `total` and `eta_seconds` may appear in status text, but never set a stage's duration.

Hovering over a timeline segment or focusing it with the keyboard highlights the segment and its stage card. After a short hover pause, the page scrolls smoothly toward an off-screen card, accounting for the sticky navigation. Keeping the timeline visible takes priority: scrolling stops when the bar reaches the top inset, even if the card cannot fully fit below it. Visible cards do not trigger scrolling, and progress refreshes do not repeat it. The highlight follows the phase ID, survives progress refreshes, and clears when hover or focus leaves. Reduced-motion preferences disable smooth scrolling and highlight transitions.

### Stage cards

Card summaries say "N/M finished", counting completed, reused and skipped stages, while each stage keeps its own status.

Every stage of the run is listed from the start: pending work is grey, running work blue, completed or reused work green and failed work red. Completed stages stay visible during later phases and after the run. Reused work is marked with the three-arrow recycling symbol. Descriptions appear as native titles, while state and elapsed time remain visible text.

The script creates DOM nodes and assigns text instead of inserting HTML from an event. Nodes whose content is unchanged are kept, so selection and focus survive polling. Phases and stages that arrive late are inserted in plan order; unchanged nodes are not moved on each poll. IDs are treated as opaque strings, never as CSS selectors.

## Test strategy

- Catalog tests validate unique IDs, metadata, ordering and parent references.
- Pure transition and state-service tests cover malformed input without writes, ownership, late events, interrupted runs, mixed cache outcomes and storage run guards.
- Import tests use real bundle validation/projection and exercise explicit analytics failures and broken reporting callbacks.
- Engine tests run tiny CLI examples and assert progress alongside real cold/warm/corrupt-cache behaviour.
- Jest tests cover late plans, reordered children, retained nodes/focus, opaque IDs, terminal parent states and publication warnings.
- PostGIS tests verify that completion observes the committed publication, lock timeouts emit failure, and a broken reporting callback cannot alter commit or cleanup.
- `tests/test_engine_import_contract.py` replays the events of real Swiss, explicit-GTFS and generic GTFS CLI runs through the application's consumer, then publishes each bundle into PostGIS. It runs in the app suite of `make quality` and CI, which supply `ENGINE_PYTHON`; ordinary test runs skip it and need no engine.

Tests do not assert exact times, heartbeat counts or row totals of the national dataset: those are operational data, not stable behaviour.
