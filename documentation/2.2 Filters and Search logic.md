# A2.2 Filter and search logic

This page defines what the map's filters and search mean. The same definition applies to every filtered request: the viewport data (`/api/data`), the summary statistics (`/api/global_stats`), the random stop and the Top N overlay, so the markers and the counts always describe the same set of rows. Rows are entries of `stops_matched`: a matched pair, an unmatched ATLAS platform, an unmatched OSM element or a [disused OSM element](0.5%20Glossary.md#disused-osm-element) ([A1](1.%20Database.md#stops-and-identities)).

This page says which rows a filter selects. What a matching rule, an OSM group or a problem type is, the engine documentation explains, and an info icon beside the **Matched**, **OSM Groups** and **Problems** filters opens it: [the matching rules](../engine/documentation/2.%20Matching%20process.md#the-matching-rules), [OSM grouping](../engine/documentation/2.%20Matching%20process.md#osm-grouping-before-the-rules) and [stop problems](../engine/documentation/4.1%20Stop%20Problems.md).

## The core rule

The filter system uses one boolean grammar only:

- within a filter group, selected values combine with `OR`
- across filter groups, active groups combine with `AND`

Formally:

`FinalResult = ScopePredicate AND SearchPredicate AND AtlasPredicate AND OsmPredicate AND DuplicatePredicate AND ProblemPredicate`

If a predicate group has no active selection, it contributes no restriction.

## Scope predicate

The scope predicate chooses which row categories are eligible.

`ScopePredicate = MatchedBranch OR AtlasUnmatchedBranch OR OsmUnmatchedBranch OR OsmDisusedBranch`

With no branch selected, the scope adds no restriction, so every row is eligible, disused elements included.

### Matched branch

Matched entries can be enabled in two ways:

- `All Matched Stops`
- one or more matching rule sub-filters

Semantics:

- `All Matched Stops` means rows with effective matched scope are included
- selecting matched sub-filters means matched rows with one of their match types are included
- if all matching rule children are selected, the UI rolls up to the parent state `all`

Formally:

- `MatchedBranch = stop_type = matched OR stop_type = effectively_matched` when the parent is `all`
- `MatchedBranch = stop_type = matched AND match_type IN selected match types` when the branch is in `subset` mode

A `match_method` value is either a matching rule key, which selects every match type of that rule, or a single match type. `backend/services/matching_rules.py` lists the rules in run order with their match types; the Matched dropdown sends:

| Group | Value | Selects the match types |
|---|---|---|
| Identifier matching | `identifier` | `sloid_identifier` |
| | `two_sided_stop` | `uic_two_sided_stop` |
| | `reference` | `uic_reference_one_osm`, `uic_reference_local_ref`, `uic_reference_one_source` |
| | `name` | `name_one_osm`, `name_local_ref` |
| GTFS route matching | `gtfs_shared_route` | `gtfs_shared_route` |
| | `gtfs_shared_direction` | `gtfs_shared_direction` |
| Distance matching | `group_distance` | `uic_ref_group_distance`, `uic_name_group_distance`, `name_group_distance` |
| | `group_long_distance` | the same three with `_group_long_distance` |
| | `local_ref_distance` | `local_ref_distance` |
| | `distance_only_candidate` | `distance_only_candidate`, `distance_only_candidate_second_pass` |
| | `distance_ratio` | `distance_ratio` |

The backend turns the selected values into one `match_type IN (...)` condition. An unknown value selects nothing.

Special case: `two_sided_stop` also includes `effectively_matched` rows, the middles of two-sided stops whose sides are matched, because those rows have no direct `match_type` but are treated as matched for map and stats semantics.

### ATLAS unmatched branch

ATLAS unmatched entries also support a parent state plus sub-filters.

Semantics:

- `ATLAS unmatched` means all atlas-unmatched rows are included
- selecting `No OSM < 50m` and/or `OSM < 50m` means only those unmatched reasons are included
- if both unmatched reasons are selected, the UI rolls up to the parent state `all`

Formally:

- `AtlasUnmatchedBranch = stop_type = atlas_unmatched` when the parent is `all`
- `AtlasUnmatchedBranch = stop_type = atlas_unmatched AND unmatched_reason IN selected reasons` when the branch is in `subset` mode

The unmatched reason mapping is:

- `No OSM < 50m` -> `match_type = no_nearby_counterpart`
- `OSM < 50m` -> `match_type != no_nearby_counterpart OR match_type IS NULL`

### OSM unmatched branch

This branch is explicit only.

Semantics:

- if `OSM unmatched` is checked, all `osm_unmatched` rows are included
- if it is not checked, OSM-unmatched rows are not added implicitly by any other selection

Formally:

- `OsmUnmatchedBranch = stop_type = osm_unmatched`

### OSM disused branch

The `OSM disused` checkbox in the Unmatched dropdown (`#masterDisusedOsmCheckbox`) selects [disused OSM elements](0.5%20Glossary.md#disused-osm-element) and shows the chip "Disused OSM". Like the OSM unmatched branch, it is explicit only: when another branch is selected and this one is not, disused rows are excluded.

Formally:

- `OsmDisusedBranch = stop_type = osm_disused`

`/api/global_stats` is stricter: it leaves disused rows out unless this branch is selected ([A2.3](2.3%20Global%20Stats.md#request-filtering)).

## Search predicate

Search tokens are OR-combined within the search group.

`SearchPredicate = token_1 OR token_2 OR token_3 ...`

Meaning:

- if multiple search tokens are active, a row matches if it matches any of them
- a stop ID or OSM ID token keeps the row with exactly that identifier: `ch:1:sloid:10035:0:1` does not keep `ch:1:sloid:10035:0:1955`
- a UIC token keeps the rows whose ATLAS platform has that number, and the rows whose OSM element lists it in `uic_ref`, alone or among `;`-separated values: `8500819` keeps Saanenwald, tagged `uic_ref=8530279;8500819`

### Accepted formats

The search input (`#smartSearchInput`) accepts a stop name ([Names and suggestions](#names-and-suggestions)) or one of the following identifiers, parsed by `parseSmartSearchInput()` in `filters.js`:

| Format | Example | Token kind | Backend `identifier_type` |
|---|---|---|---|
| Configured source identifier | `source:agency/stop:123` | `atlas` | `sloid` |
| UIC station code (seven digits starting with `85`, optionally followed by `:<digits>`) | `8503000` | `station` | `station` |
| ATLAS SLOID | `ch:1:sloid:3000:501:33` | `atlas` | `sloid` |
| OSM node ID (digits only) | `123456789` | `osm` | `osm_node_id` |
| Route ID (dash-separated or `route:` prefixed) | `11-T-j25-1` | `route` | `route` |
| Route + direction | `11-T-j25-1 dir:0` | `route` | `route` |

Input that is no identifier is searched as a name. When no stop has that name either, the box says so and shows the accepted formats hint (`#smartSearchHint`).

`source:` accepts arbitrary source identifiers, including IDs containing spaces or numeric IDs that would otherwise be interpreted as OSM/UIC identifiers. The token kind `atlas` and the identifier type `sloid` serve every configured source; the displayed source and ID labels come from `ReviewConfig`. The Swiss shortcuts are always accepted, but their hints are only shown for the GTFS identity capability. Route search is rejected when `capabilities.routes` is false, and route hints/actions are hidden.

OSM node IDs may also be entered as `node/123456789`. Route input accepts `dir:0` or `dir:1`; the token stores the direction for subsequent filtered requests, while the initial centering lookup validates the route ID itself.

### Names and suggestions

From the second character typed, a list under the box suggests stops whose name or number matches the text, from `/api/search/suggest?q=` (`backend/services/stop_suggest.py`, drawn by `static/js/components/search-suggest.js`). Each suggestion shows a name, its number and its source:

- **A station** of the official dataset: the platforms that share a UIC number, shown with that number and how many platforms it has. A platform without a station number is its own entry, shown with its stop ID.
- **An OSM element without a match**, shown with its OSM ID and "no match" or "disused". An unmatched element that carries the UIC number of a station is not listed apart: its name is one of that station's names.

A station is also found under the OSM names of its matched elements and of the unmatched elements that carry its number. The suggestion then names the OSM name that matched, for example *Zürich HB · OSM name: Zürich Hauptbahnhof*.

Names are compared without case, accents or punctuation, so `zurich hb` finds *Zürich HB* and `saint imier` finds *St-Imier* through its OSM name *Saint-Imier*. The best eight suggestions are listed in this order:

1. The name or number is the text.
2. The name or number starts with the text.
3. Every word of the text starts a word of the name, in any order: `bahnhof bern` finds *Bern, Bahnhof*.
4. The name contains the text (three characters or more).

Within a step, stations come before OSM elements and a station's own name before its other names; then stations found by number are ordered by number, and names by length, so *Zürich HB* comes before *Zürich HB SZU*.

Picking a suggestion, with the mouse or with the arrow keys and Enter, adds the same filter as typing its number: a station adds a UIC filter, a platform its stop ID and an OSM element its node or way ID. Enter without a choice picks the first suggestion, unless the text is an identifier: `8503000` and `node/123` are searched as typed. A dashed text such as `Saint-Imier` may be a name or a route ID; it is searched as a name first and as a route ID when no name matches, and `route:` makes it a route ID.

Chips of these filters show the stop's name before its identifier, for example *Zürich HB · UIC: 8503000*, whether the stop was picked from the list or typed by its identifier.

The suggestions come from an index of every station and unmatched OSM element of the published snapshot. Each web worker builds it on the first request after an import and keeps it until another snapshot is published.

### Search flow

1. User submits input via Enter key, or picks a suggestion
2. `parseSmartSearchInput()` classifies the value into a token kind or returns a validation error; a name takes the first suggestion's token
3. `addSearchToken()` adds the token to `activeFilters.station` and calls `fetchAndCenterSpecificStop()`
4. `fetchAndCenterSpecificStop()` calls `/api/stop_by_id` with the identifier and type
5. On success: the map moves to the result and filters update. SLOID and OSM node searches open the stop's popup and place the stop two thirds down the map, so the popup fits above it; UIC and route searches open no popup and centre the stop ([A2.1](2.1%20Map%20Data%20Loading%20and%20Rendering.md#stop-popups))
6. On failure: the token is reverted and an error is shown

### Not-found feedback

When a correctly formatted input does not match any database entry, `/api/stop_by_id` returns a 404. The frontend displays an error in the `#smartSearchError` element, styled via `.smart-search-feedback` in `static/css/components/shared-filters.css`.

The error message follows the pattern: `No {type} found matching: {identifier}`, where `{type}` is the human-readable token kind (e.g. "OSM node", "UIC station", "ATLAS SLOID").

### Route filters and their variants

A route token keeps the rows that have a side among the stops of a line. The line is every ATLAS and OSM [line family](0.5%20Glossary.md#line-family) the route ID names, plus the families linked to them (`get_stops_for_route()` in `transport_routes.py`). Its stops are those of all their [itineraries](0.5%20Glossary.md#itinerary), or only one direction's.

The route chip's dropdown chooses how much of the line to keep:

- **Both directions**, or **Direction 0** or **1** (*all variants*): every variant, or one direction's. The chip shows *Both*, *Dir: 0* or *Dir: 1*.
- **A variant**: exactly the stops of that variant. The variants come from `/api/routes/variants?route_id=` when the dropdown first opens, each listed under its direction. The variants the engine paired come first, as one entry, then those left unpaired. An entry shows the variant's name once, with `->` drawn as `→`, and an **ATLAS** and/or **OSM** tag for the sources it keeps. When a pair's OSM name differs, it appears below in grey. The chip then shows the name, followed by *· ATLAS only* or *· OSM only* for one source; its tooltip names both sides.

A variant narrows the line to its itineraries' stops, whatever their direction. The kept rows are the `stops_matched` rows with a side among those stops, so each stop's match appears too, even when no variant of the filter calls at it. The two platforms of Zürich Selnau, for example, appear with the platform each is matched to. A selection whose keys name no itinerary keeps no stop; it never widens to the whole line.

Variants are named with the route lists' keys: the ATLAS itinerary id (`atlas_variant`) and the OSM route relation id (`osm_variant`). An ATLAS key is looked up exactly, then with the timetable year ignored. A link to the main map can name them ([A2.9](2.9%20Permalinks.md#map)); the routes page's variant maps link to the main map this way.

## ATLAS predicate

ATLAS-side attributes are OR-combined within the ATLAS predicate group.

`AtlasPredicate = atlas_attribute_1 OR atlas_attribute_2 OR ...`

ATLAS attribute filters:

- ATLAS operator

Semantics:

- ATLAS predicates are evaluated on every row that has an ATLAS side
- matched rows can satisfy ATLAS predicates
- ATLAS-unmatched rows can satisfy ATLAS predicates
- OSM-unmatched rows naturally do not satisfy ATLAS predicates because they have no ATLAS side

## OSM predicate

The OSM predicate is composed of four subgroups that are AND-combined:

`OsmPredicate = TransportPredicate AND EntityPredicate AND OsmOperatorPredicate AND OsmGroupPredicate`

### Transport predicate

Transport types are OR-combined.

`TransportPredicate = transport_type_1 OR transport_type_2 OR ...`

Examples:

- `ferry_terminal`
- `tram_stop`
- `station`
- `platform`
- `stop_position`
- `aerialway_station`

### Entity predicate

OSM entity types (nodes vs ways) are OR-combined.

`EntityPredicate = entity_type_1 OR entity_type_2 OR ...`

Examples:

- `way` (OSM entries derived from ways, identified by a `way_` prefix in their ID)

### OSM operator predicate

OSM stop operators are OR-combined within their own subgroup.

`OsmOperatorPredicate = osm_operator_1 OR osm_operator_2 OR ...`

The predicate is implemented through `OsmNode.osm_operator` and is AND-combined with the other OSM-side subgroups.

### OSM group predicate (pairs and two-sided stops)

OSM group types are OR-combined. An OSM group is an OSM pair or a PTv2 two-sided stop.

`OsmGroupPredicate = group_type_1 OR group_type_2 OR ...`

Examples:

- `ptv2_pair_uic_ref`
- `ptv2_pair_uic_ref_equal_count`
- `ptv2_pair_name`
- `ptv2_pair_name_equal_count`
- `tram_stop_pair`
- `tram_stop_pair_equal_count`
- `ptv2_two_sided_stop`

If the OSM groups master is selected with no subtype refinement, the system treats it as:

- `OsmGroupPredicate = group_member(any type)`

If only `ptv2_two_sided_stop` is selected, pair rows are excluded.

### OSM-side semantics

OSM predicates always apply to rows that have an OSM side.

This is an intentional product rule.

Consequences:

- matched rows can satisfy OSM predicates
- OSM-unmatched rows can satisfy OSM predicates
- ATLAS-unmatched rows naturally do not satisfy OSM predicates because they have no OSM side

## Duplicate predicate

The only duplicate control is `Duplicate ATLAS`.

Semantics:

- `Duplicate ATLAS` is an AND-filter on ATLAS duplicate-group membership:
	- row has `representative_sloid` set (non-representative member), OR
	- row is a representative referenced by at least one sibling (`EXISTS atlas_stops WHERE representative_sloid = this.sloid`)

Formally:

- `DuplicatePredicate = atlas_duplicate_member = true`

Implementation note:

- duplicate filtering is a data predicate
- this predicate is applied server-side across `/api/data`, `/api/top_matches`, `/api/random_stop`, and `/api/global_stats`
- whether both sides of a matched row are drawn is a rendering decision, not a predicate

## Problem predicate

The **Problems** dropdown keeps the rows that have a problem, as the [Problems page](2.4%20Problems%20Page.md) lists them, so the map shows the problems of the area in view. It has an *All problems* checkbox, one checkbox per problem type, named as on the Problems page, and the priorities P1, P2 and P3. Ticking every type is *All problems*.

Semantics:

- one problem of the row must have one of the chosen types and one of the chosen priorities
- no type chosen means any type; no priority chosen means any priority
- a priority alone keeps the rows with a problem of that priority

Formally:

`ProblemPredicate = EXISTS problems p WHERE p.stop_id = row.id AND p.problem_type IN chosen types AND p.priority IN chosen priorities`

Requests send `problem_type` (`all` or a comma-separated list) and `priority` (for example `1,2`), the names the Problems page uses ([A2.9](2.9%20Permalinks.md#map)). `parse_filter_params()` reads them for `/api/data`, `/api/global_stats`, `/api/random_stop` and `/api/top_matches`, and `has_problem_condition()` in `backend/services/problem_filters.py` builds the condition. The chips read *Problem: Distance* and *Problem priority: P1*.

## Top N distances

Top N is not part of the canonical predicate formula for `/api/data`.

It is a special matched-only mode used by:

- `/api/top_matches`
- `/api/random_stop`
- `/api/global_stats`

The UI shows the Top N control whenever matched scope exists, meaning either:

- `All Matched Stops` is checked
- or at least one matched sub-filter is selected

If matched scope disappears, Top N is automatically disabled.

Endpoint behaviour:

- `/api/top_matches` returns the `limit` matched rows with the largest `distance_m` among the filtered rows, by descending `distance_m`
- `/api/random_stop` and `/api/global_stats` apply `top_n` by narrowing to the `top_n` matched rows with the largest `distance_m`; all three use `top_distance_matches()`
- the main map skips normal `/api/data` viewport loading while Top N is active
- the Top N overlay request is issued by `loadTopNMatches()` only when the matched parent scope is active; with a matched scope of matching rules only, `/api/random_stop` and `/api/global_stats` apply `top_n` all the same

## Low-zoom overview mode

Below the marker threshold and without filters, the map loads a reduced overview that is a display choice, not a filter; [A2.1 Zoom levels](2.1%20Map%20Data%20Loading%20and%20Rendering.md#zoom-levels) describes it.

## Request serialization rules

The frontend sends the active filters (`appendCurrentFilterParams()` in `static/js/pages/main.js`; the Top N overlay builds its own request in `loadTopNMatches()`). The scope, matching rule, OSM, operator, duplicate, problem and Top N filters use the names and values that the map keeps in the address bar, listed in [A2.9](2.9%20Permalinks.md#map), including how a parent checkbox stands for its children. The backend treats any matching rule selection as implying matched scope, so `match_method=reference` works even if `stop_filter=matched` is omitted.

Search tokens are sent as parameters that the address bar does not use (it repeats `search=` instead):

- `station_filter`, `filter_types` and `route_directions`: one entry per token, in the same order; `route_directions` keeps its empty entries (`""` is both directions)
- `route_variants`, for a route token narrowed to variants: a JSON list with one entry per token, `null` or `{"atlas": key, "osm": key}`. JSON, because ATLAS headsigns can contain commas. Malformed input narrows to no stop

## Consistency guarantees

The endpoints below share the same request parameter model for common filters:

- `/api/data`
- `/api/global_stats`
- `/api/random_stop`
- `/api/top_matches`

All four start from one query, `filtered_stops_query()`: the attribute filters (`apply_common_filters()`), the scope (`resolve_stop_type_match_filters`, `build_stop_scope_condition`) and the ATLAS duplicate filter. `/api/data` adds the viewport, and `/api/top_matches` keeps the matched rows with the largest distance. [A2.3](2.3%20Global%20Stats.md) explains how `/api/global_stats` counts the filtered rows.

## Worked examples

Example 1:

`(group distance OR atlas-unmatched OR osm-unmatched) AND operator=SBB AND duplicate_atlas`

This means:

- keep rows in any of those three scope branches
- then require an ATLAS side with operator `SBB`
- then require ATLAS duplicate-group membership

Example 2:

`matched OR osm-unmatched` plus `platform`

This means:

- keep matched rows and OSM-unmatched rows in scope
- then keep only those whose OSM side is `platform`

Example 3:

`operator=SBB` and `tram_stop`

This means:

- require an ATLAS side satisfying `SBB`
- require an OSM side satisfying `tram_stop`
- in practice this mostly yields matched rows because both sides must exist
