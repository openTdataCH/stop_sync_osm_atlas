# Best Option Going Forward

## Is the document correct?
Yes, the mathematical analysis in `5.3.2 Filter math.md` is spot on, and making a distinction between "UI Combinatorics" and "Data Combinatorics" is highly insightful. 

By modeling the filters logically using the scope constraints (`atlas_only`, `osm_only`, vs `atlas+osm`) and measuring the exact data distribution, the document proves that the theoretical combinatorial explosion does not happen in practice. The observation that there are only **2,292 populated data buckets** out of an astronomical theoretical maximum completely validates the shift towards a precomputed data structure. 

## What is the best option going forward (Maintainability-First)?

The absolute best option is to **precompute into a persisted summary table (`global_stats_buckets`) during the data import phase**, and use this table natively via standard parameterized SQL queries on the backend API.

While an in-memory Python dictionary sparse cube provides high compute performance, **a database-backed summary table is vastly superior for long-term maintainability**:

### 1. Avoiding Logic Drift (Single Source of Truth)
Currently, `global_stats` shares UI filter mapping semantic logic with `QueryBuilder` (the same engine that filters map viewport data). If we evaluate subsets in pure Python, we effectively have to recreate `QueryBuilder` logic over dictionary keys. By keeping the target source as a database table, we can abstract the `QueryBuilder` to apply standard SQLAlchemy filtering predicates directly upon the new bucket table, ensuring logic never drifts between the API endpoints.

### 2. Operational Consistency
In-memory data is tied per process. With multiple workers or containers in a potential production deployment, each retains a separate state, leading to complex horizontal-scaling tradeoffs and warmup delays. A Persisted DB table ensures that stats remain entirely stateless and instantaneous for all concurrent backend instances.

### 3. Immediate Observability
If numbers mismatch, attempting to grep through a huge serialized JSON cube payload or logging in-memory dictionary states is an opaque debugging experience. Storing the ~2,300 buckets in an indexed SQL table enables trivial debugging using raw Postgres verification queries.

### 4. Hybrid Query Routing
Not all requests should hit the aggregated cube. A user might use the UI "Smart Search" to filter global stats by a single explicit route ID (`11-T-jXX`). Since our bucket intentionally drops identifying keys (like node ID or exact SLOID) to reduce cardinality, it cannot filter efficiently on these values. By acting as a Query Router, the `global_stats.py` controller can flawlessly query the `global_stats_buckets` natively for large structural UI changes (`SUM()`), while retaining the blazing-fast fallback of dynamically filtering `StopsMatched` for highly selective individual node lookups.

### 5. Deprecating the Cache Mechanism
Because iterating a ~2,000 row SQLite/Postgres grouping is natively evaluated functionally as $O(1)$ compared to a 60,000+ row multidimensional relational aggregate, the brittle `_GLOBAL_STATS_CACHE` mechanism, threading locks, and `collections.OrderedDict` logic in Python can be safely deleted entirely.

## Conclusion
Adopting the **database-first persisted bucket structure** solves all remaining performance bottlenecks for the Global Stats implementation. It combines the absolute performance of pre-aggregation with the architectural security, consistency, and observability of classical relational data models.
