# Filter Logic

This document defines the filtering system used on the index map page.

## Core Model

The effective result set is computed as:

`Result = ScopeFilter AND StationFilter AND NodeTypeFilter AND TransportFilter AND AtlasOperatorFilter AND OsmGroupFilter AND DuplicateFilter`

The important distinction is:

- `ScopeFilter` decides which stop categories are visible.
- All other filters further restrict that set.

If a filter group has no active selection, it contributes no restriction.

## 1. Scope Filter

The scope filter is an OR-combination of the visible stop categories.

`ScopeFilter = MatchedScope OR AtlasUnmatchedScope OR OsmUnmatchedScope`

If none of the three scope branches is active, there is no scope restriction and all stop categories remain eligible.

### 1.1 Matched Scope

Matched entries can be enabled in two different ways:

- `All Matched Stops` checked
- One or more matched sub-filters checked (`Exact`, `Name`, distance stages, route stages)

The semantics are:

- If `All Matched Stops` is checked, all matched rows are included.
- If `All Matched Stops` is not checked, but matched sub-filters are checked, only matched rows with one of those methods are included.
- If both the master checkbox and sub-filters are checked, the master wins semantically: the frontend sends `stop_filter=matched` and does not send matched `match_method` refinements.

Formally:

- `MatchedScope = stop_type = matched` when the master checkbox is on
- `MatchedScope = stop_type = matched AND match_type IN selected matched methods` when only matched sub-filters are on

### 1.2 ATLAS Unmatched Scope

ATLAS unmatched entries work the same way:

- If `ATLAS unmatched` is checked, all `atlas_unmatched` rows are included.
- If the master is not checked, but `No OSM < 50m` and/or `OSM < 50m` are checked, only that subset is included.
- If both the master and reason filters are checked, the master wins semantically and all `atlas_unmatched` rows are included.

Formally:

- `AtlasUnmatchedScope = stop_type = atlas_unmatched` when the master checkbox is on
- `AtlasUnmatchedScope = stop_type = atlas_unmatched AND unmatched_reason IN selected reasons` when only reason filters are on

The reason mapping is:

- `No OSM < 50m` -> `match_type = no_nearby_counterpart`
- `OSM < 50m` -> `match_type != no_nearby_counterpart OR match_type IS NULL`

### 1.3 OSM Unmatched Scope

This scope is explicit only.

- If `OSM unmatched` is checked, `stop_type = osm_unmatched` is included.
- If it is not checked, OSM unmatched rows are not added by any hidden rule.

This is intentional. Selecting ATLAS unmatched no longer implicitly adds OSM unmatched rows.

## 2. Station / Identifier Filters

Station-like search tokens are OR-combined within the station filter group:

- UIC
- ATLAS SLOID
- OSM node id
- Route
- HRDF route

Formally:

`StationFilter = token1 OR token2 OR token3 ...`

That group is then AND-ed with the other filter groups.

## 3. Node Type Filter

When active, node type is an OR-group:

- `atlas`
- `osm`

Formally:

- `atlas` means rows with an ATLAS-side identifier
- `osm` means rows with an OSM-side identifier

`NodeTypeFilter = atlas OR osm`

If no node type is selected, no node-type restriction is applied.

## 4. Transport Type Filter

Transport-type filters apply through OSM-side attributes and are OR-combined inside their group.

Examples:

- `ferry_terminal`
- `tram_stop`
- `station`
- `platform`
- `stop_position`
- `aerialway_station`

Formally:

`TransportFilter = transport_type_1 OR transport_type_2 OR ...`

## 5. Atlas Operator Filter

Selected ATLAS operators are OR-combined within the group.

Formally:

`AtlasOperatorFilter = operator_1 OR operator_2 OR ...`

## 6. OSM Group Filter

The OSM group filters restrict rows whose `osm_node_id` is a member of an `OsmStopGroup`.

Two settings matter:

- `Only grouped OSM members`
- `Include matched entries`

### 6.1 Group Membership

If `Only grouped OSM members` is not checked, no OSM group restriction is applied.

If it is checked:

- with no subtype selected, all OSM group types are allowed
- with one or more subtypes selected, only those `group_type` values are allowed

### 6.2 Scope of OSM-side Filters

`Include matched entries` controls whether OSM-side filters also apply to matched rows.

- If checked: OSM-side filters can match both matched and unmatched rows.
- If unchecked: OSM-side filters are restricted to non-matched rows.

This rule affects OSM group filters and transport filters consistently because both are implemented as OSM-side conditions.

## 7. Duplicate ATLAS Filter

`Duplicate ATLAS` is a simple AND filter:

`DuplicateFilter = has_atlas_duplicate = true`

## 8. Top N Distances

Top N is not a general row filter for `/api/data`.

It is a special matched-only mode used by:

- `/api/top_matches`
- `/api/random_stop`
- `/api/global_stats`

Top N is available whenever matched scope exists, meaning either:

- `All Matched Stops` is checked, or
- at least one matched sub-filter is selected

If matched scope disappears, Top N is automatically disabled.

## 9. Low-Zoom Overview Mode

When the map is below the marker threshold and there are no active filters, the UI deliberately switches to an overview mode:

- `stop_filter = atlas_unmatched`
- `node_type = atlas`

This is not normal filtering semantics. It is a display optimization for the unfiltered overview.

As soon as any user filter is active, normal filter semantics are used again.

## 10. Request Serialization Rules

The frontend sends only the filters that are semantically active.

Important examples:

- `All Matched Stops` checked -> send `stop_filter=matched`, omit matched `match_method` refinements
- `Exact` checked without `All Matched Stops` -> send `match_method=exact`, omit `stop_filter=matched`
- `ATLAS unmatched` checked -> send `stop_filter=atlas_unmatched`, omit unmatched reason refinements
- `No OSM < 50m` checked without ATLAS unmatched master -> send `match_method=no_nearby_counterpart`

This avoids ambiguous requests like `stop_filter=matched&match_method=exact` when the user intent is clearly “all matched”.

## 11. Consistency Guarantees

The shared backend helper now builds the scope condition for:

- `/api/data`
- `/api/global_stats`
- `/api/random_stop`

The shared matched-method helper is also used by `/api/top_matches`, including unified route match variants.

That means the same request parameters now produce the same category semantics across the main map, summary stats, random selection, and Top N results.
