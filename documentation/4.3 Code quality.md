# A4.3 Code quality

This page explains the [code quality dashboard](/quality): the map of both repositories' code, the places it suggests to clean up, and the test and coverage results of the commit the site runs. It also defines the criticality of a module and the statuses of the results. To run the checks yourself or maintain the module catalog, see [A4.4 Running the quality checks](4.4%20Running%20the%20quality%20checks.md).

The **module catalog** (`quality/modules.yml` in each repository) divides the code into modules. A module is a group of files with one responsibility, such as snapshot publication or the query API. The catalog assigns every source file to exactly one module and records the module's criticality, owner, invariants, entry points, dependencies, documentation and tests. The result bundle connects engine and application modules through a declared contract instead of shared code.

The CI run of each commit measures every module and builds the code map. The dashboard shows what CI measured on the commit the site runs: it downloads that commit's file from GitHub, so nothing is committed and no command runs before a deployment. [How the evidence reaches the site](4.4%20Running%20the%20quality%20checks.md#how-the-evidence-reaches-the-site) explains this and what the server needs.

## Criticality

Criticality is a maintained judgment, not a measurement. It answers one question: what would the worst plausible defect in this module do? It never depends on how well the module is tested; do not lower it to accommodate weak tests.

| Criticality | The worst defect in the module | Modules |
|---|---|---|
| `critical` | Publishes wrong, incomplete or lost data, or blocks recovery or deployment | Snapshot publication, schema and deployment, matching core, result production |
| `high` | Shows wrong results or stops data from refreshing, while the published data stays recoverable | Query API, review UI, pipeline orchestration, engine input integrations |
| `medium` | Degrades presentation, documentation or tooling; data and results stay correct | Documentation delivery, styles and assets |
| `low` | Is cosmetic or only affects developer convenience | None |

Criticality raises the documentation a module must have. `critical` and `high` modules must record invariants and an explanation page, and `critical` modules also a reference page; the catalog check fails without them. The report's **Docs** column also expects a decision record for `critical` modules.

## Read the dashboard

From top to bottom, the dashboard at [`/quality`](/quality) shows:

| Part | Contents |
|---|---|
| CI results | The commit that was measured, how many required checks passed, and a link to the checks on GitHub |
| Figures | Counts of modules, files, functions, boundary findings and cleanup candidates; each leads to its section |
| Code map | The code of both repositories on three levels: **Modules**, **Files** and **Functions** |
| Cleanup candidates | Functions nothing mentions, copied code and long files |
| Module boundaries | Dependencies between modules that the catalog and the code disagree on |
| What the map cannot see | The places where reading the code is not enough |
| CI results by module, Required checks | Tests, branch coverage and the other results of each module, and each check of the run |

When GitHub has no results for the running commit yet, the page says so and names the commit; missing results are never shown as a pass. A run of the checks on a developer's computer is shown instead of the CI results and is marked **Local run**. A local map built alone has no results: the page then shows the map and its findings, marked **Map only**.

### The code map

The three levels are one picture, drawn in one style:

- **A circle** is a module, or a file when one module is drawn alone. Its name sits on its top edge.
- **A dot** is a file or a function. Names show on the largest dots first; zooming in names more.
- **Lines** between dots are thin and faint until something is selected.
- **Colour** is the module by default, the same on every level. **Colour by** changes it to criticality, branch coverage or repository.

| Level | What it draws | Size means |
|---|---|---|
| **Modules** | Each module as a filled circle, and one arc for each pair of modules whose code is linked | The circle's area is the module's lines of code |
| **Files** | The same circles in the same places, each holding its files as dots | A larger dot is a longer file; a ringed dot is over 1,000 lines |
| **Functions** | Every function and class as a dot, in module circles piled in the same order: a module rests above the modules it depends on, each repository in its own pile | A larger dot is used by more functions and files; a hollow dot is one nothing mentions |

**Modules.** Each repository is a column. A module sits above the modules it declares as dependencies, so declared dependencies point down. An arc goes from the module whose code uses another module to the module it uses; its number, shown when the arc is selected, counts the code references: imports, imported names, calls, names shared between browser scripts, script loads, HTTP requests from scripts and templates to Flask routes, and templates rendered, extended or included. A link to a page, such as a navbar entry or a `redirect(url_for(...))`, draws nothing, because following a link does not use the page's code. An arc that follows the layering runs down the outer side of its column; one that goes against it runs up the inner side.

| Line | Meaning |
|---|---|
| Solid grey arc | A code dependency the catalog declares |
| Orange dashed arc | A code dependency the catalog does not declare |
| Dotted grey arc | A declared dependency without any code reference |
| Dotted purple, to a diamond | A contract between the repositories, such as the result bundle |

**Files.** Thin lines join files that use each other. Selecting a file lights its own lines, grey inside its module, navy across a declared module dependency and orange dashed across an undeclared one, and lists what it uses and what uses it. A dashed black line joins two files that hold the same block of code; selecting it shows where both copies are. With **Colour by** set to **Branch coverage**, each file has the colour of its own coverage, and files without measured coverage, such as styles and templates, are grey.

**Functions.** Thin lines join a function to the functions it calls or references, in Python and in browser scripts alike. Selecting a function lists its callers and callees. Calls through objects, such as `self.save()` or `this.render()`, are not seen. With **Branch coverage**, a function has the colour of its file.

**Moving between levels.** The column left of the map holds the search box and the module list, which is also the key to the module colours. The list has the order of the map on every level: one repository after the other, parted by a thin line, each from its top module down to the modules everything else depends on.

- **The module in focus** follows you across the levels. Click a module in the list, or the module itself on **Modules**: on **Modules** it stays with its dependencies lit while every other module fades, its files are lit and fitted to the map on **Files**, and it is drawn alone on **Functions**, with a circle for each of its files. Its details are in the side panel. Clicking it again, **Reset**, the first entry of the breadcrumb at the top left, or <kbd>Esc</kbd> gives up the focus.
- **Several modules together.** The box before each module in the list adds it to the modules in focus, as does a click on its name with <kbd>Ctrl</kbd>, <kbd>⌘</kbd> or <kbd>Shift</kbd>. The other modules fade and only the lines from one chosen module to another stay lit, so **Files** shows which files connect them. The side panel lists the dependencies between them. On **Functions**, several modules are shown among every function instead of drawn alone.
- **A double-click goes one level in:** a module opens its files, a module's circle or a file opens its functions.
- **Search** finds functions, classes and files by name. A function opens on **Functions**, a file on **Files**.
- **A click** selects: everything except the selection and what it is linked to fades, until <kbd>Esc</kbd> or a click on the background. A click inside a circle of dots counts as a click on the background.
- **Edges** and **Labels**, on **Files** and **Functions**, hide the lines and the names. A selection still shows its own.

Drag to move the map; zoom with its buttons, a trackpad pinch, or <kbd>Ctrl</kbd>/<kbd>⌘</kbd> and the scroll wheel, so that plain scrolling still scrolls the page. The crosshair button fits the map to the screen. **Expand** makes the map fill the browser window below the navbar; there the plain scroll wheel zooms, and <kbd>Esc</kbd> or the same button returns to the page. **Details** shows and hides the side panel; selecting something opens it again. The [colours](2.7%20Colours%20and%20styles.md#code-quality-map) come from the app palette.

The dots are placed by a small force layout in `static/js/quality/dashboard.js`, computed once for each picture: each module starts as a disc of its dots, links inside a module pull dots that use each other closer, and collisions keep dots apart. No dot leaves its disc, so circles never overlap. **Modules** and **Files** share one layout, which is why a module is in the same place on both. There is no randomness, so the same code map always gives the same picture.

### Cleanup candidates

These are places to look, not failures. Each row opens its place on the map.

| List | What it holds | How it is found |
|---|---|---|
| Functions nothing mentions | Functions and classes that are probably unused | The name appears nowhere else in the code of either repository. Tests do not count, so code used only by its tests is listed. Routes, declared entry points and decorated functions are left out, because a framework calls them. |
| Copied code | The same block of at least 10 lines and 70 tokens in two places | jscpd, the tool behind the **Duplicated blocks** column |
| Files over 1,000 lines | Long code files | Line counts of Python, JavaScript, CSS and template files |

Check a function for a call the map cannot see, such as a name built at runtime, before deleting it.

### Module boundaries

Lists what the map finds at module borders: undeclared dependencies, pairs of modules that depend on each other, private Python names (starting with `_`) used from another module, and declared dependencies without code references.

### What the map cannot see

Lists where reading the code is not enough: URLs, `url_for` endpoints or template names that reach nothing the app serves; routes no script, template or view reaches; URLs and templates chosen at runtime; browser names declared by several scripts; and the limits of the method.

In these sections, a check that found something is a card with its count; a card lists six rows and **Show more** opens the rest. The checks that found nothing share one card at the end, one line each.

**URLs and templates chosen at runtime** is not a list of defects. Each row is a line where the code passes a variable, not a fixed text, to a request, `url_for` or `render_template`: for example a script that reads its URL from a `data-` attribute the template wrote. The map draws no line from such a row, so a route reached only this way can appear under **Routes nothing in the code reaches** although it is used.

The map is static analysis of the source, so it has limits:

- Python imports are exact. Python calls resolve only through local definitions and imports; calls on objects and dynamic dispatch are missing.
- Browser scripts are parsed with espree, the parser ESLint uses. A script's top-level declarations, `window` properties and members of a shared namespace such as `MapComponents.MapCore` are its exports. A name another script reads but does not declare links to the one script that exports it; a name exported by several scripts is listed instead. Whether both scripts load on the same page is not checked.
- Flask routes are read from their `@route` decorators, and a test checks them against the routes the app registers. A URL string in a script or template links to the route it matches, with any part known only at runtime matching one path segment; a `url_for` endpoint links exactly. A URL built entirely at runtime, such as `fetch(url)` with `url` passed in, is listed as a blind spot.
- Shared database tables, external services, the data a view passes to its template and links in the Markdown documentation are not links. A dotted declared dependency can still be real.

## Read the results

**CI results by module** has one row for each module:

| Column | Meaning |
|---|---|
| Criticality | Declared in the catalog, as described in [Criticality](#criticality) |
| Tests | Result of the tests associated with the module. Skipped tests or declared test files without results need attention. |
| Branch coverage | Share of the module's runtime code branches the tests executed, also drawn as a bar. Not applicable to modules without runtime code, such as styles. |
| Duplicated blocks | Code clones of at least 10 lines and 70 tokens that touch the module, found by jscpd. The status says whether any is new since the reviewed baseline. |
| Docs | Required catalog slots filled: owner, review date, invariants and the documentation the module's criticality requires |
| Architecture | Whether the module's imports respect the enforced boundaries, such as the application never importing the engine |

There is no combined quality score. Each column stands on its own, and a high percentage does not replace the publication, rollback and contract tests that the invariants call for.

### Statuses

| Status | Meaning |
|---|---|
| `pass` | The recorded check or comparison passed |
| `fail` | Executed tests or an enforced rule failed |
| `measured` | A valid measurement is available; the percentage is not itself a pass or fail |
| `attention` | Needs review: skipped or missing declared tests, or a new duplicated block |
| `not measured` | The input for this measurement was not collected |
| `not applicable` | There is nothing to measure, for example no runtime code in a styles module |
| `invalid` | The evidence cannot be trusted, such as incomplete coverage |

The pill beside the results says **Checks failed** when a required check failed. Otherwise it says **Complete** when every module has its test and coverage results, and **Partial** when some are absent. It describes the measurements, not the quality of the code.
