# A4 Web App Tests

The supported verification entry point is `make quality` from the app repository. It builds Python 3.13 and Node 22 tooling, runs the app without an installed engine, runs engine tests in a separate interpreter, and supplies a disposable PostGIS database. The same runner powers CI's **Required quality** job. Tests and workflows do not commit or push generated evidence.

## Commands and scope

| Command from the app repository | Purpose | Prerequisites |
|---|---|---|
| `make quality-fast-container` | Ownership, documentation references, architecture, Python/JS/CSS lint, template/config syntax, local vendor checks and focused quality/contract tests | Docker Compose v2 and the engine checkout |
| `make quality-fast` | The same fast checks without Docker | Python 3.13, Node 22.13+, installed app/test/quality requirements, `npm ci` |
| `make quality` | Required checks, all suites, real publication, branch coverage, clone/dead-code ratchets and generated evidence | Docker Compose v2 and the engine checkout |
| `make quality-ci ENGINE_ROOT=../engine ENGINE_PYTHON=/absolute/path/to/engine-venv/bin/python` | Full runner in an already prepared native environment | Isolated engine interpreter and explicit `TEST_POSTGRES_URI` in addition to the fast prerequisites |
| `make quality-down` | Remove the disposable quality services and volumes | Docker Compose v2 |

Set `ENGINE_ROOT` when the engine is not at `../engine`. The [quality guide](../quality/README.md) gives complete setup, environment variables, commands, artifacts, maintenance and troubleshooting instructions. The fast command prints the deeper verification command; passing it alone does not establish coverage or publication safety.

## Independent test boundaries

| Suite | Responsibility | Evidence from a full run |
|---|---|---|
| Application Python | Flask/API behavior, independent bundle reader, imports, publication, scheduling, documentation and exports | `quality/raw/app-tests.xml`, `app-python-coverage.json` and `.xml` |
| Browser JavaScript | Map adapters/lifecycle, filters, popups, review pages and progress presentation | `quality/raw/javascript-tests.json`, `javascript-coverage.json`, and `lcov.info` |
| Engine Python | Source-neutral matching, input integrations, profiles, validation and atomic bundle writing | `quality/raw/engine-tests.xml`, `engine-python-coverage.json` and `.xml` |
| Producer/consumer subprocess contract | Real engine output and progress consumed by the app without cross-project Python imports | `quality/raw/contract-tests.xml` |
| PostGIS publication | Staging visibility, rollback and publication lock timeout against a real database | Included in application test evidence |

The PostGIS database name must end in `_test`. Publication tests reset its public schema. The quality Compose project creates its own database and does not use the deployment database. App-only pytest runs skip publication cases without `TEST_POSTGRES_URI`. The three progress producer/consumer cases intentionally skip in the isolated app run and execute separately with the engine interpreter during `make quality`.

Application contract tests read `tests/fixtures/result-v1` with engine imports forbidden. Hypothesis checks valid bundle variations and malformed values, including coordinate boundaries, identifiers, section shapes and reference invariants. Engine properties exercise matching and result validation independently. Small synthetic fixtures keep these checks offline and reproducible; no national download is needed.

Pipeline-progress coverage is contract-oriented: the engine validates its stage catalog and structured events, the app validates plan merging and state transitions, and the browser validates a generic tree renderer, including a synthetic stage unknown to the frontend. Algorithm tests do not duplicate UI assertions.

## Trustworthy measurements

Python collection includes branches and unexecuted source files. Browser tests use the shared instrumented loader; first-party scripts that no test loads remain visible at zero coverage. The coverage sanity gate rejects absent source files, zero executed production coverage, invalid hit totals, missing branch collection and evidence collected for different inputs. Unexpected browser errors, rejected promises, console errors and leaked timers fail tests.

`quality/latest.json` aggregates results by ownership module. `quality/report.md` and the [Code Quality page](4.3%20Code%20Quality.md) render that evidence. Coverage targets, changed-line coverage and trends start advisory; reviewed clone/dead-code baselines prevent new structural debt. Missing, stale or invalid evidence is reported explicitly. Keep the checkout stable during a full run: modifying sources, tests or documentation invalidates its recorded fingerprints.

## CI and periodic work

The main workflow runs the required local-equivalent gate and uploads evidence even when a check fails. The dependency workflow audits production Python dependencies and npm packages on pull requests and weekly. CodeQL analyzes Python and JavaScript. A separate scheduled/manual mutation sample probes critical engine result validation; its survivors remain advisory until a reviewed baseline is established.

Repository administrators must configure the pinned engine repository/revision/credential and required branch checks as described in the quality guide. Workflow files cannot establish branch protection themselves. Full browser E2E/visual regression, performance budgets and broader mutation coverage are tracked rollout work; a unit-suite pass does not imply those checks ran.
