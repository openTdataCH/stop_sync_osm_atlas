# A3.5 Pipeline Progress

The analytics page presents live pipeline progress without coupling the review application to matching-engine internals. The interface is a versioned stage plan plus state keyed by stable stage IDs.

## Data model

`backend/services/pipeline_progress.py` owns the eight top-level phases and the application substages for database loading and publication. The separately installed engine emits its own self-describing substage plan. `backend/services/pipeline_status.py` validates and merges both plans into the persisted status:

```json
{
  "progress_schema_version": 2,
  "stage_plan": [
    {
      "id": "database.validate",
      "parent_id": "database",
      "phase": "database",
      "label": "Validate the result bundle",
      "description": "Verify the bundle schema, checksums and entity references.",
      "order": 10,
      "progress_kind": "indeterminate"
    }
  ],
  "stage_states": {
    "database.validate": {
      "status": "complete",
      "started_at": "2026-09-21T10:00:00+00:00",
      "finished_at": "2026-09-21T10:00:02+00:00",
      "duration_seconds": 2.0
    }
  }
}
```

Allowed states are `waiting`, `running`, `complete`, `reused`, `skipped` and `failed`. A determinate stage may additionally supply `processed` and `total`. The UI never invents a percentage for indeterminate work.

## Execution order

The phases follow the actual processing sequence:

1. **Check sources** (`source_check`): check ATLAS and timetable sources.
2. **Prepare source files** (`source_files`): prepare ATLAS, download timetable data, prepare patterns, build timetable identities/routes, then download OSM.
3. **Load matching inputs** (`matching_inputs`): read ATLAS, read cached timetable products, optionally prepare an explicitly supplied GTFS feed, then parse OSM.
4. **Stop matching** (`stop_matching`).
5. **Route matching** (`route_matching`).
6. **Build result bundle** (`bundle`).
7. **Stage database** (`database`).
8. **Publish dataset** (`publish`).

Applicable bullets execute in displayed order. Cache hits resolve in place as `reused`. `match-import` skips source checks and reuses source files, then executes input loading normally. `import` skips acquisition, input loading and matching, and reuses the existing bundle.

This regrouping is progress schema version 2: child IDs remain stable, but their parent phases and ordering change. Update the engine, scheduler and web application together between runs. Version-1 live events are rejected; persisted historical plans are displayed as recorded. No result-bundle migration or processing-order change is required.

## Application substages

| Parent | Stable ID | Label |
|---|---|---|
| Stage database | `database.validate` | Validate the result bundle |
| Stage database | `database.prepare` | Prepare application records |
| Stage database | `database.load` | Load and index the staged database |
| Publish dataset | `publish.swap` | Publish the new dataset |
| Publish dataset | `publish.analytics` | Generate analytics |

Import functions receive an optional structured stage callback. Delivery is best-effort: a callback exception is logged and cannot abort work or mask its original exception. `publish.swap` finishes only after its transaction commits, and cleanup follows the committed publication result even if reporting fails.

Analytics errors are explicit. The standalone importer raises `PublishedDatasetError` with the committed manifest if reports cannot be generated. The runner preserves that publication, records the data-update timestamp, and finishes with `dataset_published: true` and nonempty `warnings`. The page shows “Dataset published with warnings”; it does not claim that analytics completed. A warning run does not advance `last_success_at`.

## Engine boundary

The scheduler reads newline-delimited engine JSON. Version-2 progress events are completely validated before a pure transition function computes one persisted update; unversioned JSON remains diagnostic log output and never drives UI state. New substages require no application mapping. Invalid telemetry is logged and ignored without changing the plan or aborting the subprocess reader.

An engine can introduce a new child stage without changing the browser bundle: the plan includes its label, description, parent and order. Conflicting definitions for an existing ID are rejected during a run. Unknown schema versions are rejected rather than guessed.

Cache and run-mode outcomes remain explicit. When a whole phase is marked `reused` or `skipped` before the engine plan arrives, later children inherit that outcome.

Engine events may only describe children of engine-owned phases, not roots or database/publication work. Numeric fields must be finite and nonnegative, counts must be integers, and a supplied `stage_spec.id` must match `stage_id`. Definitions cannot conflict and a plan cannot repeat an ID.

## Lifecycle and persistence

`pipeline_progress.apply_progress_event(state, event, now)` owns child transitions without performing I/O. `project_stage_states` derives parent states from those children and runner phase information. The browser uses these parent states instead of assuming that every earlier phase succeeded. Parent durations sum their child work durations. Preparing source files finishes before loading matching inputs begins; reuse and skip decisions consume no work time.

The runner binds events to its application run ID. Storage rechecks that ID and the active-run state under its write lock or Redis transaction. Terminal runs ignore late updates; completed or failed children ignore duplicate events and delayed heartbeats. An explicit start may supersede an earlier reuse/skip decision, but there is no implicit retry of completed or failed work.

Run failure marks active children failed and never-started children skipped with a reason, preserving work that already finished. Successful exit with unresolved children produces warnings instead of inventing completion. Starting a new run resets its plan, children, publication flag and warnings. Self-describing lifecycle events can still introduce a missing child when the initial plan was missed, subject to the same validation rules.

## Browser rendering

`static/js/pages/data-analytics.js` renders the eight parent phases and reconciles both the timeline and persistent substage groups from `stage_plan`. Persisted version-1 runs retain their original nine-phase grouping; a new run replaces that plan without a page reload. It uses DOM creation and text assignment rather than HTML from the event payload. Existing nodes are retained when content is unchanged, preserving selection and focus during polling. Late-arriving phases and children are placed in plan order; unchanged nodes are not moved on each poll. IDs are treated as opaque strings, not CSS selectors.

Card summaries say “N/M finished”, counting completed, reused and skipped children while retaining each child’s explicit status.

Hovering a timeline segment or focusing it with the keyboard gently highlights both the segment and its corresponding substage card. After a short hover pause, the page scrolls smoothly toward an off-screen card, accounting for the sticky navigation. Keeping the timeline visible takes priority: scrolling stops when the bar reaches the top inset, even if the card cannot fully fit below it. Visible cards do not trigger scrolling, and progress refreshes do not repeat it. The highlight follows the phase ID, survives progress refreshes, and clears when hover or focus leaves. Reduced-motion preferences disable smooth scrolling and highlight transitions.

Every applicable child is listed from the beginning: pending work is gray, active work is blue, successful or reused work is green, and failures are red. Completed bullets remain visible during later phases and after the run. Reused work uses the three-arrow reuse symbol rather than a retry-style arrow. Descriptions appear as native titles, while state and elapsed time remain visible text.

## Test strategy

- Catalog tests validate unique IDs, metadata, ordering and parent references.
- Pure transition and state-service tests cover malformed input without writes, ownership, late events, interrupted runs, mixed cache outcomes and storage run guards.
- Import tests use real bundle validation/projection and exercise explicit analytics failures and broken reporting callbacks.
- Engine tests run tiny CLI examples and assert progress alongside real cold/warm/corrupt-cache behavior.
- Jest tests cover late plans, reordered children, retained nodes/focus, opaque IDs, terminal parent states and publication warnings.
- PostGIS tests verify that completion observes the committed publication, lock timeouts emit failure, and a broken reporting callback cannot alter commit or cleanup.
- The dedicated CI composition job runs `PROGRESS_CONTRACT_ENGINE=engine python -m pytest tests/test_engine_progress_contract.py -q`. It replays actual Swiss, explicit-GTFS and generic GTFS CLI events through the app consumer. Normal app tests skip it and require no engine installation.

Tests do not assert exact wall times, heartbeat counts or national-dataset row totals. Those values are operational data rather than stable behavior.
