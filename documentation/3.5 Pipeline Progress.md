# A3.5 Pipeline progress

The Data page (`/data/analytics`) shows the progress of a pipeline run live, without the review application knowing how the engine works inside. The engine describes its own stages; the application merges them with its own into one versioned **stage plan**, and records the state of each stage under a stable ID. This page describes that model, the order of the stages, the rules at the engine boundary and how the browser displays them. [A3.3](3.3%20Background%20Scheduler.md#live-status-in-the-web-interface) describes the timeline from a user's point of view.

## Data model

`backend/services/pipeline_progress.py` defines the eight top-level phases and the application's own stages for loading and publishing the database. The separately installed engine sends a plan of its stages, each with its own label and description. `backend/services/pipeline_status.py` validates and merges both plans into the persisted status:

```json
{
  "progress_schema_version": 2,
  "stage_plan": [
    {
      "id": "database.validate",
      "parent_id": "database",
      "phase": "database",
      "label": "Validate the result bundle",
      "description": "Verify the bundle schema, checksums and entity references.",
      "order": 10,
      "progress_kind": "indeterminate"
    }
  ],
  "stage_states": {
    "database.validate": {
      "status": "complete",
      "started_at": "2026-09-21T10:00:00+00:00",
      "finished_at": "2026-09-21T10:00:02+00:00",
      "duration_seconds": 2.0
    }
  }
}
```

A stage is `waiting`, `running`, `complete`, `reused`, `skipped` or `failed`. A stage of kind `determinate` may also report `processed` and `total`; the UI never invents a percentage for indeterminate work.

## Execution order

The phases follow the processing order:

1. **Check sources** (`source_check`): check ATLAS and timetable sources.
2. **Prepare source files** (`source_files`): prepare ATLAS, download timetable data, prepare patterns, build timetable identities/routes, then download OSM.
3. **Load matching inputs** (`matching_inputs`): read ATLAS, read cached timetable products, optionally prepare an explicitly supplied GTFS feed, then parse OSM.
4. **Stop matching** (`stop_matching`).
5. **Route matching** (`route_matching`).
6. **Build result bundle** (`bundle`).
7. **Stage database** (`database`).
8. **Publish dataset** (`publish`).

The stages within a phase run in the order shown. A stage served from cache is marked `reused` in place. `match-import` skips the source check, reuses the source files and then loads the inputs normally. `import` skips acquisition, input loading and matching, and reuses the existing bundle.

This is progress schema version 2. Live events of another version are rejected; runs recorded with version 1 are displayed as they were recorded. When the version changes, update the engine, the scheduler and the web application together, between runs. The result bundle format does not depend on it.

## Application stages

| Parent | Stable ID | Label |
|---|---|---|
| Stage database | `database.validate` | Validate the result bundle |
| Stage database | `database.prepare` | Prepare application records |
| Stage database | `database.load` | Load and index the staged database |
| Publish dataset | `publish.swap` | Publish the new dataset |
| Publish dataset | `publish.analytics` | Generate analytics |

The import functions receive an optional callback for stage events. Reporting is best effort: an exception in the callback is logged, and can neither abort the work nor hide the work's own exception. `publish.swap` finishes only after its transaction has committed, and the cleanup after it depends on the committed result even if reporting fails.

A failure to generate statistics is reported, not hidden. The importer then raises `PublishedDatasetError` with the committed manifest. The runner keeps the publication, records the data-update timestamp and finishes with `dataset_published: true` and non-empty `warnings`. The page shows "Dataset published with warnings" and does not claim that the statistics were generated. Such a run does not advance `last_success_at`.

## Engine boundary

The scheduler reads the engine's output as JSON lines. A version-2 progress event is validated completely before a pure transition function turns it into one stored update. JSON without a progress version is diagnostic log output and never changes what the UI shows. An invalid event is logged and ignored: it neither changes the plan nor stops the reading of the engine's output.

The engine can add a stage without any change to the application, because the plan carries its label, description, parent and order. A conflicting definition for an existing ID is rejected during a run, and an unknown schema version is rejected rather than guessed.

Cache and run-mode outcomes stay explicit. When a whole phase is marked `reused` or `skipped` before the engine's plan arrives, its stages inherit that outcome.

Engine events may describe only stages below the engine's own phases, never a top-level phase or the database and publication work. Numbers must be finite and non-negative, counts must be integers, and a supplied `stage_spec.id` must equal `stage_id`. Definitions cannot conflict, and a plan cannot repeat an ID.

## Lifecycle and persistence

`pipeline_progress.apply_progress_event(state, event, now)` computes stage transitions without any I/O. `project_stage_states` derives the state of each phase from its stages and from the runner's phase. The browser uses these phase states instead of assuming that every earlier phase succeeded. A phase's duration is the sum of its stages' work. Preparing source files finishes before loading matching inputs begins; reuse and skip decisions take no work time.

The runner binds events to its run ID. The store checks that ID and the active-run state again under its write lock or Redis transaction. A finished run ignores late updates; a completed or failed stage ignores repeated events and delayed heartbeats. An explicit start may replace an earlier reuse or skip decision, but completed or failed work is never silently restarted.

When a run fails, running stages are marked failed and stages that never started are marked skipped with a reason; finished work keeps its state. A successful exit with unresolved stages produces warnings instead of invented completion. A new run resets the plan, the stages, the publication flag and the warnings. A lifecycle event that carries its own definition can still add a stage that the initial plan missed, under the same validation rules.

## Browser rendering

`static/js/pages/data-analytics.js` renders the eight phases and keeps both the timeline and the stage lists in step with `stage_plan`. Runs recorded with version 1 keep their original nine-phase grouping; a new run replaces that plan without a page reload. The script creates DOM nodes and assigns text instead of inserting HTML from an event. Nodes whose content is unchanged are kept, so selection and focus survive polling. Phases and stages that arrive late are inserted in plan order; unchanged nodes are not moved on each poll. IDs are treated as opaque strings, never as CSS selectors.

Card summaries say "N/M finished", counting completed, reused and skipped stages, while each stage keeps its own status.

Hovering over a timeline segment or focusing it with the keyboard highlights the segment and its stage card. After a short hover pause, the page scrolls smoothly toward an off-screen card, accounting for the sticky navigation. Keeping the timeline visible takes priority: scrolling stops when the bar reaches the top inset, even if the card cannot fully fit below it. Visible cards do not trigger scrolling, and progress refreshes do not repeat it. The highlight follows the phase ID, survives progress refreshes, and clears when hover or focus leaves. Reduced-motion preferences disable smooth scrolling and highlight transitions.

Every stage of the run is listed from the start: pending work is grey, running work blue, completed or reused work green and failed work red. Completed stages stay visible during later phases and after the run. Reused work uses the three-arrow reuse symbol rather than a retry-style arrow. Descriptions appear as native titles, while state and elapsed time remain visible text.

## Test strategy

- Catalog tests validate unique IDs, metadata, ordering and parent references.
- Pure transition and state-service tests cover malformed input without writes, ownership, late events, interrupted runs, mixed cache outcomes and storage run guards.
- Import tests use real bundle validation/projection and exercise explicit analytics failures and broken reporting callbacks.
- Engine tests run tiny CLI examples and assert progress alongside real cold/warm/corrupt-cache behavior.
- Jest tests cover late plans, reordered children, retained nodes/focus, opaque IDs, terminal parent states and publication warnings.
- PostGIS tests verify that completion observes the committed publication, lock timeouts emit failure, and a broken reporting callback cannot alter commit or cleanup.
- The `producer-consumer-contract` check of `make quality-ci` runs `tests/test_engine_progress_contract.py` with `PROGRESS_CONTRACT_ENGINE` set to the engine checkout. It replays the events of real Swiss, explicit-GTFS and generic GTFS CLI runs through the application's consumer. Ordinary test runs skip it and need no engine.

Tests do not assert exact times, heartbeat counts or row totals of the national dataset: those are operational data, not stable behaviour.
