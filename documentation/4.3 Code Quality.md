# A4.3 Code quality

This page explains the code-quality evidence of both repositories and how to read it: the [code quality dashboard](/quality), the report at the end of this page, the criticality of each module and the statuses the report uses. To run the checks yourself or maintain the module catalog, see [A4.4 Running the quality checks](4.4%20Running%20Quality%20Checks.md).

The **module catalog** (`quality/modules.yml` in each repository) divides the code into modules. A module is a group of files with one responsibility, such as snapshot publication or the query API. The catalog assigns every source file to exactly one module and records the module's criticality, owner, invariants, entry points, dependencies, documentation and tests. The result bundle connects engine and application modules through a declared contract instead of shared code.

The CI run of each commit measures every module and produces the report. Both the dashboard and this page show the report of the deployed commit; [How the report reaches the site](#how-the-report-reaches-the-site) explains how.

## Criticality

Criticality is a maintained judgment, not a measurement. It answers one question: what would the worst plausible defect in this module do? It never depends on how well the module is tested; do not lower it to accommodate weak tests.

| Criticality | The worst defect in the module | Modules |
|---|---|---|
| `critical` | Publishes wrong, incomplete or lost data, or blocks recovery or deployment | Snapshot publication, schema and deployment, matching core, result production |
| `high` | Shows wrong results or stops data from refreshing, while the published data stays recoverable | Query API, review UI, pipeline orchestration, engine input integrations |
| `medium` | Degrades presentation, documentation or tooling; data and results stay correct | Documentation delivery, styles and assets |
| `low` | Is cosmetic or only affects developer convenience | None |

Criticality raises the documentation a module must have. `critical` and `high` modules must record invariants and an explanation page, and `critical` modules also a reference page; the catalog check fails without them. The report's **Docs** column also expects a decision record for `critical` modules.

## Read the dashboard

The dashboard at [`/quality`](/quality) has five parts. **Open the dashboard** at the top of this page and **Code quality dashboard** at the bottom of the documentation sidebar lead to it.

The top of the page shows the CI run the evidence comes from, its commits and whether it is stale, then the module, file and boundary-finding counts.

The map has three levels, chosen at the top left of its toolbar: **Modules**, the module map described next; **Files**, every module's files at once, with the modules in the layers of the module map; and **Functions**, every function and class of both repositories on one functions map, described below.

**Module map.** Each box is a module, taller for more lines of code and coloured by criticality, branch coverage or repository. An arrow goes from the module whose code uses another module to the module it uses; its number, shown when the arrow is hovered or selected, counts the code references: imports, imported names, calls, names shared between browser scripts, script loads, HTTP requests from scripts and templates to Flask routes, and templates rendered, extended or included. A link to a page, such as a navbar entry or a `redirect(url_for(...))`, draws no arrow, because following a link does not use the page's code; the file panel lists it. A module sits above the modules it declares as dependencies, so declared dependencies point down. Hovering a box or an arrow only marks it: a darker outline and thicker arrows of its own, and after a short rest a tooltip beside it. Clicking focuses: everything except the element and its direct links fades, and the side panel shows the details, until <kbd>Esc</kbd> or a click on the background. Drag to move the map; zoom with its buttons, a trackpad pinch, or <kbd>Ctrl</kbd>/<kbd>⌘</kbd> and the scroll wheel, so that plain scrolling still scrolls the page. The crosshair button fits the map to the screen. **Expand**, at the right end of the toolbar, makes toolbar, map, panel and legend fill the browser window below the navbar, which stays visible and usable; it is not the browser's full screen. While expanded, the page behind does not scroll and the plain scroll wheel zooms the map; the same button, shown as a blue **Exit** in the window's top-right corner, or <kbd>Esc</kbd>, returns to the page. **Details**, beside it, shows and hides the side panel. While the panel is open the button is tinted blue. The × on the panel's guide also hides it, and the button then rings once to show where the panel went. Hidden, the map takes the whole width; **Details**, or selecting a box, arrow or dot, opens the panel again. The [colours](2.7%20Colours%20and%20styles.md#code-quality-map) come from the app palette.

| Arrow | Meaning |
|---|---|
| Solid grey | A code dependency the catalog declares |
| Orange dashed | A code dependency the catalog does not declare |
| Dotted grey | A declared dependency without any code reference |
| Dotted purple, to a diamond | A contract between the repositories, such as the result bundle |

**Module files.** Double-click a module, or select it and choose **Open module files**, to see its files. Modules that use it are on the left and modules it uses on the right. Inside, files are ordered by how far they are from where calls enter the module. A ringed file is used from another module, so the arrows that cross the module's border are its actual interface. The side panel compares that interface with the module's declared entry points. **All modules** at the top left of the map, or <kbd>Esc</kbd>, goes back.

**File functions.** Double-click a file, or select it and choose **Open file functions**, to see its functions and classes in line order. What uses them is on the left and what they use on the right, grouped by file; a file box without functions is reached at file level, such as a module-level import or a script's request. Arrows are calls, imported or shared names, HTTP requests and templates rendered. A ringed function is used from another module. Selecting a function lists its callers and callees, page links included; double-clicking one on either side opens its file. The module name at the top left, or <kbd>Esc</kbd>, goes back to the module's files. Calls through objects, such as `self.save()` or `this.render()`, are not seen.

**Functions map.** **Functions** shows every function and class of both repositories together as dots. Each dot is coloured by its module, and each module is a light circle with its name on top; a file's functions start side by side. A larger dot is used by more functions and files. Thin grey lines join a function to the functions it calls or references, in Python and in browser scripts alike; page links draw none, as in the other views. Each dot keeps clear of its neighbours by more than half its own width, so zooming in opens space between the dots where lines and names show, instead of only making the dots larger. Names show on the largest dots at first; zooming in names more dots, as many as fit without covering each other or a circle's name, and hovering any dot shows its name, file and module. While a zoom runs the names grow and shrink with the map, and they are placed again once it rests, so zooming stays smooth. Hovering a circle shows its module or file; a click inside a circle counts as a click on the background, and a double-click goes into it. The list beside the map holds:

- a search box for functions, classes and files: the arrow keys and <kbd>Enter</kbd>, or a click, choose a match. A function is selected and zoomed to; a file selects all its functions and shows the file's details. While one module is shown, a match in another module shows that module instead;
- **Edges** and **Labels** switches, which hide the lines and the names. A selection still shows its own lines and names;
- the modules, most functions first, with their colour and number of functions. Clicking one, or double-clicking its circle on the map, shows only that module's functions, laid out on their own in a circle for each file and fitted to the map, with the module's details in the panel. Double-clicking a file's circle opens its functions in **File functions**. Lines to other modules are not drawn there; a selected function's panel still lists them. Clicking the module again, **Reset**, **All functions** at the top left or <kbd>Esc</kbd> shows every function again.

Hovering a dot marks it and its lines. Clicking it fades everything except the dot and its direct callers and callees, whose lines then keep their meaning: grey inside a module, navy across a declared module dependency, orange dashed across an undeclared one. The side panel shows the same details as in **File functions**: callers, callees and page links. Double-clicking a dot, or **Open file functions** in the panel, opens its file in **File functions**; **All functions** at the top left, or <kbd>Esc</kbd> with nothing selected, comes back to the map with the function still selected. Colour by **Module** is the default here; criticality, branch coverage and repository colour the dots by their module's value. The map is for exploring: the module map stays the place to review boundaries.

The dots are placed by a small force layout in `static/js/quality/dashboard.js`, computed once when **Functions** is first opened: each module starts as a disc of its files' functions, the discs are packed into one cloud, links inside a module pull functions that use each other closer, and collisions keep dots apart. No dot leaves its module's disc, so the circles never overlap; each is drawn just wider than its outermost dot. Links between modules are drawn but do not pull, since a dot pulled towards another module would only pile up on its disc's edge. A module shown alone is laid out once in the same way, with a disc for each file. There is no randomness, so the same code map always gives the same picture.

**Module boundaries.** Lists what the map finds at module borders: undeclared dependencies, pairs of modules that depend on each other, private Python names (starting with `_`) used from another module, and declared dependencies without code references.

**What the map cannot see.** Lists where reading the code is not enough: URLs, `url_for` endpoints or template names that reach nothing the app serves; routes no script, template or view reaches; URLs and templates chosen at runtime; browser names declared by several scripts; and the limits of the method.

**Evidence by module** and **Required checks** show the same evidence as the [report](#latest-report) on this page.

The map is static analysis of the source, so it has limits:

- Python imports are exact. Python calls resolve only through local definitions and imports; calls on objects and dynamic dispatch are missing.
- Browser scripts are parsed with espree, the parser ESLint uses. A script's top-level declarations, `window` properties and members of a shared namespace such as `MapComponents.MapCore` are its exports. A name another script reads but does not declare links to the one script that exports it; a name exported by several scripts is listed instead. Whether both scripts load on the same page is not checked.
- Flask routes are read from their `@route` decorators, and a test checks them against the routes the app registers. A URL string in a script or template links to the route it matches, with any part known only at runtime matching one path segment; a `url_for` endpoint links exactly. A URL built entirely at runtime, such as `fetch(url)` with `url` passed in, is listed as a blind spot.
- Shared database tables, external services, the data a view passes to its template and links in the Markdown documentation are not links. A dotted declared dependency can still be real.

## Read the report

| Column | Meaning |
|---|---|
| Criticality | Declared in the catalog, as described in [Criticality](#criticality) |
| Tests | Result of the tests associated with the module. Skipped tests or declared test files without results need attention. |
| Branch coverage | Share of the module's runtime code branches the tests executed. Not applicable to modules without runtime code, such as styles. |
| Mutation | Share of injected faults the tests detected. Measured only for the engine's result validation. |
| Duplicated blocks | Code clones of at least 10 lines and 70 tokens that touch the module, found by jscpd. The status says whether any is new since the reviewed baseline. |
| Python dead code | Vulture's certain findings in the module's Python files, with the same baseline status. Not applicable to modules without Python. |
| Docs | Required catalog slots filled: owner, review date, invariants and the documentation the module's criticality requires |
| Architecture | Whether the module's imports respect the enforced boundaries, such as the application never importing the engine |

There is no combined quality score. Each column stands on its own, and a high percentage does not replace the publication, rollback and contract tests that the invariants call for.

### Statuses

| Status | Meaning |
|---|---|
| `pass` | The recorded check or comparison passed |
| `fail` | Executed tests or an enforced rule failed |
| `measured` | A valid measurement is available; the percentage is not itself a pass or fail |
| `attention` | Needs review: skipped or missing declared tests, or a new structural finding |
| `not measured` | The input for this measurement was not collected |
| `not applicable` | There is nothing to measure, for example no runtime code in a styles module |
| `invalid` | The evidence cannot be trusted, such as incomplete coverage |
| `stale` | The evidence was measured on other code than the code running here |

The report's overall **evidence** is separate from the check results. `partial` means some measurements are absent. A passing run is `partial`, because security is not measured for any module and mutation only for the engine's result validation. `complete` describes the available measurements, not quality. A missing or unreadable report is shown as **unavailable**: missing evidence is never a pass.

## How the report reaches the site

The site is built from a Git checkout of `main`, so a report reaches it only by being committed. The dashboard and this page show only the report committed in `quality/published/`, never a local run.

Before each deployment:

1. Push your commits to `main` and wait for the **Required quality** CI check to pass.
2. Run `make deploy-report`.
3. Deploy.

`make deploy-report` (`scripts/deploy_report.py`) refuses unless the local `HEAD` is `origin/main` and CI passed on that commit. It downloads that run's evidence and commits four files to `quality/published/`, as "Record quality report for &lt;commit&gt;":

| File | Contents |
|---|---|
| `quality/published/latest.json` | The CI run's measurements, unchanged |
| `quality/published/code-map.json` | The CI run's code map, which the dashboard draws |
| `quality/published/report.md` | The report as Markdown, linking to the CI run for raw evidence |
| `quality/published/publication.json` | The measured commit, the CI run's address and a fingerprint of the shipped code |

CI ignores pushes that only change `quality/published/`, so the report commit does not start another run.

The site cannot compare commit IDs: the report commit always follows the commit it measured, and the application image contains no `.git`. Instead, the fingerprint in `publication.json` hashes the files the `dockerfile` copies into the image (`backend/`, `templates/`, `static/`, `migrations/`, `config/`, `documentation/`, `README.md`, `LICENSE`, `entrypoint.sh` and `engine.ref`). The site hashes the same files where it runs and compares the report's engine revision with `engine.ref`. If either differs, a warning names the measured commit and every result is marked **stale**. On a deployment, that warning means the code was deployed without running `make deploy-report`; run it and deploy again. In a development checkout, uncommitted edits show the same warning.

GitHub keeps CI artifacts for 30 days, so the raw-evidence link of an older report stops working; the committed measurements remain. Never edit the published files by hand.
