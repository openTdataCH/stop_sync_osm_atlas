# A4.3 Code quality

This page explains the code-quality evidence of both repositories and how to read it: the [code quality dashboard](/quality), the report at the end of this page, the criticality of each module and the statuses the report uses. To run the checks yourself or maintain the module catalog, see [A4.4 Running the quality checks](4.4%20Running%20Quality%20Checks.md).

The **module catalog** (`quality/modules.yml` in each repository) divides the code into modules. A module is a group of files with one responsibility, such as snapshot publication or the query API. The catalog assigns every source file to exactly one module and records the module's criticality, owner, invariants, entry points, dependencies, documentation and tests. The result bundle connects engine and application modules through a declared contract instead of shared code.

The CI run of each commit measures every module and produces the report. Both the dashboard and this page show the report of the deployed commit; [How the report reaches the site](#how-the-report-reaches-the-site) explains how.

## Criticality

Criticality is a maintained judgment, not a measurement. It answers one question: what would the worst plausible defect in this module do? It never depends on how well the module is tested; do not lower it to accommodate weak tests.

| Criticality | The worst defect in the module | Modules |
|---|---|---|
| `critical` | Publishes wrong, incomplete or lost data, or blocks recovery or deployment | Snapshot publication, schema and deployment, matching core, result production |
| `high` | Shows wrong results or stops data from refreshing, while the published data stays recoverable | Query API, review UI, pipeline orchestration, engine input integrations |
| `medium` | Degrades presentation, documentation or tooling; data and results stay correct | Documentation delivery, styles and assets |
| `low` | Is cosmetic or only affects developer convenience | None at present |

Criticality raises the documentation a module must have. `critical` and `high` modules must record invariants and an explanation page, and `critical` modules also a reference page; the catalog check fails without them. The report's **Docs** column also expects a decision record for `critical` modules.

## Read the dashboard

The dashboard at [`/quality`](/quality) has four parts.

**Module map.** Each circle is a module, sized by its lines of code and coloured by criticality, branch coverage or repository. An arrow goes from the module whose code uses another module to the module it uses; its number counts the code references: imports, imported names, calls and script loads from templates. A module sits above the modules it declares as dependencies, so declared dependencies point down.

| Arrow | Meaning |
|---|---|
| Solid grey | A code dependency the catalog declares |
| Orange dashed | A code dependency the catalog does not declare |
| Dotted grey | A declared dependency without any code reference |
| Dotted purple, to a diamond | A contract between the repositories, such as the result bundle |

**Module files.** Double-click a module, or select it and choose **Open module**, to see its files. Modules that use it are on the left and modules it uses on the right. Inside, files are ordered by how far they are from where calls enter the module. A file with a blue ring is used from another module, so the arrows that cross the module's border are its actual interface. The side panel compares that interface with the module's declared entry points.

**Module boundaries.** Lists what the map finds at module borders: undeclared dependencies, pairs of modules that depend on each other, private Python names (starting with `_`) used from another module, and declared dependencies without code references.

**Evidence by module** and **Required checks** show the same evidence as the [report](#latest-report) on this page.

The map is static analysis of the source, so it has limits:

- Python imports are exact. Python calls resolve only through local definitions and imports; calls on objects and dynamic dispatch are missing.
- A browser script's top-level declarations and `window` properties count as its exports. References to them from other scripts are a heuristic.
- HTTP requests, database access and data passed to templates are not seen at all. A dotted declared dependency, such as the review UI calling the query API over HTTP, is often real.

## Read the report

| Column | Meaning |
|---|---|
| Criticality | Declared in the catalog, as described in [Criticality](#criticality) |
| Tests | Result of the tests associated with the module. Skipped tests or declared test files without results need attention. |
| Branch coverage | Share of the module's runtime code branches the tests executed. Not applicable to modules without runtime code, such as styles. |
| Mutation | Share of injected faults the tests detected. Measured only for the engine's result validation. |
| Duplicated blocks | Code clones of at least 10 lines and 70 tokens that touch the module, found by jscpd. The status says whether any is new since the reviewed baseline. |
| Python dead code | Vulture's certain findings in the module's Python files, with the same baseline status. Not applicable to modules without Python. |
| Docs | Required catalog slots filled: owner, review date, invariants and the documentation the module's criticality requires |
| Architecture | Whether the module's imports respect the enforced boundaries, such as the application never importing the engine |

There is no combined quality score. Each column stands on its own, and a high percentage does not replace the publication, rollback and contract tests that the invariants call for.

### Statuses

| Status | Meaning |
|---|---|
| `pass` | The recorded check or comparison passed |
| `fail` | Executed tests or an enforced rule failed |
| `measured` | A valid measurement is available; the percentage is not itself a pass or fail |
| `attention` | Needs review: skipped or missing declared tests, or a new structural finding |
| `not measured` | The input for this measurement was not collected |
| `not applicable` | There is nothing to measure, for example no runtime code in a styles module |
| `invalid` | The evidence cannot be trusted, such as incomplete coverage |
| `stale` | The evidence was measured on other code than the code running here |

The report's overall **evidence** is separate from the check results. `partial` means some measurements are absent, which is the honest result of a passing run while security and mutation are not measured for every module. `complete` describes the available measurements, not quality. A missing or unreadable report is shown as **unavailable**: missing evidence is never a pass.

## How the report reaches the site

The site is built from a Git checkout of `main`, so a report reaches it only by being committed. The dashboard and this page show only the report committed in `quality/published/`, never a local run.

Before each deployment:

1. Push your commits to `main` and wait for the **Required quality** CI check to pass, about four minutes.
2. Run `make deploy-report`.
3. Deploy.

`make deploy-report` (`scripts/deploy_report.py`) refuses unless the local `HEAD` is `origin/main` and CI passed on that commit. It downloads that run's evidence and commits four files to `quality/published/`, as "Record quality report for &lt;commit&gt;":

| File | Contents |
|---|---|
| `quality/published/latest.json` | The CI run's measurements, unchanged |
| `quality/published/code-map.json` | The CI run's code map, which the dashboard draws |
| `quality/published/report.md` | The report as Markdown, linking to the CI run for raw evidence |
| `quality/published/publication.json` | The measured commit, the CI run's address and a fingerprint of the shipped code |

CI ignores pushes that only change `quality/published/`, so the report commit does not start another run.

The site cannot compare commit IDs: the report commit always follows the commit it measured, and the application image contains no `.git`. Instead, the fingerprint in `publication.json` hashes the files the `dockerfile` copies into the image (`backend/`, `templates/`, `static/`, `migrations/`, `config/`, `documentation/`, `README.md`, `LICENSE`, `entrypoint.sh` and `engine.ref`). The site hashes the same files where it runs and compares the report's engine revision with `engine.ref`. If either differs, a warning names the measured commit and every result is marked **stale**. On a deployment, that warning means the code was deployed without running `make deploy-report`; run it and deploy again. In a development checkout, uncommitted edits show the same warning.

GitHub keeps CI artifacts for 30 days, so the raw-evidence link of an older report stops working; the committed measurements remain. Never edit the published files by hand.
