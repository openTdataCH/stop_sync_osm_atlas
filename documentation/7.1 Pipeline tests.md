# 7.1 Pipeline Tests

Because running the full 60,000+ stop OSM to ATLAS matching pipeline can take upwards of 15 minutes, we have instituted a **micro-dataset** test methodology to allow rapid iteration when refactoring the pipeline codebase.

## The Minimal Dataset

The tests use pre-extracted deterministic static flat files:
* `tests/data/sample_atlas.csv`
* `tests/data/sample_osm.xml`

These files represent a heavily subsetted boundary box containing ~40 randomized ATLAS stops and matching OSM nodes. Importantly, these ~40 stops intentionally cover all the major matching edge cases needed to guarantee pipeline stability:
* Exact `uic_ref` matches
* `local_ref` disambiguation
* Name matching
* Spatial distance bounding logic
* Route-based parsing
* Duplicate group propagation

By routing these files instead of the full `data/raw` sets into the pipeline, we get sub-second validation of the core execution logic.

## Running the Pipeline Test

To ensure the environment perfectly matches production, the matching pipeline should always be tested from within the Docker container. 

Run the test suite using standard pytest:

```bash
# Execute the full micro-pipeline test
docker-compose run --rm app-dev bash -c "python -m pytest tests/matching_pipeline/test_full_pipeline.py -v"
```

## Creating/Updating the Sample Data

If you introduce new logic (e.g., a new node type) and need the mini-dataset to reflect it, you can regenerate it using the extraction utility:

```bash
docker exec stop_sync_osm_atlas_app_dev bash -c "cd /app && PYTHONPATH=/app python scripts/extract_sample_fast.py"
```

This will randomly sample 40 stops from your active `stops_ATLAS.csv` and pull the corresponding ±5km bounding box from `osm_data.xml`.
