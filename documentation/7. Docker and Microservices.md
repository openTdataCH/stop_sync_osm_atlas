# 7. Microservices and Docker Architecture

This section explains the system's microservices architecture, its background task execution strategy, and the multi-stage Docker build process used to optimize environments.

## Docker Build Architecture: Multi-Stage Strategy

To optimize image size, build times, and security, the application uses a **Multi-Stage Dockerfile**. The backend web application and the background data scheduler serve entirely different purposes and require different dependencies.

The `Dockerfile` is divided into three logical stages:

1. **`base` Stage**: 
   - Installs common system drivers (Python, dos2unix).
   - Installs core shared libraries from `requirements-base.txt` (`SQLAlchemy`, `GeoAlchemy2`, `redis`, `requests`, `pytest`).
2. **`app-stage` Stage (Flask Web API)**:
   - Built on top of the `base` stage.
   - Installs web-specific dependencies (`Flask`, `weasyprint`, `bleach`, `Flask-Limiter`, and `redis` client libraries) from `requirements-web.txt`.
   - Includes system dependencies specific to PDF generation (Cairo, Pango).
   - **Benefit**: Ensures the web application remains extremely lightweight and boots instantly, without the bulk of geospatial data science libraries.
3. **`scheduler-stage` Stage (Data Pipeline)**:
   - Built on top of the `base` stage.
   - Installs heavy data-processing requirements (`geopandas`, `pandas`, `shapely`, `numpy`) from `requirements-scheduler.txt`.
   - Also includes the minimal Flask extension set required by shared ORM/migration imports (`Flask-SQLAlchemy`, `Flask-Limiter`, `Flask-Talisman`, `Flask-Migrate`).
   - Includes heavy system geospatial dependencies (GDAL, Geos, Proj).
   - Does not install PDF rendering libraries like `weasyprint`; scheduler runs skip optional PDF summary generation when those packages are unavailable.
   - **Benefit**: Isolates heavy memory/CPU workloads and large dependencies to the background service while keeping web-only rendering dependencies out of scheduler images.

In `docker-compose.yml`, the `app` service builds targeting `app-stage`, while `scheduler` builds targeting `scheduler-stage`.

## Service Architecture

The `docker-compose.yml` spins up four integrated services:

- **`app`**: The Flask web UI and API. Extremely lightweight.
- **`scheduler`**: The APScheduler-based background runner for the data pipeline. Handles heavy geospatial analysis.
- **`db`**: Postgres + PostGIS database containing the schema and tables for the imported data.
- **`redis`**: A shared distributed cache used for Flask rate limiting, pipeline status storage, and distributed locks.

## Scheduler Behavior

Scheduler implementation:

- Module: `matching_and_import_db/scheduler/service.py`
- Runner: `matching_and_import_db/scheduler/job_runner.py`
- Status store: `backend/services/pipeline_status.py`

Default schedule:

- Timezone: `Europe/Zurich`
- Time: `02:00`

Configurable environment variables:

- `PIPELINE_TIMEZONE`
- `PIPELINE_SCHEDULE_HOUR`
- `PIPELINE_SCHEDULE_MINUTE`
- `PIPELINE_IMPORT_ETA_SECONDS`

## Pipeline Phases and UI State

The scheduler publishes lifecycle state to Redis and exposes it through:

- `GET /api/system/pipeline_status`

Fields include:

- `status` (`idle`, `running`, `failed`)
- `phase` (`atlas_download`, `osm_download`, `matching`, `import`, etc.)
- `message`
- `blocking_maintenance` (true only during blocking import/maintenance window)
- `maintenance` (legacy compatibility field; mirrors `blocking_maintenance`)
- `started_at`, `updated_at`, `finished_at`
- `eta_seconds`
- `run_id`, `trigger`
- `last_success_at`, `last_error`, `next_run_at`

Frontend integration:

- Base layout includes a global maintenance overlay.
- Script polls status API.
- Overlay is visible only when `blocking_maintenance=true`.
- A non-blocking top notice is shown when `status=running` and `blocking_maintenance=false`.

## Entry Point Modes

The shared `entrypoint.sh` supports two runtime modes based on the container that invokes it:

- App mode (default): waits for DB, applies migrations, starts Flask.
- Scheduler mode: waits for DB, starts APScheduler service.

Optional startup run:

- Set `RUN_STARTUP_PIPELINE=true` to run one full pipeline before app startup.

## Manual Operations

Use VS Code tasks to trigger the same pipeline manually:

- `Docker: Run Matching & Import (Existing Data)`
- `Docker: Run Full Data Pipeline (Download & Match & Import)`
- `Docker: Trigger Scheduled Pipeline Now`

All manual runs use the same scheduler runner and status/lock logic.

## Concurrency and Safety

A distributed lock prevents concurrent pipeline runs.

If a run is active and another trigger arrives, the second run is skipped. This avoids overlapping imports, crashing the server due to out-of-memory errors, and inconsistent state in the PostGIS database.

## Operational Notes

- `app` and `scheduler` mount the same project root into `/app`. Any code change on the host immediately reflects in both.
- Shared modules are designed to lazy-load web-only report/PDF dependencies, so scheduler jobs can run without WeasyPrint/Cairo packages.
- Import still rebuilds import tables; blocking overlay is shown only during the blocking maintenance phase.
- Matching/download and other non-blocking phases surface as a lightweight running notice instead of a full-page blocker.
- `user_input_db` remains separate and is not wiped by import jobs.
- If Redis is unavailable, the status service falls back to in-process memory (best effort), though distributed locking may fail.
- The `app` image intentionally omits heavy pipeline dependencies and Node.js; use `scheduler` for pipeline-heavy Python tasks and a Node environment for JavaScript tests.
